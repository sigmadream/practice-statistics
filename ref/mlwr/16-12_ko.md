# 고급 데이터 준비 (Advanced Data Preparation)

실제 머신 러닝 프로젝트에 투자되는 시간의 80%가 데이터 준비에 쓰인다는 뻔한 말은 너무나 널리 인용되어 거의 의문 없이 받아들여집니다. 이 책의 앞선 장들에서도 이러한 진부한 표현을 조건 없이 사실인 양 언급하며 영속시키는 데 일조했습니다. 이것이 분명 일반적인 경험이자 인식인 것은 사실이나, 통계에서 일반화할 때 흔히 그렇듯 이 또한 지나친 단순화(oversimplification)입니다. 현실에서 데이터 준비에 대한 단 하나의 획일적인 경험이란 존재하지 않습니다. 그러나 데이터 준비 작업이 거의 항상 예상보다 더 많은 노력을 수반한다는 것만큼은 분명한 사실입니다.

이전 장들에서처럼 R로 쉽게 읽어 들여 단 몇 줄의 R 코드만으로 처리할 수 있는 단일 CSV 형식의 텍스트 파일이 제공되는 경우는 드뭅니다. 대신, 필요한 데이터 요소들은 여러 데이터베이스에 분산되어 있는 경우가 많으며, 머신 러닝에 피처를 사용하기 전에 이러한 요소들을 수집, 필터링, 재구성(reformat), 그리고 결합하는 과정을 거쳐야 합니다. 이는 이해관계자(stakeholders)로부터 데이터 접근 권한을 얻고 데이터를 탐색하며 이해하는 데 소요되는 시간을 고려하기 전부터 이미 상당한 노력을 필요로 할 수 있습니다.

이 장은 현실 세계에서 준비하게 될 더 크고 복잡한 데이터 세트를 다루도록 여러분을 준비시키는 것(의도된 말장난입니다!)을 목표로 합니다. 이 장에서는 다음 내용을 배우게 됩니다.

- 더 나은 모델을 구축하는 데 데이터 준비가 왜 중요한가
- 데이터를 더 유용한 예측 변수로 변환하기 위한 팁과 요령
- 데이터를 효율적으로 준비하기 위한 특화된 R 패키지

팀과 프로젝트에 따라 데이터 과학자가 머신 러닝 과정을 위해 데이터를 준비하는 데 투자해야 하는 시간은 각기 다르며, 따라서 80%라는 통계는 특정 프로젝트나 단일 기여자의 측면에서 필요한 노력을 과장하거나 과소평가할 수 있습니다.

그럼에도 이 작업을 수행하는 주체가 여러분이든 다른 누구이든, 고급 데이터 준비 과정이 강력한 머신 러닝 프로젝트를 구축하는 데 있어 필수적인 단계라는 부인할 수 없는 사실을 곧 발견하게 될 것입니다.

# 피처 엔지니어링 수행하기 (Performing feature engineering)

시간, 노력, 그리고 상상력은 도메인 전문 지식(subject-matter expertise)을 적용하여 예측을 위한 새로운 피처를 생성하는 **피처 엔지니어링(feature engineering)** 과정의 핵심입니다. 간단히 말해, 이는 데이터를 더욱 유용하게 만드는 예술(art)이라 할 수 있습니다. 좀 더 복잡하게 표현하자면 도메인 전문 지식과 데이터 변환(data transformations)의 결합을 수반합니다. 머신 러닝 프로젝트를 위해 어떤 데이터를 수집하는 것이 유용할지 아는 것뿐만 아니라, 알고리즘의 기대치에 부합하도록 데이터를 어떻게 병합하고, 코딩하며, 정리할 것인지도 알아야 합니다.

피처 엔지니어링은 *제11장, 머신 러닝 성공하기(Being Successful with Machine Learning)*에서 설명한 데이터 탐색(data exploration)과 밀접하게 연관되어 있습니다. 두 과정 모두 가설의 생성 및 테스트를 통해 데이터를 깊이 파고드는 과정(interrogating data)을 포함합니다. 탐색과 브레인스토밍은 어떤 피처가 예측에 유용할지에 대한 통찰력을 이끌어 낼 가능성이 높으며, 피처를 엔지니어링하는 행위 자체도 탐구할 새로운 질문을 촉발할 수 있습니다.

그림 12.1: 피처 엔지니어링은 모델과 데이터가 더 잘 연계되어 작동하도록 돕는 순환 과정의 일부입니다.

피처 엔지니어링은 모델과 데이터가 함께 더 잘 작동하도록 돕기 위해 노력을 투자하는, 순환 속의 순환 과정(cycle within a cycle)의 일부입니다. 한 차례의 데이터 탐색과 피처 엔지니어링은 데이터의 개선으로 이어지고, 이는 더 나은 모델을 훈련하는 반복 과정으로 이어지며, 결과적으로 추가적인 데이터 개선 가능성을 시사합니다. 이러한 잠재적 개선 사항들은 단순히 단순한 데이터 문제를 해결하고 알고리즘이 R에서 실행되도록 하는 데 필요한 최소한의 정리 및 준비 작업에 그치지 않고, 알고리즘이 더 효과적으로 학습하도록 이끄는 단계들까지 포함합니다. 여기에는 다음이 포함될 수 있습니다.

- 알고리즘이 더 빨리 학습하거나 데이터의 더 간단한 표현(representation)을 학습하도록 돕는 복잡한 데이터 변환 수행
- 해석하기 쉽거나 근본적인 이론적 개념을 더 잘 나타내는 피처 생성
- 비정형 데이터(unstructured data) 활용 또는 기본 소스에 추가적인 피처 병합

이 세 가지 모두 깊은 사고와 창의성을 요구하며, 공식화된(formulaic) 방식이라기보다는 임기응변적(improvisational)이고 도메인에 특화되어(domain-specific) 있습니다. 그렇다 하더라도 컴퓨터와 실무자는 상호 보완적인 강점을 활용하여 이 작업을 분담할 수 있습니다. 컴퓨터가 창의성과 임기응변 능력이 부족한 부분은 강력한 연산 능력, 무차별 대입(brute force), 그리고 흔들림 없는 끈기를 통해 보완할 수 있습니다.

## 인간과 기계의 역할 (The role of human and machine)

피처 엔지니어링은 학습 과정의 추상화(abstraction) 단계에서 인간과 기계 간의 협업으로 볼 수 있습니다. *제1장, 머신 러닝 소개(Introducing Machine Learning)*에서 추상화 단계를 저장된 데이터를 더 넓은 개념과 표현으로 변환하는 것이라고 정의했던 것을 상기해 보십시오. 다시 말해, 추상화 과정 동안 원시 데이터(raw data)의 요소들 간에 연결고리가 만들어지며, 이는 학습 목표에 중요한 개념을 나타내게 됩니다. 이러한 관계는 일반적으로 관심 있는 결과에 학습된 개념을 연결하는 모델에 의해 정의됩니다. 피처 엔지니어링 과정에서 인간은 더 나은 성능의 모델을 생성한다는 목표를 가지고 특정 방향으로 추상화 과정을 부드럽게 이끌거나 유도(nudges)합니다.

이렇게 상상해 보십시오. 과거에 여러분이 어려운 개념을 학습하려고 시도했던—아마도 바로 이 교재를 읽고 있던 중이었을 수도 있는—경험을 떠올려 보십시오! 텍스트를 읽고 또 읽어도 개념을 이해하는 데 전혀 도움이 되지 않아 좌절한 끝에 친구나 동료에게 도움을 요청합니다. 어쩌면 이 친구는 비유나 예시를 사용하여 여러분의 이전 경험과 개념을 연결하는 데 도움을 주어 다른 방식으로 개념을 설명할 수 있으며, 이로 인해 "유레카!" 하는 깨달음의 순간을 맞이하게 됩니다. 모든 것이 갑자기 명확해지고, 애초에 왜 이 개념을 이해하지 못했는지 의아해할 것입니다. 이것이 바로 학습 과정을 돕기 위해 한 학습자에서 다른 학습자에게 전이될 수 있는 추상화의 힘입니다. 피처 엔지니어링 과정은 인간이 의도적이고 목적에 맞게 설계된 입력 데이터를 통해 자신의 직관적인 지식이나 도메인 전문 지식을 기계로 전이할 수 있게 해 줍니다.

추상화가 학습 과정의 초석(cornerstone)이라는 사실을 고려하면, 머신 러닝은 근본적으로 피처 엔지니어링이라고 주장할 수 있습니다. 저명한 컴퓨터 과학자이자 인공지능 선구자인 앤드류 응(Andrew Ng)은 "_피처를 고안하는 것은 어렵고, 시간이 많이 걸리며, 전문 지식을 요구합니다. 응용 머신 러닝은 기본적으로 피처 엔지니어링입니다(Coming up with features is difficult, time-consuming, and requires expert knowledge. Applied machine learning is basically feature engineering)_"라고 말했습니다. 컴퓨터 과학 교수이자 머신 러닝 서적 *마스터 알고리즘(The Master Algorithm)*의 저자인 페드로 도밍고스(Pedro Domingos)는 "_어떤 머신 러닝 프로젝트는 성공하고 어떤 프로젝트는 실패합니다. 무엇이 이런 차이를 만들까요? 단연코 가장 중요한 요인은 사용된 피처들입니다(some machine learning projects succeed and some fail. What makes the difference? Easily the most important factor is the features used)_"라고 언급했습니다.

앤드류 응의 인용구는 *뇌 시뮬레이션을 통한 머신 러닝과 AI(Machine Learning and AI via Brain simulations)*라는 제목의 강연에서 나온 것으로, 웹 검색을 통해 온라인에서 확인할 수 있습니다. 페드로 도밍고스의 저서 _마스터 알고리즘(The Master Algorithm)_ (2015) 외에도 _Communications of the ACM_ (2012)에 실린 그의 훌륭한 논문 "머신 러닝에 대해 알아두면 유용한 몇 가지(A few useful things to know about machine learning)"를 참조하십시오. <https://doi.org/10.1145/2347736.2347755>.

피처 엔지니어링을 잘 수행하면 약한 학습기(weaker learners)를 훨씬 강력한 학습기(stronger learners)로 바꿀 수 있습니다. 많은 머신 러닝 및 인공지능 문제는 데이터가 충분히 정리되어 있다고 가정할 때 단순한 선형 회귀 방법으로 해결될 수 있습니다. 아주 복잡한 머신 러닝 기법조차도 충분한 피처 엔지니어링이 주어지면 표준 선형 회귀로 복제될 수 있습니다. 선형 회귀는 스플라인(splines)과 이차항(quadratic terms)을 사용하여 비선형 패턴을 모델링하도록 조정할 수 있으며, 원본 입력 데이터의 상호 작용이나 변환으로 신중하게 설계된 충분한 수의 새로운 피처가 주어질 경우 가장 복잡한 신경망의 성능에 근접할 수도 있습니다.

단순한 학습 알고리즘을 더 복잡한 문제에 적용할 수 있다는 생각은 비단 회귀에만 국한되지 않습니다. 예를 들어 의사 결정 트리는 입력 데이터의 회전을 통해 축-평행(axis-parallel) 결정 경계를 우회할 수 있으며, 초평면(hyperplane) 기반 서포트 벡터 머신은 잘 선택된 커널 트릭(kernel trick)을 통해 복잡한 비선형 패턴을 모델링할 수 있습니다. 입력 데이터 및 학습 문제에 대한 충분한 이해와 많은 노력이 주어진다면 k-NN처럼 단순한 방법조차 회귀나 훨씬 더 복잡한 기법을 모방하는 데 사용될 수 있습니다. 그러나 여기에 함정이 있습니다. 훨씬 복잡한 알고리즘이 자동으로 피처 엔지니어링까지 수행하면서 성능 또한 비슷하거나 더 나을 수 있는데, 굳이 왜 그토록 많은 시간을 들여 단순한 기법에 피처 엔지니어링을 수행해야 할까요?

실제로 데이터에 내재된 패턴의 복잡성에 맞게, 이를 수월하게 처리할 수 있는 학습 알고리즘을 연결하는 것이 아마도 최선일 것입니다. 컴퓨터가 자동으로 수행할 수 있는데도 수작업으로 피처 엔지니어링을 하는 것은 수고스러울 뿐만 아니라 실수를 유발하고 중요한 패턴을 놓칠 우려가 있습니다. 의사 결정 트리나 충분히 큰 규모의 은닉 노드(hidden nodes)를 지닌 신경망(특히 딥러닝 신경망)과 같은 알고리즘은 자체적인 형태의 피처 엔지니어링을 수행하는 데 탁월하며, 이는 수작업으로 하는 것보다 더 엄격하고 철저할 가능성이 높습니다. 불행하게도 이는 이러한 동일한 방법들을 모든 작업에 맹목적으로 적용할 수 있다는 의미는 아닙니다. 결국 머신 러닝에 '공짜 점심(free lunch)'은 없기 때문입니다!

모든 문제에 동일한 알고리즘을 적용한다는 것은 피처 엔지니어링에 만능 접근 방식(one-size-fits-all approach)이 있음을 시사하지만, 우리는 그것이 과학인 동시에 예술이라는 사실을 알고 있습니다. 결과적으로 모든 실무자가 모든 작업에 동일한 방법을 적용한다면, 성능 향상 가능성을 알 길이 없습니다. 어쩌면 약간 다른 피처 엔지니어링 접근 방식이 이탈률(churn)이나 암(cancer)을 더 정확하게 예측하는 모델을 낳고 더 큰 수익이나 더 많은 인명 구조로 이어졌을지도 모릅니다. 약간의 성능 향상만으로도 경쟁에서 상당한 우위를 점할 수 있는 현실 세계에서 이는 명백한 문제입니다.

캐글(Kaggle)의 머신 러닝 대회와 같이 높은 판돈이 걸린 경쟁 환경에서는 각 팀이 동일한 학습 알고리즘에 접근할 수 있으며 어떤 알고리즘이 가장 잘 수행되는지 식별하기 위해 신속히 모두 적용해 볼 수 있는 능력을 갖추고 있습니다. 따라서 캐글 우승자들과의 인터뷰를 읽다 보면 공통된 주제가 등장하는 것은 놀라운 일이 아닙니다. 그들은 대개 피처 엔지니어링에 상당한 노력을 쏟습니다. 2012-2013년 캐글에서 1위 데이터 과학자였던 사비에 코노르(Xavier Conort)는 인터뷰에서 다음과 같이 말했습니다.

> "우리가 사용한 알고리즘은 캐글러(Kagglers)들에게 매우 표준적인 것들이었습니다... 우리는 대부분의 노력을 피처 엔지니어링에 투자했습니다... 또한 과적합(overfitting) 위험에 노출시킬 가능성이 있는 피처는 매우 신중하게 버렸습니다."

피처 엔지니어링은 머신 러닝에서 몇 안 되는 독자적 요소 중 하나이기 때문에 팀 간의 차별화 포인트 중 하나이기도 합니다. 다시 말해 피처 엔지니어링을 잘 수행하는 팀이 경쟁에서 앞서는 경향이 있습니다.

캐글의 "No Free Hunch" 블로그에 처음 게시되었던 사비에 코노르와의 인터뷰 전문을 읽으려면 <https://web.archive.org/web/20190609154949/http://blog.kaggle.com/2013/04/10/qa-with-xavier-conort/>를 방문하십시오. 다른 캐글 챔피언들과의 인터뷰는 <https://medium.com/kaggle-blog/tagged/kaggle-competition>에서 확인할 수 있습니다.

코노르의 발언에 비추어 보면 피처 엔지니어링에 투자해야 할 필요성이 인간의 지능 및 도메인 전문 지식의 적용에 더 큰 투자를 요구한다고 가정하기 쉽지만 이는 항상 사실인 것은 아닙니다. 캐글에서 뛰어난 성과를 낸 "DataRobot" 팀의 멤버인 제레미 아친(Jeremy Achin)은 인간 전문 지식의 유용성이 놀랍도록 제한적이라고 지적했습니다. 그의 팀이 피처 엔지니어링에 소비한 시간에 대해 언급하며 그는 인터뷰에서 다음과 같이 말했습니다.

> "가장 놀랐던 점은 도메인 지식이나 데이터 시각화에서 얻은 통찰력을 사용하려던 거의 모든 시도가 훨씬 더 나쁜 결과로 이어졌다는 것입니다. 우리는 아주 재능 있는 생화학자로부터 2시간짜리 화이트보드 강의를 마련하여 우리가 배운 것에 기반한 아이디어들을 내놓았지만, 그중 어느 것도 효과가 없었습니다."

제레미 아친은 사비에 코노르 및 다른 여러 유명 캐글 그랜드 마스터(Grand Masters)와 함께 캐글 대회에서의 성공을 바탕으로 현재 수십억 달러의 가치를 지닌 DataRobot이라는 인공지능 회사를 설립했습니다. 이들의 소프트웨어는 머신 러닝을 자동으로 수행하며, 이는 그들이 캐글 작업을 통해 배운 핵심 교훈이 컴퓨터가 머신 러닝 과정의 여러 단계를 인간만큼, 어쩌면 더 잘 수행할 수 있다는 것임을 시사합니다.

캐글의 "No Free Hunch" 블로그에 처음 게시되었던 제레미 아친과의 인터뷰 전문을 읽으려면 <https://web.archive.org/web/20190914030000/http://blog.kaggle.com/2012/11/04/team-datarobot-merck-2nd-place-interview/>를 방문하십시오. DataRobot 회사의 웹사이트는 <https://www.datarobot.com>입니다.

물론, 도메인 전문 지식을 바탕으로 요소를 하나씩 결합하여 모델을 구축하는 것과 무엇이 유효한지 알아보기 위해 기계에 모든 것을 쏟아붓는 방식 사이에는 균형이 존재합니다. 오늘날의 피처 엔지니어링이 여전히 대부분 수작업 과정에 의존하고 있지만, 해당 분야의 미래는 이른바 "무엇이 먹히는지 보자(see what sticks)" 식의 산탄총 방식(scattershot approach)으로 향하는 듯하며 **자동화된 피처 엔지니어링(automated feature engineering)**은 빠르게 성장하는 연구 분야입니다. 자동화된 피처 엔지니어링 도구의 근본 원리는 컴퓨터가 부족한 창의성과 도메인 지식을 보완하기 위해 인간이 시도할 수 있는 시간의 한계를 넘어서 훨씬 다양한 피처 조합을 테스트할 수 있다는 아이디어에 기초합니다. 자동화된 피처 엔지니어링은 좁지만 통제된(narrow-but-guided) 인간의 사고를 넓고 체계적인(broad-and-systematic) 컴퓨터의 사고와 맞바꿈으로써, 보다 최적화된 솔루션을 찾아낼 가능성이 있는 반면, 해석의 어려움과 과적합 발생 가능성의 증가와 같은 단점을 수반하기도 합니다.

자동화의 잠재력에 지나치게 들뜨기 전에 주목해야 할 점이 있습니다. 이러한 도구들이 인간으로 하여금 피처 엔지니어링에 대한 사고(thinking) 과정 일부를 외주(outsource) 맡길 수 있게 해 줄지는 모르나, 여전히 코딩(coding) 작업에는 인간의 수고가 필요하다는 사실입니다. 다시 말해 과거 피처들을 일일이 수작업으로 코딩하던 시간이, 유용한 피처를 체계적으로 찾거나 구성하는 함수를 코딩하는 데 쓰이게 된 것입니다.

파이썬(Python) 기반의 `Featuretools` 패키지(및 파이썬 코드와 상호 작용하는 R 패키지 `featuretoolsR`)와 같이 개발 중인 유망한 알고리즘은 피처 생성 과정을 자동화하는 데 도움이 될 수 있지만, 이러한 도구의 사용이 아직 널리 퍼진 것은 아닙니다. 또한 이 방법들은 데이터와 컴퓨팅 시간을 소비해야 하므로, 둘 다 많은 머신 러닝 프로젝트에서 제한 요인이 될 수 있습니다.

Featuretools에 대한 자세한 정보는 <https://www.featuretools.com>을 방문하십시오.

## 빅데이터와 딥러닝의 영향 (The impact of big data and deep learning)

피처 엔지니어링을 인간이 수행하든 자동화된 기계 방법이 수행하든 노력을 더 투자해도 학습 알고리즘 성능 향상이 거의 또는 전혀 없는 지점에 불가피하게 도달하게 됩니다. 더 정교한 학습 알고리즘의 적용은 모델 성능을 약간 향상시킬 수도 있지만 적용할 수 있는 잠재적 방법의 수가 유한하고 성능 차이가 비교적 사소한 경향이 있기 때문에 이것 또한 수확 체감(diminishing returns)의 법칙을 따릅니다. 결과적으로 추가적인 성능 향상이 진정으로 필요한 경우 우리에게 남은 유일한 선택지는 추가적인 피처나 예시를 통해 훈련 데이터 세트의 크기를 늘리는 것입니다. 게다가 추가 열(columns)을 추가하려면 이전 비즈니스 프로세스에서 생성된 데이터를 수정해야 하므로 많은 경우 더 많은 행(rows)을 수집하는 것이 더 쉬운 옵션입니다.

실제로 더 많은 행의 데이터를 포함시켜 달성할 수 있는 성능 향상에는 비교적 낮은 한계(ceiling)가 있습니다. 이 책에 설명된 대부분의 알고리즘은 이내 정체 상태(plateaus)에 빠지며 수천 개의 행을 포함하는 데이터 세트보다 100만 개의 행을 가진 데이터 세트에서 더 나은 성능을 내지 못합니다. 본인 관심 분야의 실제 프로젝트에 머신 러닝 기법을 적용해 본 적이 있다면 이미 이 사실을 직접 관찰했을 것입니다. 많은 실제 애플리케이션의 경우 단 몇 천 개의 행만으로도 충분히 큰 데이터 세트가 되면, 추가 예시는 오히려 계산 시간을 늘리고 메모리 부족을 야기하는 등 추가적인 문제만 일으킬 뿐입니다. 더 많은 데이터가 더 많은 문제를 일으킨다면 자연스럽게 뒤따르는 질문은 "그렇다면 왜 소위 '빅데이터' 시대에 대한 과대광고(hype)가 이렇게 많을까?"입니다.

이 질문에 답하려면 먼저 다양한 크기의 데이터 세트 사이의 철학적 차이를 구별하는 것부터 시작해야 합니다. 분명히 말하지만 "빅데이터(big data)"는 단순히 수많은 행이나 데이터베이스 또는 파일 시스템에서 사용된 저장 공간의 양을 의미하지 않습니다. 사실 데이터 크기는 빅데이터의 존재를 나타낼 수 있는 네 가지 요소 중 하나일 뿐이므로 이 두 가지는 물론 그 이상을 포함합니다.

이른바 빅데이터의 네 가지 V(**four V's of big data**)는 다음과 같습니다.

- 규모(**Volume**): 더 많은 행, 더 많은 열, 또는 더 많은 저장 공간 등 데이터의 문자 그대로의 크기
- 속도(**Velocity**): 데이터가 누적되는 속도로, 데이터 양뿐만 아니라 데이터 처리의 복잡성에도 영향을 미침
- 다양성(**Variety**): 시스템 간 데이터 유형이나 정의의 차이, 특히 텍스트, 이미지, 오디오 데이터와 같은 비정형 데이터 소스의 추가
- 정확성(**Veracity**): 입력 데이터의 신뢰성과 여러 출처에 걸쳐 데이터를 일치시킬 수 있는 능력

이 목록을 위에서부터 아래로 읽어 내려가면 그 요소들이 직관적으로는 덜 명백해지지만 막상 조우했을 때 다루기는 더 까다로워집니다. 볼륨과 속도라는 첫 두 가지 요소는 소위 미디엄 데이터(**medium data**) 영역이라고 부를 수 있는 부분의 기초입니다. 고용량, 고속 데이터를 처리하는 데 어려움이 없다는 것은 아니지만 이러한 문제는 종종 기존에 하던 방식의 규모를 확장(scaling up)하는 것만으로도 해결될 수 있습니다. 예를 들어 더 많은 메모리를 갖춘 빠른 컴퓨터를 사용하거나 계산 효율성이 더 높은 알고리즘을 적용할 수 있습니다. 반면 다양성이 커지고 신뢰성이 떨어지는 데이터가 존재하면 고속, 고용량 규모에서는 머신 러닝 프로젝트에 사용하기 위한 완전히 다른 접근 방식이 필요합니다. 다음 표는 스몰, 미디엄, 빅데이터 영역 간의 몇 가지 차이점을 나열합니다.

스몰에서 미디엄으로, 미디엄에서 빅데이터로 이동할 때는 기하급수적인 투자가 요구됩니다. 데이터 세트의 크기와 복잡성이 증가함에 따라 필요한 인프라 또한 훨씬 더 복잡해져 한층 전문화된 데이터베이스, 컴퓨팅 하드웨어, 분석 도구들이 추가되며, 이 중 일부는 *제15장, 빅데이터 활용하기(Making Use of Big Data)*에서 다룰 것입니다. 이러한 도구들은 매우 빠르게 변화하기 때문에 지속적인 교육과 재숙련(re-skilling)이 필요합니다. 데이터 규모가 커지면 시간은 더욱 중대한 제약 요소가 됩니다. 수많은 변화무쌍한 구성 요소들과 얽힌 프로젝트들은 더 복잡해지고 반복 및 정제 주기가 더 많이 필요해질 뿐만 아니라 말 그대로 작업을 완료하는 데 훨씬 오랜 시간이 걸립니다! 미디엄 크기의 데이터 세트에서 수 분 안에 실행되던 머신 러닝 알고리즘이 훨씬 더 방대한 데이터 세트에서는 클라우드 컴퓨팅 성능의 도움을 받더라도 몇 시간 혹은 며칠이 소요될 수 있습니다.

빅데이터에는 높은 부담이 따르는 만큼 이러한 프로젝트에 인력을 구성하고 리소스를 배치하는 데 있어 규모 면에서 큰 차이가 있는 경우가 많습니다. 이는 단순한 "비즈니스 수행 비용(cost of doing business)"으로 간주됩니다. 필요한 인프라와 데이터 처리 파이프라인을 지원하는 IT 전문가들과 동일한 수의 수십 명의 데이터 과학자가 있을 수도 있습니다. 일반적인 빅데이터 솔루션은 수많은 도구와 기술을 상호 운용할 것을 요구합니다. 이는 데이터 설계자(**data architects**)에게 다양한 컴퓨팅 리소스를 계획 및 구조화하고 보안, 성능, 클라우드 호스팅 비용을 모니터링할 수 있는 기회를 창출합니다. 마찬가지로 데이터 과학자는 데이터 소스 간의 파이프를 구축하고 가장 복잡한 프로그래밍 작업을 담당하는 같거나 더 많은 수의 데이터 엔지니어(**data engineers**)와 매칭되는 경우가 많습니다. 대용량 데이터 처리에 대한 이들의 노력 덕분에 데이터 과학자는 분석과 머신 러닝 모델 구축에 더 집중할 수 있습니다.

오늘날 가장 거대하고 도전적인 머신 러닝 프로젝트를 수행하는 이들의 관점에서 보면, 이 책에서 다루는 거의 모든 예시를 포함한 대다수 일상적인 프로젝트는 스몰 데이터 체제(**small data regime**)라 불리는 범주에 명확하게 속합니다. 이 패러다임 내에서 데이터 세트는 행의 수나 순수한 스토리지 용량 측면에서 "대규모(large)"로 성장할 수는 있으나 결코 진정한 의미의 "빅데이터"가 되지는 않을 것입니다. 컴퓨터 과학 및 머신 러닝 전문가 앤드류 응은 스몰 데이터 영역에서는 여전히 인간의 역할이 큰 영향을 미친다고 지적했습니다. 즉, 인간은 수작업으로 피처를 엔지니어링하거나 성능이 가장 뛰어난 학습 알고리즘을 선택함으로써 프로젝트의 성과에 지대한 영향을 줄 수 있습니다. 그러나 데이터 세트가 "대규모"를 넘어서 "초거대(huge)" 규모, 나아가 빅데이터 체제(**big data regime**)로 진입하게 되면, 또 다른 클래스의 알고리즘들이 성과 정체기(performance plateau)를 돌파하며 수작업 조정으로 얻을 수 있는 작은 이득을 능가하게 됩니다.

그림 12.3: 스몰 데이터 환경에서는 전통적인 머신 러닝 알고리즘이 훨씬 더 복잡한 방법들과 충분히 경쟁할 수 있거나 심지어 더 나은 성능을 보여주기도 하지만, 데이터의 크기가 증가함에 따라 복잡한 방법들의 성능이 월등히 뛰어납니다.

스몰 데이터 체제의 제약 조건 내에서는 단일 알고리즘이나 특정 종류의 알고리즘이 항상 더 나은 성과를 거둔다고 예측할 수 없습니다. 여기서 도메인 지식과 수작업으로 코딩된 피처를 포함한 영리한 피처 엔지니어링은 더 단순한 알고리즘이 훨씬 복잡한 접근 방식이나 딥러닝 신경망을 능가하게 해 줄 수 있습니다.

데이터의 크기가 미디엄 데이터 환경으로 증가함에 따라 앙상블 기법(ensemble approaches, *제14장, 더 나은 학습기 구축(Building Better Learners)*에서 설명함)은 전통적인 머신 러닝 알고리즘을 사용하여 심혈을 기울여 수작업으로 만든 모델보다 훨씬 더 뛰어난 성능을 발휘하는 경향이 있습니다. 빅데이터 환경에서 발견되는 가장 큰 데이터 세트의 경우 딥러닝 신경망(*제7장, 블랙박스 기법 - 신경망 및 서포트 벡터 머신(Black-Box Methods – Neural Networks and Support Vector Machines)*에서 소개되었고, *제15장, 빅데이터 활용하기(Making Use of Big Data)*에서 자세히 다룰 예정)만이 최고의 성능을 발휘할 수 있는 것으로 보입니다. 추가 데이터로부터 학습하는 딥러닝 모델의 역량은 사실상 정체되는 법이 없기 때문입니다. 그렇다면 이는 "공짜 점심은 없다(no free lunch)"는 정리가 틀렸고 모든 것을 다스리는 단 하나의 학습 알고리즘이 진정 존재한다는 뜻일까요?

스몰 데이터 및 빅데이터 체제에 따른 여러 학습 알고리즘의 성능을 시각화한 내용은 앤드류 응의 직접 설명을 통해 확인할 수 있습니다. 이를 찾아보려면 유튜브(YouTube)에서 "Nuts and Bolts of Applying Deep Learning" (영상 3분 경과 시점에 등장) 또는 "Artificial Intelligence is the New Electricity" (영상 20분 경과 시점에 등장)를 검색하시면 됩니다.

특정 알고리즘이 빅데이터 환경에서 다른 알고리즘보다 왜 더 나은 성과를 거두는지, 그리고 왜 "공짜 점심은 없다"는 원칙이 여전히 적용되는지를 이해하려면 먼저 데이터의 크기 및 복잡성, 복잡한 패턴을 학습하는 모델의 역량, 과적합 위험 간의 관계를 고려해야 합니다. 우선 데이터의 크기와 복잡성이 일정하게 유지되지만 훈련 데이터에서 관찰된 것과 더 가깝게 모델링하기 위해 학습 알고리즘의 복잡성을 높이는 경우를 생각해 봅시다. 예를 들어 의사 결정 트리를 지나치게 크게 성장시키거나, 회귀 모델에서 예측 변수의 수를 늘리거나, 신경망에서 은닉 노드를 추가할 수 있습니다. 이 관계는 편향-분산 상충 관계(bias-variance trade-off)의 개념과 밀접하게 연관되어 있습니다. 모델 복잡성을 높임으로써 모델이 훈련 데이터에 더 밀접하게 일치하도록 만들 수 있으므로 결과적으로 고유한 편향을 줄이고 분산을 증가시키게 됩니다.

*그림 12.4*는 모델 복잡성이 증가할 때 발생하는 전형적인 패턴을 보여줍니다. 초기에 모델이 훈련 데이터 세트에 과소적합(underfitted)된 상태일 때 모델 복잡성이 증가하면 모델 오류가 감소하고 모델 성능이 향상됩니다. 그러나 모델 복잡성 증가가 훈련 데이터 세트를 과적합시키는 데 기여하는 시점이 존재합니다. 이 지점을 넘어서면 훈련 데이터 세트에 대한 모델의 오류율은 계속 감소하지만 훈련 수준을 넘어 일반화할 수 있는 모델의 능력이 극적으로 방해받아 테스트 세트 오류율이 증가하게 됩니다. 반복하지만 이 역시 모델의 증가하는 복잡성을 뒷받침할 데이터 세트의 능력이 한계에 부딪혔다고 가정할 때의 이야기입니다.

그림 12.4: 많은 훈련 데이터 세트에서 학습 알고리즘의 복잡성을 높이면 과적합 위험과 테스트 세트 오류가 증가하게 됩니다.

훈련 데이터 세트의 크기와 범위를 늘릴 수 있다면 빅데이터 체제가 두 번째 차원의 머신 러닝 성능을 열어 줄 수도 있지만 이는 오로지 학습 알고리즘 또한 추가된 데이터를 활용할 수 있을 만큼 복잡성을 늘릴 능력을 갖췄을 때만 가능합니다. 이 책에서 지금까지 다룬 것과 같은 많은 전통적인 알고리즘들은 최소한 약간의 추가적인 도움이 없다면 이러한 진화적 도약을 이루어낼 능력이 없습니다.

전통적인 머신 러닝 알고리즘과 이러한 도약을 이룰 수 있는 알고리즘 사이의 연결 고리(missing link)는 알고리즘이 데이터에 대해 학습하려고 시도하는 매개변수(parameters)의 수와 관련이 있습니다. *제11장, 머신 러닝 성공하기(Being Successful with Machine Learning)*에서 매개변수는 데이터의 추상화를 나타내는 학습기의 내부 값으로 묘사되었음을 상기해 보십시오. 전통적으로 위에서 묘사된 편향-분산 상충 관계를 포함한 여러 이유와 더불어 더 복잡한 모델보다 더 단순하고 간결한(parsimonious) 모델이 선호되어야 한다는 믿음 때문에 매개변수가 더 적은 모델이 선호되어 왔습니다. 매개변수 수를 너무 높게 늘리면 데이터 세트가 훈련 데이터를 단순히 암기하게 되어 심각한 과적합을 초래할 것이라 추정되었습니다.

흥미롭게도 이는 사실이지만, *그림 12.5*에서 나타나듯 어디까지나 특정 시점까지만 그렇습니다. 모델 복잡성(즉, 매개변수의 수)이 증가함에 따라 테스트 세트 오차는 이전과 동일한 U자형 패턴을 따릅니다. 그러나 복잡성과 매개변수화가 보간 임계값(**interpolation threshold**)—사실상 모든 훈련 세트 예제를 암기하고 정확하게 분류할 수 있을 만큼 충분한 매개변수가 있는 지점—에 도달하면 새로운 패턴이 나타납니다. 이 임계값에서 모델은 훈련 데이터에 심하게 과적합되었기 때문에 일반화 오류는 최고조에 달합니다. 하지만 모델 복잡성이 한층 더 증가하면 테스트 세트 오류는 다시 떨어지기 시작합니다. 충분한 추가적 복잡성이 주어지면 훈련 데이터에 심하게 과적합된 모델조차 (적어도 우리가 "과적합"이라고 알고 있는 기존 개념에 비추어 볼 때) 정교하게 튜닝된 전통적 모델의 성능을 넘어설 수 있습니다.

그림 12.5: 일부 알고리즘은 훈련 데이터에 심하게 과적합된 것처럼 보인 이후에도 빅데이터를 활용하여 일반화를 잘 수행할 수 있습니다.

여기에 묘사된 "이중 하강(double descent)" 곡선의 명백한 모순에 대한 더 많은 정보를 원하시면, 다음의 획기적인 논문을 참조하십시오: _Reconciling modern machine-learning practice and the classical bias–variance trade-off, Belkin M, Hsu D, Ma S, and Mandal S, 2019, Proceedings of the National Academy of Sciences, Vol. 116(32), pp. 15,849-15,854_.

이렇듯 예상 밖의 결과를 설명해 주는 메커니즘은 보간 임계값을 넘어 추가 매개변수화 능력을 갖춘 모델에서 일어나는 흥미롭고, 어쩌면 마법 같기도 한 변환과 관련이 있습니다. 학습기가 훈련 데이터를 보간(훈련 데이터에 충분히 부합)할 수 있는 충분한 매개변수를 갖게 되면, 추가된 매개변수는 초과매개변수화(**overparameterization**) 상태를 유도하고 이 추가된 복잡성은 더 높은 수준의 사고와 추상화를 가능하게 합니다. 본질적으로 초과매개변수화된 학습기는 고차원적인 개념을 학습할 수 있으며, 이는 곧 피처 엔지니어링 방법이나 학습하는 방법을 스스로 깨우칠 수 있다는 의미가 됩니다. 모델 복잡성이 보간 임계값을 넘어서 크게 증가하면 알고리즘이 문제에 접근하는 방식에서도 엄청난 도약이 이루어질 가능성이 큽니다. 그러나 물론 모든 알고리즘이 이러한 도약을 이룰 수 있는 것은 아닙니다.

계층형 구조에 은닉 노드를 추가함으로써 끊임없이, 그리고 비교적 수월하게 복잡성을 높일 수 있는 심층 신경망(deep neural networks)은 빅데이터를 소비하기 위한 가장 이상적인 후보입니다. *제15장, 빅데이터 활용하기(Making Use of Big Data)*에서 배우게 되겠지만 훌륭하게 설계된 신경망은 이미지, 텍스트, 또는 오디오와 같은 비정형 데이터에서 독자적인 피처를 스스로 엔지니어링할 수 있습니다. 유사하게 범용 함수 근사기(universal function approximator)라는 명칭은 데이터에서 식별한 어떤 패턴이라도 이를 모델링하기 위한 최상의 함수 형태를 스스로 찾아낼 수 있음을 시사합니다. 이쯤 되면 애초에 가졌던 의문, 즉 이런 능력이 도대체 왜 "공짜 점심은 없다"는 원리에 어긋나지 않는가라는 질문으로 다시 돌아가 봐야 합니다. 데이터 세트의 규모가 충분히 거대하다면, 심층 신경망은 단 하나의 최상의 접근 방식인 것처럼 보입니다.

현실 세계의 대다수 프로젝트가 스몰 데이터 체제에 속해 있다는 사실, 심층 신경망은 연산 비용이 비싸고 훈련하기 까다롭다는 점 등 몇 가지 현실적 문제를 잠시 접어두고 생각해 봅시다. 딥러닝이 "공짜 점심은 없다"는 원리에 어긋나지 않는 핵심적인 이유는 신경망이 비대해지고 실질적으로 초과매개변수화되어, 충분히 방대하고 복잡한 훈련 데이터 세트에 접근할 수 있게 되면, 그것은 더 이상 단일 학습 알고리즘(algorithm)이 아니라 일반화된 학습 프로세스(process)가 되기 때문입니다. 이것이 실질적인 의미가 없는 말장난처럼 들린다면 한 가지 은유가 도움이 될 것입니다. 즉, 딥러닝 프로세스는 우리에게 공짜 점심을 제공하는 것이 아니라, 알고리즘에게 스스로 점심을 차리는 방법을 가르칠 기회를 제공하는 것입니다. 여전히 진짜 빅데이터를 확보하는 데 제약이 있고, 대부분의 비즈니스 과제에서 딥러닝의 활용 범위 역시 한정되어 있으므로, 오늘날 가장 강력한 모델을 만들어내기 위해서는 머신 러닝 실무자가 피처 엔지니어링 과정에 개입하여 도움을 줄 필요가 있습니다.

# 실무에서의 피처 엔지니어링 (Feature engineering in practice)

프로젝트나 상황에 따라 피처 엔지니어링의 실제 관행은 매우 다르게 보일 수 있습니다. 일부 거대한 기술 중심 기업들은 데이터 과학자 한 명당 한 명 이상의 데이터 엔지니어를 고용하며, 이를 통해 머신 러닝 실무자들이 데이터 준비 과정보다는 모델 구축과 반복에 집중할 수 있도록 합니다. 프로젝트에 따라 요구되는 데이터 양이 매우 적거나 반대로 어마어마할 수 있는데, 이러한 양적 규모는 딥러닝 기법이나 자동화된 피처 엔지니어링 기술의 사용 여부를 가르기도 하고 불가피하게 만들기도 합니다. 초기 피처 엔지니어링 노력이 거의 필요하지 않은 프로젝트조차도 이른바 "라스트 마일(last mile)"의 문제에 직면할 수 있습니다. 이는 배달 산업에서 마지막 소비자에게 전달되는 "라스트 마일"의 유통 단계에서 투입되는 비용과 복잡성이 비약적으로 치솟는 경향을 의미합니다. 이 개념을 피처 엔지니어링에 접목해 보면, 아무리 다른 팀이나 자동화 시스템이 작업의 대부분을 처리해 준다 하더라도 모델을 위해 데이터를 준비하는 마지막 단계에서 여전히 생각보다 훨씬 많은 수고가 요구될 수 있다는 뜻이 됩니다.

오늘날 대다수의 실제 머신 러닝 프로젝트에서는 상당한 양의 피처 엔지니어링이 요구되는 편입니다. 대부분의 기업들은 데이터 과학자들이 온전히 모델 구축에만 몰두할 수 있을 만큼 조직 차원에서의 분석 성숙도를 달성하지 못했습니다. 여러 기업과 프로젝트가 그 규모가 작거나 제한된 범위 때문에 결코 이런 수준에 도달하지 못할 수도 있습니다. 수많은 중소기업과 중소규모 프로젝트에서 데이터 과학자는 프로젝트의 처음부터 끝까지 모든 측면을 주도해야 합니다. 결국, 데이터 과학자에게 있어 피처 엔지니어의 역할을 이해하고 필요할 때 이 역할을 수행할 수 있도록 철저히 대비하는 것은 매우 필수적인 일입니다.

앞서 언급했듯이 피처 엔지니어링은 과학보다는 예술에 가깝고 프로그래밍 기술 못지않게 상상력을 필요로 합니다. 간단히 말해서 피처 엔지니어링의 세 가지 주요 목표는 다음과 같이 설명할 수 있습니다.

- 이용 가능한 기존 데이터에 추가적인 외부 정보원 보완하기
- 머신 러닝 알고리즘의 요구 사항에 부합하고 모델의 학습을 지원하도록 데이터 변환하기
- 소음(noise)을 제거하는 동시에 유용한 정보의 손실을 최소화하고 반대로 가용한 정보를 최대한 활용하기

피처 엔지니어링을 수행할 때 명심해야 할 전반적인 만트라(mantra)는 "영리해져라(be clever)"입니다. 재치 있고 검소한(frugal) 데이터 마이너가 되기 위해 고군분투해야 하며, 체계적으로 작업하고 어떤 데이터도 낭비되지 않도록 하면서 모든 개별 피처에서 발견할 수 있는 미묘한 통찰력에 대해 생각해야 합니다. 이 규칙을 적용하면 필수적인 창의성을 상기시키고 가장 강력한 학습기를 구축하는 데 필요한 경쟁 정신을 고취하는 데 도움이 됩니다.

각 프로젝트에서 여러분은 이 기술을 고유한 방식으로 적용해야 하지만, 경험이 쌓이면 여러 유형의 프로젝트에 걸쳐 공통적으로 나타나는 일정한 패턴을 발견하게 될 것입니다. 다음 절에서 제시하는 피처 엔지니어링 기술을 위한 7가지 "힌트"는 모든 것을 망라하려는 것이 아니라, 데이터를 어떻게 더 유용하게 만들 것인지에 대한 창의적인 사고를 돕는 영감의 불씨를 제공하기 위함입니다.

최근까지도 안타깝게 시중에 피처 엔지니어링에 관한 책이 드물었지만 이제는 여러 권이 출판되었습니다. 이 주제에 관한 초기 책 중 두 권은 Packt Publishing의 _Feature Engineering Made Easy_(Ozdemir & Susara, 2018)와 O'Reilly의 _Feature Engineering for Machine Learning_(Zheng & Casari, 2018)입니다. _Feature Engineering and Selection_(Kuhn & Johnson, 2019)도 훌륭한 책이며 <http://www.feat.engineering>의 웹에서 무료 버전도 제공됩니다.

## 힌트 1: 새로운 피처 브레인스토밍하기 (Hint 1: Brainstorm new features)

새로운 머신 러닝 프로젝트의 주제 선택은 대개 충족되지 않은 요구(unfulfilled need)에 의해 동기가 부여됩니다. 더 많은 수익 창출, 인명 구조, 또는 단순한 호기심 등 그 동기가 무엇이든 주제가 무작위로 선택되는 경우는 거의 없습니다. 대신 회사의 핵심 문제나 호기심 많은 사람이 소중히 여기는 주제와 관련이 있으며 이 두 가지 모두 작업에 대한 근본적인 관심을 시사합니다. 프로젝트를 추진하는 회사나 개인은 해당 주제와 관심 있는 결과에 기여하는 중요한 요인들에 대해 이미 상당한 지식을 가지고 있을 가능성이 높습니다. 이러한 도메인 경험과 전문 지식을 바탕으로 프로젝트를 의뢰한 회사, 팀, 또는 개인은 자신들만이 가져올 수 있는 작업에 대한 독점적인 통찰력을 보유하고 있을 것입니다.

이러한 통찰력을 활용하기 위해, 머신 러닝 프로젝트의 초기 단계, 즉 피처 엔지니어링에 바로 앞서 이해관계자들을 모아 관심 대상인 결과와 연관될 수 있는 잠재적 요인들에 대해 아이디어를 구상하는 브레인스토밍 세션을 갖는 것이 유용할 수 있습니다. 이 과정에서는 기존 데이터 세트에서 쉽게 얻을 수 있는 정보에만 국한되지 않는 것이 중요합니다. 대신 더 추상적인 수준에서 인과 관계(cause-and-effect) 과정을 고려하여 결과에 긍정적 또는 부정적 방향으로 영향을 미치기 위해 당길 수 있는 다양한 은유적 "레버(levers)"를 상상해 보십시오. 이 세션 동안 가능한 철저하게 모든 아이디어를 도출해 보십시오. 모델에 원하는 것을 무엇이든 넣을 수 있다면 무엇이 가장 유용할까요?

브레인스토밍 세션의 결정체는 마인드 맵(**mind map**)일 수 있는데, 이는 중심 주제를 중심으로 아이디어를 도식화하는 방법입니다. 심장병 사망률 예측 모델을 설계하는 마인드 매핑 세션의 다음 예시처럼 마인드 맵의 중심에 관심 결과를 배치하고 다양한 잠재적 예측 변수들이 중심 주제에서 바깥쪽으로 뻗어나갑니다.

마인드 맵 다이어그램은 계층 구조를 사용하여 연관된 개념을 연결하거나 유사한 데이터 소스에서 관련된 요인들을 그룹화할 수 있습니다.

마인드 매핑 세션은 두 개 이상의 요인이 결과에 불균형적인 영향을 미치는, 즉 결합 효과가 개별 효과의 합보다 클(또는 작을) 수 있는 피처 간의 잠재적 상호 작용(interactions)을 드러내는 데에도 도움이 될 수 있습니다. 심장병 예시의 경우, 스트레스와 비만의 복합적인 효과가 각각의 효과를 합친 것보다 심장병을 유발할 가능성이 실질적으로 더 높다는 가설을 세울 수 있습니다. 의사 결정 트리와 신경망 같은 알고리즘은 이러한 상호 작용 효과를 자동으로 찾아낼 수 있지만 그 외의 많은 알고리즘은 그렇지 못합니다. 어느 쪽이든 간에, 이러한 조합을 데이터 내에 명시적으로 인코딩(coded explicitly)해 두면 학습 과정을 돕거나 훨씬 더 단순하고 해석하기 쉬운 모델을 도출하는 데 득이 될 수 있습니다.

## 힌트 2: 텍스트에 숨겨진 통찰력 찾기 (Hint 2: Find insights hidden in text)

숨겨진 데이터의 가장 풍부한 원천 중 하나이자 가장 성과가 좋은 피처 엔지니어링 영역 중 하나는 텍스트 데이터입니다. 머신 러닝 알고리즘은 인간이 언어를 평생 사용하면서 얻은 의미론적 의미(semantic meaning)에 대한 외부 지식이 부족하기 때문에 일반적으로 텍스트 데이터의 가치를 충분히 이끌어내는 데 능숙하지 않습니다.

물론 방대한 양의 텍스트 데이터가 주어진다면 컴퓨터도 같은 것을 배울 수는 있겠지만, 이는 다수의 프로젝트에서 실현 불가능한 일이며 프로젝트의 복잡성만 크게 가중시킬 것입니다. 게다가 각 텍스트 블록은 고유한 특성을 지니며 결과적으로 특정 결과를 암시하는 일종의 지문(fingerprint)처럼 작용하기 때문에, 텍스트 데이터는 차원의 저주(curse of dimensionality)로 인해 있는 그대로 사용할 수 없습니다. 이를 학습 과정에 그대로 차용할 경우, 알고리즘은 텍스트 데이터에 심각하게 과적합되거나 아니면 이를 통째로 무시해버리게 됩니다.

차원의 저주는 기계 학습 모델에서 이미지와 오디오 데이터를 직접 사용하는 것이 마찬가지로 어렵기 때문에 비정형 "빅" 데이터에 좀 더 보편적으로 적용됩니다. *제15장, 빅데이터 활용하기(Making Use of Big Data)*에서는 이러한 유형의 데이터 소스를 전통적인 머신 러닝 접근 방식과 함께 사용할 수 있게 해주는 몇 가지 방법을 다룹니다.

학습 알고리즘을 위한 피처 구축을 담당하는 사람은 텍스트 해석에서 파생된 차원이 감소된 피처(reduced-dimensionality features)를 코딩하여 텍스트 데이터에 통찰력을 더할 수 있습니다. 적은 수의 범주를 선택함으로써 암묵적인 의미를 명시적으로 만듭니다. 예를 들어 고객 이탈 분석에서 회사에 고객의 공개 트위터(Twitter) 타임라인에 대한 접근 권한이 있다고 가정해 봅시다. 각 고객의 트윗은 고유하지만 인간은 긍정, 부정, 중립의 세 가지 범주로 분류할 수 있습니다. 이는 언어의 감정을 분석하는 감성 분석(**sentiment analysis**)의 간단한 형태입니다. 일부 R 패키지를 포함한 컴퓨터 소프트웨어는 단순한 의미론을 이해하도록 설계된 모델이나 규칙을 사용하여 이 프로세스를 자동화하는 데 도움을 줄 수 있습니다. 감성 분석 외에도 주제별로 텍스트 데이터를 범주화하는 것도 가능할 수 있습니다. 이탈의 예시에서 고객 서비스에 관해 트윗하는 고객은 가격에 관해 트윗하는 고객보다 다른 회사로 갈아탈 가능성이 더 높을 수 있습니다.

감성 분석을 수행할 수 있는 R 패키지는 많으며 그중 일부는 유료 서비스 구독을 필요로 합니다. 빠르고 쉽게 시작하려면 직관적인 이름의 `SentimentAnalysis` 및 `RSentiment` 패키지와 `Syuzhet` 패키지를 확인하십시오. 이 패키지들 모두 단 단 몇 줄의 R 코드만으로 문장을 긍정적 또는 부정적으로 분류할 수 있습니다. 텍스트 마이닝 및 감성 분석에 대해 더 깊이 알고 싶다면 *Text Mining with R: A Tidy Approach, 2017, Silge J and Robinson D*라는 책을 참조하십시오. 이 책은 <https://www.tidytextmining.com>에서 볼 수 있습니다. 추가로 *Text Mining in Practice with R, 2017, Kwartler T*도 참조하십시오.

텍스트의 외적인 의미를 코딩하는 것을 넘어 피처 엔지니어링의 정교한 기술 중 하나는 텍스트 데이터 내에 묻혀 있는 숨겨진 통찰력을 찾아내는 것을 포함합니다. 특히, 텍스트 데이터에 코딩된 정보 중에는 텍스트의 직접적인 해석과는 관계없지만 포커 게임에서의 "텔(tell)"—플레이어의 비밀스러운 의도를 드러내는 미세한 표정(micro-expression)—처럼 텍스트에 우연히 또는 무심결에 등장하는 유용한 정보가 있을 수 있습니다.

숨겨진 텍스트 데이터는 연령, 성별, 직급, 위치, 재산 또는 사회경제적 지위(socioeconomic status)와 같은 개인의 정체성 측면을 밝히는 데 도움이 될 수 있습니다. 몇 가지 예는 다음과 같습니다.

- Mr.와 Mrs. 또는 Jr.와 Sr.와 같은 이름 및 경칭, 전통적인 이름과 현대적인 이름, 남성 이름과 여성 이름 또는 재산과 관련된 이름
- CEO, 사장, 보좌관, 시니어, 이사(director)와 같은 직함 및 카테고리
- 우편 번호, 건물 층수, 국내외 지역, 1등석 티켓, 사서함 및 유사한 것들과 같은 지리적 및 공간적 코드
- 은어(slang)나 개인 정체성의 특정 측면을 드러낼 수 있는 표현과 같은 언어적 표시

이러한 유형의 숨겨진 통찰력을 찾기 시작하려면 관심 결과를 염두에 두고 텍스트 데이터를 체계적으로 검토해야 합니다. 텍스트가 결과에 영향을 미칠 수 있는 미묘한 단서를 어떻게 드러낼 수 있는지 생각하면서 가능한 한 많은 텍스트를 읽으십시오. 패턴이 나타나면 통찰력을 바탕으로 피처를 구성하십시오. 예를 들어 텍스트 데이터에 직함이 흔히 포함되어 있다면 직업을 엔트리 레벨(entry-level), 중간 관리자(mid-career), 임원(executive)과 같은 직급으로 분류하는 규칙을 만드십시오. 그런 다음 이러한 직급을 대출 연체 또는 이탈 가능성과 같은 결과를 예측하는 데 사용할 수 있습니다.

## 힌트 3: 수치 범위 변환하기 (Hint 3: Transform numeric ranges)

특정 학습 알고리즘은 다른 알고리즘에 비해 수치 데이터에서 더 잘 학습하는 능력을 갖추고 있습니다. 수치 데이터를 사용할 수 있는 알고리즘 중에서도 수치 값의 범위에서 중요한 절단점(cut points)을 학습하는 데 뛰어나거나, 극도로 치우친(skewed) 데이터를 처리하는 데 능숙한 알고리즘들이 있습니다. 수치 피처를 사용하는 데 적합한 의사 결정 트리 같은 방법도 수치 데이터에서 과적합하는 경향이 있으며, 따라서 수치 범위를 더 적은 수의 잠재적 절단점으로 줄이는 변환이 유리할 수 있습니다. 회귀분석 및 신경망과 같은 다른 기법들은 로그 스케일링(log scaling), 정규화(normalization), 계단 함수(step functions) 등 수치 데이터의 비선형 변환에서 이득을 얻을 수 있습니다.

이러한 기법 중 다수는 앞선 장에서 이미 다루고 적용된 바 있습니다. 예를 들어, *제4장, 확률적 학습 – 나이브 베이즈를 사용한 분류(Probabilistic Learning – Classification Using Naive Bayes)*에서 우리는 수치 데이터를 나이브 베이즈 알고리즘에 사용할 수 있도록 범주형 데이터로 변환하는 수단으로서 이산화(discretization, "비닝(binning)" 또는 "버키팅(bucketing)"이라고도 함) 기법을 살펴보았습니다. 이 기법은 수치 데이터를 기본적으로 처리할 수 있는 학습기에게도 때때로 유용한데 결정 경계(decision boundary)를 명확히 하는 데 도움이 될 수 있기 때문입니다.

다음 그림은 연령이라는 수치 예측 변수를 사용하여 심장병을 예측하는 가상 모델에 적용되는 이 과정을 보여줍니다. 왼쪽을 보면 수치로 표시된 연령이 증가할수록 색상이 더 어두워지며 이는 나이가 들수록 심장병 발병률이 증가함을 나타냅니다. 겉보기에는 이렇게 뚜렷한 추세에도 불구하고 의사 결정 트리 모델은 적절한 절단점을 식별하는 데 어려움을 겪을 수 있으며 이를 임의로 수행하거나 수많은 작은 절단점을 선택할 수 있습니다. 이 두 경우 모두 훈련 데이터에 과적합될 가능성이 큽니다. 이러한 선택을 모델에 맡기는 대신 사전 지식(_a priori_ knowledge)을 활용하여 "젊은(young)" 환자와 "나이 든(old)" 환자를 위한 사전 정의된 그룹을 만드는 편이 나을 수 있습니다. 이 방식은 실제 기저에서 나타나는 점진적 변화(gradient)의 미묘한 차이를 일부 상실하긴 하지만, 의사 결정 트리의 "고분산(high variance)" 접근법을 이론에 기반한 이산화라는 "고편향(high bias)" 접근법과 맞바꿈으로써 모델이 향후 들어올 데이터에 대해 더 잘 일반화되도록 돕습니다.

## 힌트 4: 이웃의 행동 관찰하기 (Hint 4: Observe neighbors’ behavior)

피처 엔지니어링 중에 숨겨진 통찰력을 표면화하는 덜 알려진 방법 중 하나는 "유유상종(birds of a feather flock together)"이라는 상식을 적용하는 것입니다. 우리는 이 원칙을 *제3장, 게으른 학습 – 최근접 이웃을 사용한 분류(Lazy Learning – Classification Using Nearest Neighbors)*에서 예측에 적용했지만, 유용한 예측 변수를 식별하기 위한 유용한 사고방식이기도 합니다. 이 아이디어는 데이터셋의 행 전체에 명시적 또는 암시적 그룹이 존재할 수 있으며, 하나의 예시가 해당 이웃이나 그룹 내의 다른 예시와 어떻게 연관되는지 검토함으로써 통찰력을 얻을 수 있다는 사실에 근거합니다.

실제 데이터에서 자주 발견되는 명시적 그룹화의 한 예는 가구(households)입니다. 많은 데이터셋에는 개인 기반 행뿐만 아니라 가구 식별자도 포함되어 있어, 행들을 가구 그룹으로 연결하고 이 그룹들의 구성을 바탕으로 새로운 피처를 만들 수 있습니다.

예를 들어, 누군가가 가구에 속해 있다는 것을 알면 이 피처들이 원본의 개인 수준 데이터셋에 포함되지 않았더라도 결혼 여부 및 자녀나 부양가족의 수를 유추할 수 있습니다. 단순히 그룹의 피처들 중 일부를 계산하거나 집계(aggregating)하는 것만으로도 매우 유용한 예측 변수를 얻을 수 있습니다.

여기에서 그룹 내 레코드 간에 정보를 공유하는 것도 가능합니다. 예를 들어 배우자 한 명의 소득을 아는 것도 유용하지만, 둘 다 알면 사용 가능한 총소득을 더 잘 나타낼 수 있습니다. 그룹 내의 분산 정도(measures of variance)도 유용한 정보를 줄 수 있습니다. 배우자들이 특정 속성에 대해 일치하거나 동의하지 않을 때 보너스 효과를 제공하는 가구의 측면이 있을 수 있습니다. 예를 들어 두 파트너 모두 특정 통신사에 만족한다고 보고한다면, 한 명의 구성원만 만족하는 가구에 비해 그들은 특히 충성도가 높을 수 있습니다.

이러한 원칙은 덜 명백하지만 여전히 명시적인 우편번호나 지리적 지역과 같은 그룹화에도 적용됩니다. 그룹에 속하는 행을 수집하여 그룹 내 다양성을 세고(count), 합하고(sum), 평균(average)내고, 최댓값이나 최솟값을 구하거나 조사하여, 새롭고 잠재적으로 유용한 예측 변수를 구성할 수 있습니다. 동의나 다양성이 더 높거나 낮은 그룹은 특정 결과에 대해 더 강건(robust)하거나 덜 강건할 수 있습니다.

또한 데이터셋에 직접 코딩되지 않은 그룹화인 암시적 그룹화를 식별하는 것도 가치가 있을 수 있습니다. *제9장, 데이터 그룹 찾기 – k-평균을 사용한 군집화(Finding Groups of Data – Clustering with k-means)*에 설명된 군집화 방법들은 이러한 유형의 그룹화를 찾는 잠재적 방법 중 하나이며, 그 결과인 군집들은 모델에서 직접 예측 변수로 사용될 수 있습니다. 예를 들어 이탈(churn) 프로젝트에서 군집을 모델의 피처로 사용하면, 일부 군집이 다른 군집보다 이탈할 가능성이 더 높다는 사실이 밝혀질 수 있습니다. 이는 이탈이 군집의 기저 인구통계(underlying demographics)와 관련이 있거나 군집 구성원들 사이에서 다소 전염성이 있음을 시사할 수 있습니다.

즉, "유유상종"이라면 비슷한 이웃의 경험에서 선행 지표(leading indicators)를 빌려오는 것이 타당합니다. 이들은 일부 외부 요인에 비슷한 반응을 보이거나 서로 직접적인 영향을 미칠 수 있습니다. 드물거나 독특한 특성을 보이는 암시적 그룹은 그 자체로 흥미로울 수 있습니다. 어쩌면 그중 일부는 "탄광 속의 카나리아"와 같은 선도자(bellwether)일 수도 있습니다—다른 그룹들보다 더 일찍 변화에 반응하는 트렌드세터 말입니다. 이들의 행동을 관찰하고 이러한 그룹을 모델에 명시적으로 코딩하는 것은 모델의 예측 능력을 향상시킬 수 있습니다.

이웃(또는 다음 섹션에서 설명하는 관련 행)의 정보를 사용하는 경우 *제11장, 기계 학습으로 성공하기(Being Successful with Machine Learning)*에서 설명한 데이터 누수(data leakage) 문제에 주의하십시오. 모델이 배포되어 예측을 수행할 당시에 사용 가능한 정보만을 활용해 피처를 엔지니어링 하도록 유의하십시오. 예를 들어, 한 가구 구성원만이 대출 신청서를 작성하고 대출이 승인된 후 다른 배우자의 데이터가 추가되는 경우라면 신용 평가 모델에서 배우자 양쪽의 데이터를 모두 사용하는 것은 현명하지 않습니다.

## 힌트 5: 관련된 행 활용하기 (Hint 5: Utilize related rows)

이전 섹션에서 암시한 "리더 따라가기(follow the leader)" 행동을 활용하는 관행은 동일한 속성이 서로 다른 시점에서 반복적으로 측정되는 시계열 데이터셋의 관련된 행(related rows)이 주어졌을 때 특히 강력할 수 있습니다. 반복 측정을 포함하는 데이터는 유용한 예측 변수를 구성할 수 있는 추가적인 기회를 많이 제공합니다. 이전 섹션에서는 분석 단위 **전반에 걸쳐(across)** 관련된 데이터를 그룹화하는 것을 고려했다면, 이번 섹션에서는 분석 단위 **내에서(within)** 관련된 관측치를 그룹화하는 가치를 고려합니다. 기본적으로, 동일한 분석 단위를 반복적으로 관찰함으로써 그들의 과거 추세를 조사하고 미래에 대한 더 나은 예측을 할 수 있습니다.

가상의 이탈 사례로 돌아가, 온라인 비디오 스트리밍 서비스 구독자의 지난 24개월 데이터에 접근할 수 있다고 가정해 봅시다. 관측 단위(unit of observation)는 고객-월(고객당 월별 한 행)인 반면, 분석 단위는 고객입니다. 우리의 목표는 개입할 수 있도록 어떤 고객이 가장 이탈할 가능성이 높은지 예측하는 것입니다. 기계 학습용 데이터셋을 구성하려면 관측 단위를 수집하여 고객당 하나의 행으로 집계해야 합니다. 여기서 피처 엔지니어링이 특히 필요합니다. 과거 데이터를 분석을 위한 단일 행으로 "롤업(rolling up)"하는 과정에서 추세와 충성도를 살펴보는 다음과 같은 질문을 하며 피처를 구성할 수 있습니다.

- 고객의 월평균 활동이 동종 집단(peers)보다 높은가 낮은가?
- 시간이 지남에 따라 고객의 월간 활동은 어떻게 변하는가? 상승, 하락, 또는 안정적인가?
- 그들의 활동 빈도는 어떤가? 그들은 충성스러운가? 그들의 충성도는 월별로 안정적인가?
- 고객의 행동은 얼마나 일관된가? 월별로 행동의 변동이 심한가?

기본적인 미적분학에 익숙하다면 1차 도함수(first derivative)와 2차 도함수(second derivative)의 개념을 떠올려보는 것이 도움이 될 수 있으며, 이 둘은 시계열 모델에서 유용한 피처가 될 수 있습니다. 여기서 1차 도함수는 행동의 속도(velocity)—즉, 단위 시간당 행동의 횟수를 나타냅니다. 예를 들어 스트리밍 서비스에 월별로 지불한 금액, 또는 월별로 스트리밍 된 TV 프로그램 및 영화의 수를 계산할 수 있습니다. 이들만으로도 유용한 예측 변수이지만, 행동의 가속(acceleration)(또는 감속)을 의미하는 2차 도함수의 맥락에 놓일 때 더욱 유용해질 수 있습니다. 가속은 월별 지출액의 변화나 월별 스트리밍 된 프로그램의 변화와 같이 시간 경과에 따른 속도의 변화입니다. 지출액과 사용량이 모두 높은 고속(high-velocity) 고객은 이탈할 가능성이 낮을 수 있지만, 동일한 고객에게서 급격한 감속(즉, 사용량이나 지출의 큰 감소)이 나타난다면 이는 임박한 이탈을 시사할 수 있습니다.

속도 및 가속에 더하여, 예측 능력을 더욱 향상시키기 위해 일관성(consistency), 신뢰성(reliability) 및 변동성(variability)의 척도를 구성할 수 있습니다. 매우 일관된 행동이 갑자기 변하는 것은 널뛰듯 변하는 행동이 비슷하게 변하는 것보다 더 우려스러울 수 있습니다. 최근 몇 달간 구매가 있었던 비율, 특정 임계값을 충족하는 지출이나 행동이 있었던 달의 비율을 계산하면 단순한 충성도 지표가 제공되지만, 분산을 이용한 보다 정교한 척도도 가능합니다.

## 힌트 6: 시계열 분해하기 (Hint 6: Decompose time series)

이전 섹션에 기술된 바와 같이, 분석 단위당 여러 개의 관련된 행을 갖는 반복 측정 시계열 데이터는 **긴 형식(long format)**으로 되어 있다고 합니다. 이는 대부분의 R 기반 기계 학습 방법에서 요구되는 데이터 유형과 대조됩니다. 학습 알고리즘이 반복 측정 데이터의 관련된 행을 이해하도록 설계되지 않는 한, 시계열 데이터가 반복되는 데이터 행을 반복되는 열로 전치(transpose)하는 **넓은 형식(wide format)**으로 지정되어야 합니다. 예를 들어 1,000명의 환자에 대해 3개월 동안 매월 체중 측정이 기록되는 경우, 긴 형식 데이터셋은 3 * 1,000 = 3,000개의 행과 3개의 열(환자 식별자, 월 및 체중)을 가집니다. *그림 12.8\*에 묘사된 바와 같이, 동일한 데이터셋이 넓은 형식인 경우 행은 1,000개만 포함하지만 열은 환자 식별자용 1개와 월별 체중 수치용 3개, 즉 총 4개가 됩니다.

그림 12.8: 대부분의 기계 학습 모델은 긴 형식의 시계열 데이터를 넓은 형식으로 변환해야 합니다.

넓은 형식의 데이터셋을 구성하려면 예측에 과거 데이터가 얼마나 유용할지 먼저 결정해야 합니다. 더 많은 과거 데이터가 필요할수록 넓은 데이터셋에 더 많은 열을 추가해야 합니다. 예를 들어, 1개월 후 고객의 에너지 사용량을 예측하려면 해당 고객의 과거 12개월분 에너지 사용량을 예측 변수로 활용하기로 결정할 수 있으며, 이로써 계절성의 만 1년 주기가 포함됩니다. 따라서 2023년 6월 에너지 사용량을 예측하는 모델을 구축하기 위해 2023년 5월, 2023년 4월, 2023년 3월 등 2023년 6월 이전 12개월 동안의 에너지 사용량을 측정하는 12개의 예측 변수 열을 생성할 수 있습니다. 13번째 열은 예측 대상(target) 또는 종속 변수가 되며, 2023년 6월의 실제 에너지 사용량을 기록합니다. 이 데이터셋으로 학습된 모델은 2022년 6월부터 2023년 5월까지의 데이터를 기반으로 2023년 6월의 에너지 사용량을 예측하는 방법을 학습하게 되지만, 예측 대상과 예측 변수들이 특정 월(month)과 연결되어 있기 때문에 미래의 다른 월은 예측할 수 없게 된다는 점에 유의하십시오.

그 대신, 대상 월(target month)을 기준으로 계산되는 **지연 변수(lagged variables)**를 구성하는 것이 더 나은 접근 방식입니다. 지연 변수는 기본적으로 데이터셋 내의 더 최근의 나중 행으로 이월되기 위해 시간에 따라 지연된 척도입니다. 지연 변수를 사용하는 모델은 시간이 지남에 따라 추가적인 데이터 월(months)이 가용해짐에 따라 반복적인 월별(rolling, monthly basis)로 재학습될 수 있습니다. `energy_june2023` 및 `energy_may2023`과 같은 열 이름 대신 생성되는 데이터셋은 측정의 상대적인 성격을 나타내는 이름들, 예를 들어 이번 달, 지난 달, 두 달 전의 에너지 사용량을 나타내는 `energy_lag0`, `energy_lag1`, `energy_lag2`와 같은 열 이름을 가지게 됩니다. 이 모델은 항상 가장 최근 데이터에 적용되어 다가오는 기간을 예측할 것입니다.

*그림 12.9*는 이 접근 방식을 시각화한 것입니다. 매달 모델은 지난 13개월간의 데이터를 바탕으로 학습됩니다. 가장 최근 월은 예측 대상 또는 종속 변수(DV로 표시)로 사용되는 반면 이전 12개월은 지연 예측 변수(lagged predictors)로 사용됩니다. 그런 다음 모델을 사용하여 아직 관찰되지 않은 미래의 월을 예측할 수 있습니다. 첫 번째 이후 이어지는 각 달은 롤링 윈도우(rolling window)를 한 달 앞으로 이동시켜, 13개월보다 오래된 데이터는 모델에서 사용되지 않게 됩니다. 이런 식으로 구성된 데이터를 사용해 학습된 모델은 지연되지 않은(non-lagged) 변수의 경우처럼 특정 역년월(calendar months) 사이의 관계를 학습하는 것이 아닙니다; 오히려 달력상의 월과 관계없이 과거의 행동이 미래의 행동과 어떻게 관련되는지를 학습합니다.

그림 12.9: 지연 예측 변수 구성은 시계열 데이터를 모델링하는 한 방법입니다.

하지만 이 접근 방식의 한 가지 문제점은 역년(calendar time) 시간을 무시했다는 것입니다. 특정 역년월은 대상 변수에 중요한 영향을 미칠 수 있습니다. 예를 들어, 에너지 사용량은 봄과 가을보다는 겨울과 여름에 더 높을 수 있습니다. 따라서 모델이 과거와 미래의 행동 사이의 관계뿐만 아니라 계절적 효과, 즉 분석 단위와 관련된 행(rows) 내에서 국지적 패턴보다 더 광범위한 패턴에 대한 감각을 얻는 것이 모델에게 유익할 것입니다.

예측할 대상의 값은 3가지 변동(variation) 소스로 구성되어 있으며 모델을 위한 피처로 이들을 분해(decompose)하고자 한다고 생각해 볼 수 있습니다.

1.  분석 단위 고유의 속성에 기초한 국지적(local) 또는 내부적 변동이 있습니다. 에너지 수요 예측의 예에서 국지적 변동은 가구의 규모와 건축물, 거주자의 에너지 필요량, 주택 위치 등과 관련될 수 있습니다.
2.  대부분 가구의 에너지 사용량에 영향을 미치는 연료 가격이나 날씨 패턴과 같은 더 광범위한 전역적(global) 추세가 있을 수 있습니다.
3.  대상의 변화를 설명하는, 국지적 및 전역적 효과와 독립적인 계절적(seasonal) 효과가 있을 수 있습니다. 이는 앞서 언급한 연간 기상 패턴에 국한되지 않으며 주기적이거나 예측 가능한 어떠한 패턴도 계절적 효과로 간주될 수 있습니다.

에너지 예측 프로젝트와 관련된 구체적인 예는 다음 날들에 수요가 더 높거나 낮아지는 것을 포함할 수 있습니다.

- 다른 요일들, 특히 평일과 주말
- 종교적 또는 정부 공휴일
- 전통적인 학교 또는 기업 휴가 기간
- 스포츠 행사, 콘서트, 선거와 같은 대규모 군중 모임

국지적, 전역적, 그리고 계절적 특징들을 훈련 데이터셋의 예측 변수로 통합할 수 있다면, 모델은 이들이 결과에 미치는 영향을 학습할 수 있습니다. 그 이후의 과제는 두 가지입니다. 하나는 중요한 계절적 요인을 식별하기 위해 해당 분야 지식이나 데이터 탐색이 필요하다는 점이고, 다른 하나는 포함된 각 계절마다 대상을 관찰할 수 있도록 풍부한 훈련 데이터가 있어야 한다는 점입니다. 후자는 훈련 데이터가 단일 달의 시간 단면(cross-section of time) 이상으로 구성되어야 함을 의미합니다; 그렇지 않으면 학습 알고리즘이 계절과 대상(target) 사이의 관계를 당연히 찾아낼 수 없게 됩니다!

다시 원래의 긴 형식 데이터로 돌아가야 하는 것처럼 보일 수 있지만, 사실은 그렇지 않습니다. 실제로는 매달 생성된 지연 변수가 포함된 넓은 데이터를 분석 단위당 여러 개의 행을 갖는 단일 통합 데이터셋으로 쌓아 올릴(stacked) 수 있습니다. 각 행은 특정 시점의 한 개인을 나타내며, 해당 시점의 결과를 측정하는 대상 변수와, 대상 시점 이전 기간의 지연 변수로 구성된 넓은 열 세트를 갖습니다. 또한 행렬을 더 넓히고 계절, 요일, 휴일에 대한 표시기(indicators)와 같은 다양한 시간 변동 성분을 분해하기 위해 추가적인 열을 더할 수도 있습니다; 이 열들은 주어진 행이 이런 관심 기간에 속하는지 여부를 나타냅니다.

다음 그림은 이 방식을 사용한 가상의 데이터셋을 나타냅니다. 각 가구(`household_id` 열로 표시)는 예측 대상(`energy_use`)과 예측 변수(`season`, `holiday_month`, `energy_lag1` 등)의 다른 값들과 함께 반복적으로 나타날 수 있습니다. 주의할 점은 데이터셋의 처음 몇 행에 대해서는 지연 변수가 비어 있으며(`NA` 값으로 표시됨), 이는 이 행들을 학습이나 예측에 사용할 수 없음을 뜻한다는 점입니다. 하지만 나머지 행들은 숫자 예측을 수행할 수 있는 어떠한 머신 러닝 기법으로든 사용할 수 있으며, 훈련된 모델은 주어진 현재 달력월에 대한 데이터 행을 받아들여 그 다음 달의 에너지 사용량을 쉽게 예측해낼 수 있습니다.

시계열 데이터의 모델링에 서둘러 뛰어들기 전에, 여기서 설명한 데이터 준비 방법에 대한 중요한 주의사항을 이해하는 것이 필수적입니다. 동일한 분석 단위에서 반복 측정된 행들은 서로 관련되어 있기 때문에, 이들을 훈련 데이터에 포함시키는 것은 회귀분석과 같은 기법의 '독립적 관찰' 가정을 위반하게 됩니다. 이러한 데이터를 바탕으로 구축된 모델이 여전히 유용할 수는 있지만, 공식적인 시계열 모델링을 위한 다른 기법이 더 적절할 수도 있습니다. 그러므로 여기서 설명한 방법들을 앞서 다루었던 머신 러닝 방법들로 예측(forecasting)을 수행하기 위한 우회적 수단(workaround)으로 간주하는 것이 최선입니다. 선형 혼합 모델(Linear mixed models)과 순환 신경망(recurrent neural networks)은 이러한 유형의 데이터를 자체적으로 처리할 수 있는 잠재적인 두 가지 접근법이지만, 이 두 가지 방법 모두 본 서의 범위를 벗어납니다.

R에서 혼합 모델을 구축할 때는 `lme4` 패키지가 사용되지만, 이러한 유형의 모델이 지니는 통계적 기반을 이해하지 않고 무작정 시도하는 것은 현명하지 않습니다; 이들은 전통적인 회귀 모델링보다 복잡성이 한 단계 훨씬 더 높습니다. 책 _Linear Mixed-Effects Models Using R_(Gałecki & Burzykowski, 2013)은 이 같은 유형의 모델을 구축하는 데 필요한 이론적 배경을 제공합니다. 순환 신경망을 구축하는 경우에는 이를 위해 존재하는 특화된 도구들이 있으므로 R이 적합한 도구가 아닐 수 있습니다. 그러나 `rnn` 패키지는 시계열 예측을 위한 단순한 RNN 모델을 구축할 수 있습니다.

## 힌트 7: 외부 데이터 덧붙이기 (Hint 7: Append external data)

이 책의 교육용 예시들과 달리, 현실 세계에서 머신 러닝 프로젝트가 시작될 때, 미리 구축된 피처들과 관심 주제를 설명하는 예시들이 있는 데이터셋을 인터넷에서 단순히 다운로드할 수는 없습니다. 이 단순한 이유 때문에 얼마나 많은 대단히 흥미로운 프로젝트들이 시작되기도 전에 죽고 마는지 모릅니다. 고객의 이탈을 예측하려는 기업은 모델을 구축할 역사적 데이터가 전혀 없다는 사실을 깨닫고, 빈곤 지역에서 식량 분배를 최적화하려는 학생들은 이 지역에서 나오는 희소한 양의 데이터 때문에 한계에 부딪히며, 수익을 늘리거나 세상을 더 나은 곳으로 바꿀 수 있는 수많은 프로젝트가 시작되기도 전에 멈춰버립니다. 머신 러닝 프로젝트 주변에 형성된 열의는 결국 데이터 부족으로 인해 흐지부지 되고 맙니다.

낙담으로 끝내기보다는 이런 에너지를 무에서 필요한 데이터를 생성하려는 노력으로 전환하는 것이 더 낫습니다. 이는 관련 데이터의 조각이 포함된 데이터베이스에 대한 접근 권한을 줄 수 있는 사람과 연결하기 위해 동료에게 전화를 걸거나 일련의 이메일 메시지를 발송하는 것을 의미할 수 있습니다. 또한 소매를 걷어붙이고 직접 손을 더럽히는 일이 필요할 수도 있습니다. 어쨌든 우리는 데이터가 풍부할 뿐만 아니라 전자 센서 및 자동화된 데이터 입력 도구의 도움으로 쉽게 기록되는 이른바 빅데이터 시대에 살고 있습니다.

기존 데이터셋을 더욱 풍부하게 만들기 위해 종종 외부 출처의 추가 피처를 덧붙일 기회가 있습니다. 특히 관심 있는 메인 데이터셋에 우편 번호와 같은 지리적 식별자가 포함되어 있을 때 그러한데, 대중에게 공개된 여러 데이터베이스가 이런 지역의 속성을 측정하고 있기 때문입니다. 물론, 우편 번호 수준의 데이터셋이 특정 개인의 정확한 특성을 밝히지는 않겠지만, 해당 지역의 평균적인 사람이 더 부유한지, 더 건강한지, 더 젊은지, 자녀를 가질 가능성이 더 높은지 등 예측 모델의 질을 향상하는 데 도움을 줄 수 있는 수많은 요인들에 대한 통찰력을 제공할 수는 있습니다. 이러한 유형의 데이터는 많은 정부 기관 웹사이트에서 쉽게 찾아 무료로 다운로드할 수 있으며, 단순히 이 데이터를 메인 데이터셋에 병합하는 것만으로 추가적인 잠재적 예측 변수를 얻을 수 있습니다.

마지막으로 Facebook, Zillow, LinkedIn과 같은 많은 소셜 미디어 기업 및 데이터 집계(aggregator) 서비스는 데이터의 제한적인 부분에 대해 무료 접근을 제공합니다. 예를 들어 Zillow는 우편번호 지역 단위로 주택 가치 평가액을 제공합니다. 어떤 경우에는 이런 회사들이나 다른 판매자들이 해당 데이터셋에 대한 접근 권한을 판매하기도 하며, 이는 예측 모델을 증강시키는 강력한 수단이 될 수 있습니다. 이러한 데이터를 얻을 때 수반되는 재정적 비용 외에도, 공통의 고유 식별자가 없는 데이터셋 간에 엔티티들을 일치시키는 것과 관련된 **레코드 연결(record linkage)**의 측면에서 종종 중요한 도전을 제기합니다. 이 문제를 해결하려면 한 출처의 각 행을 다른 출처의 해당 행에 매핑하는 **크로스워크(crosswalk)** 테이블을 작성해야 합니다. 예를 들어, 크로스워크는 주(main) 데이터셋의 고객 식별 번호로 식별된 사람을 외부 소셜 미디어 데이터셋의 고유한 웹사이트 URL에 연결할 수 있습니다. `RecordLinkage`와 같이 소스 전반에 걸친 매칭 수행을 돕는 R 패키지들이 있긴 하지만, 이들은 발견적 방법론(heuristics)에 의존하기 때문에 인간의 지능만큼 성능이 좋지 않을 수 있으며, 특히 대규모 데이터베이스의 경우 막대한 계산 비용이 필요합니다. 전반적으로 레코드 연결은 인적 자원 및 계산 비용의 관점에서 흔히 비용이 많이 든다고 가정하는 것이 안전합니다.

외부 데이터의 획득을 고려할 때는 출처의 이용 약관뿐만 아니라 해당 외부 출처의 사용과 관련된 해당 지역의 법률 및 조직 규칙을 반드시 조사해야 합니다. 관할권(jurisdiction)에 따라 다른 곳보다 규칙이 더 엄격하기도 하고, 시간이 지남에 따라 많은 규칙이 더 엄격해지고 있으므로 외부 데이터 사용에 따른 합법성과 법적 책임(liability)에 대해 항상 최신 상태를 유지하는 것이 중요합니다.

고급 데이터 준비에 수반되는 작업들을 고려해, R 자체도 새로운 요구에 부응하도록 발전해 왔습니다. 역사적으로 R은 매우 크고 복잡한 데이터셋을 다루는 데 어려움을 겪는 것으로 악명이 높았으나, 시간이 지나면서 이러한 단점을 해결하고 지금까지 이 장에서 설명한 작업 유형들을 수행하기 더 쉽게 만들어주는 새로운 패키지들이 개발되었습니다. 본 장의 나머지 부분에서는 실제 세계의 데이터 문제에 부합하도록 R 문법을 현대화한 이 패키지들에 대해 배울 것입니다.

# R의 tidyverse 탐색하기 (Exploring R’s tidyverse)

R에서 데이터를 작업하는 지배적인 패러다임으로 새로운 접근 방식이 빠르게 자리를 잡았습니다. R이 초기에 인기를 끄는 데 기여한 패키지들의 배후에 있는 인물, 해들리 위컴(Hadley Wickham)이 주도한 이 새로운 물결은 현재 Posit(구 RStudio)의 훨씬 더 거대한 팀에 의해 지원을 받고 있습니다. 이 회사의 사용자 친화적인 RStudio 데스크톱 애플리케이션은 깔끔한 데이터(tidy data)에 전념하는 패키지의 우주를 제공하기 때문에 **tidyverse**로 알려진 이 새로운 생태계와 훌륭하게 통합됩니다. 전체 tidyverse 패키지 세트는 `install.packages("tidyverse")` 명령을 통해 설치할 수 있습니다.

홈페이지 <https://www.tidyverse.org>를 시작으로, tidyverse에 대해 배울 수 있는 점점 더 많은 자원(resources)이 온라인에 제공되고 있습니다. 이곳에서 본 장에 묘사된 몇 가지 패키지들을 비롯해 세트에 포함된 다양한 패키지들에 대해 알아볼 수 있습니다. 또한 Hadley Wickham과 Garrett Grolemund가 저술한 책 *R for Data Science*가 <https://r4ds.hadley.nz>에서 무료로 온라인으로 제공되며, 자신들을 "의견이 강한(opinionated)" 접근법이라고 자칭하는 tidyverse의 접근법이 데이터 과학 프로젝트를 어떻게 간소화시키는지 보여줍니다.

저는 데이터 과학과 기계 학습을 위한 R과 Python의 비교에 대한 질문을 자주 받습니다. RStudio와 tidyverse는 아마도 R의 가장 큰 자산이자 차별점일 것입니다. 데이터 과학의 여정을 시작하는 데 이보다 더 쉬운 방법은 단언컨대 없을 것입니다. 일단 데이터 분석을 수행하는 "깔끔한(tidy)" 방법을 배우고 나면, 당신은 모든 곳에 tidyverse 기능이 존재했으면 하고 바라게 될 것입니다!

## tibble로 깔끔한 테이블 구조 만들기 (Making tidy table structures with tibbles)

기본(base) R 우주의 중심이 데이터 프레임인 반면, tidyverse의 중심에 있는 데이터 구조는 `tibble` 패키지(<https://tibble.tidyverse.org>)에 있습니다. 이 이름은 "테이블(table)"이라는 단어의 언어유희이자 *스타트렉(Star Trek)*의 전승(lore) 속 악명 높은 "트리블(tribble)"을 나타냅니다. **티블(tibble)**은 데이터 프레임과 거의 똑같이 동작하지만, 편의와 단순성을 위한 현대적인 기능이 추가되었습니다. 티블은 데이터 프레임을 사용할 수 있는 거의 모든 곳에서 사용 가능합니다. R에서 `vignette("tibble")` 명령을 입력하면 티블에 대한 자세한 정보를 찾을 수 있습니다.

티블은 대부분의 R 패키지에서 데이터 프레임으로 통할 수 있기 때문에, 보통 티블을 사용하는 것은 아주 자연스럽고 매끄럽습니다. 하지만 드물게 티블을 데이터 프레임으로 변환해야 할 때는 `as.data.frame()` 함수를 사용하십시오. 반대 방향으로 가서 데이터 프레임을 티블로 변환하려면 `as_tibble()` 함수를 사용합니다. 여기에서는 이전 장에서 처음 소개되었던 Titanic 데이터셋으로부터 티블을 만들어 보겠습니다.

```R
> library(tibble) # tidyverse가 이미 로드되어 있다면 필요하지 않습니다
> titanic_csv <- read.csv("titanic_train.csv")
> titanic_tbl <- as_tibble(titanic_csv)
```

이 객체의 이름을 타이핑해 보면 표준 데이터 프레임보다 더 깔끔하고 유익한 정보가 출력되는 티블을 확인할 수 있습니다.

tidyverse는 많은 연산에서 자동으로 tibble 객체를 생성하기 때문에 tibble과 데이터 프레임 간의 구분을 이해하는 것이 중요합니다. 전반적으로 tibble이 데이터 프레임보다 속도가 빠르고 작업하기 수월하다는 것을 알게 될 것입니다. 일반적으로 tibble은 데이터에 대해 더 영리한 가정을 내리기 때문에, 문자열 열을 요인(factor)으로 변환하거나 반대로 되돌리는 것과 같은 R의 작업을 재작업하는 데 들이는 시간을 줄일 수 있습니다.

실제로 티블과 데이터 프레임의 한 가지 간단한 차이점은 티블은 상대적으로 최근에 R 버전 4.0이 출시될 때까지 기본 R의 기본 동작이었던 `stringsAsFactors = TRUE`를 절대 가정하지 않는다는 것입니다. 이전 장들에서 설명했듯이 문자열 열이 기본적으로 요인으로 자동 변환되는 R의 `stringsAsFactors` 설정은 종종 코딩 시 혼란을 주거나 버그를 초래했습니다. 티블과 데이터 프레임 간의 또 다른 차이점은, 이름을 백틱(`` ` ``) 문자로 둘러싸는 한, 기본 R의 객체 작명 규칙을 위반하는 `` `my var` `` 같은 비표준 열 이름을 사용할 수 있다는 점입니다. 티블의 또 다른 이점들은 다음 섹션들에서 설명할 상호 보완적인 tidyverse 패키지들을 통해 얻을 수 있습니다.

## readr과 readxl로 직사각형(rectangular) 파일을 더 빠르게 읽기 (Reading rectangular files faster with readr and readxl)

지금까지 거의 모든 장에서 R 데이터 프레임에 데이터를 로드할 때 `read.csv()` 함수를 사용했습니다. 이 데이터 프레임들을 티블로 변환할 수도 있지만, 티블 형식으로 데이터를 가져오는 더 빠르고 직접적인 방법이 있습니다. tidyverse는 표 형식 데이터를 불러오기 위해 `readr` 패키지(<https://readr.tidyverse.org>)를 포함합니다. 이에 관해서는 *R for Data Science*의 데이터 가져오기(data import) 챕터(<https://r4ds.hadley.nz/data-import.html>)에서 설명하고 있지만 기본 기능은 단순합니다.

`readr` 패키지는 기본 R의 `read.csv()` 함수와 매우 비슷하게 CSV 파일에서 데이터를 로드하는 `read_csv()` 함수를 제공합니다. 함수 이름에서 나타나는 미묘한 차이를 제쳐둔다면, 두 방법의 주요 차이점은 데이터를 자동으로 티블로 변환해서만이 아니라 tidyverse의 버전이 훨씬 더 빠르다는 점입니다. 패키지 저자들에 따르면 데이터를 읽는 속도가 약 10배 더 빠르다고 합니다. 로드할 열의 형식을 처리하는 데 있어서도 더 똑똑합니다. 예를 들어, 이 함수는 화폐 기호가 있는 숫자를 처리하고, 날짜 열을 파싱(parsing)하는 기능을 가지고 있으며 다국어 데이터를 더 잘 다룹니다.

CSV 파일에서 티블을 생성하려면 다음과 같이 `read_csv()` 함수를 사용하기만 하면 됩니다.

```R
> library(readr) # tidyverse가 이미 로드되어 있다면 필요하지 않습니다
> titanic_train <- read_csv("titanic_train.csv")
```

이것은 각 열의 올바른 데이터 유형(즉, 문자 또는 수치)을 유추하려고 시도하는 기본 파싱 설정을 사용합니다. 열 명세(column specification)는 파일 읽기가 완료되는 시점에 R 출력으로 표시됩니다. 유추된 데이터 유형은 `read_csv()` 함수에 전달되는 `col()` 함수 호출을 통해 알맞은 열 명세(specification)를 제공함으로써 재정의(override)할 수 있습니다. 구문에 대한 더 자세한 정보는 `vignette("readr")` 명령어를 통해 문서를 참조하십시오.

`readxl` 패키지(<https://readxl.tidyverse.org>)는 마이크로소프트 엑셀(Microsoft Excel) 스프레드시트 형식에서 데이터를 직접 읽어 들이는 방법을 제공합니다. XLSX 파일에서 티블을 생성하려면 다음과 같이 `read_excel()` 함수를 사용하기만 하면 됩니다.

```R
> library(readxl)
> titanic_train <- read_excel("titanic_train.xlsx")
```

대안으로, *제2장, 데이터 관리와 이해(Managing and Understanding Data)*에서 처음 소개되었듯이 RStudio 데스크톱 애플리케이션이 여러분을 위해 데이터 가져오기 코드를 작성하도록 할 수 있습니다. 인터페이스 오른쪽 상단의 **Environment(환경)** 탭 아래에 **Import Dataset(데이터셋 가져오기)** 버튼이 있습니다. 이 메뉴는 기본 R 또는 `readr` 패키지를 이용하는 CSV 파일 같은 일반 텍스트 형식과 더불어 엑셀(Excel) 그리고 기타 통계 컴퓨팅 소프트웨어 도구에서 생성된 SPSS, SAS 및 Stata 형식을 포함한 데이터 가져오기 옵션 목록을 보여줍니다. **From Text (readr)** 옵션을 선택하면 다음과 같은 그래픽 인터페이스가 열리며 가져오기 과정을 쉽게 사용자 지정(customize)할 수 있습니다.

## dplyr을 사용하여 데이터 준비하고 전달하기(piping) (Preparing and piping data with dplyr)

`dplyr` 패키지(<https://dplyr.tidyverse.org>)는 데이터 변형 및 조작이 가능한 기본 기능을 포함하므로 tidyverse를 위한 인프라를 제공합니다. 또한 R에서 더 큰 데이터셋으로 작업을 시작하기 위한 간단한 방법을 제공합니다. 빠른 속도(raw speed)를 갖추고 있거나 훨씬 더 방대한 데이터셋을 다루기에 더 적합한 다른 패키지도 있지만, dplyr은 여전히 강력한 역량을 자랑하며 기본 R의 속도나 메모리 한계에 부딪혔을 때 내디딜 수 있는 좋은 첫걸음입니다.

tibble 객체와 함께 사용할 때 dplyr은 인상적인 기능을 발휘합니다.

- dplyr은 벡터 대신 데이터 프레임에 중점을 두기 때문에 새로운 연산자가 도입되었으며 이로 인해 매우 높은 가독성을 유지하면서 더 적은 코드로 공통적인 데이터 변환이 가능합니다.
- 이 패키지는 데이터 프레임에 대해 합리적인 가정을 하여 귀하의 노력뿐만 아니라 메모리 사용을 최적화합니다. 가능하면 원본 값을 가리키는 방식으로 복사본 생성을 피합니다.
- 패키지 작성자들에 따르면, 코드의 핵심 부분이 C++로 작성되었기 때문에 많은 연산에서 기본 R에 비해 20배에서 1,000배가량의 성능 향상을 가져옵니다.
- R 데이터 프레임은 사용 가능한 메모리에 의해 제한됩니다. dplyr을 사용하면 메모리에 저장할 수 있는 한계를 넘는 디스크 기반 데이터베이스에 티블을 투명하게 연결할 수 있습니다.

데이터를 다루는 dplyr 문법(grammar)은 초기의 학습 곡선을 넘어선 후엔 자연스러워집니다(second nature). 문법에는 다섯 가지 핵심 동사(verbs)가 있으며, 데이터 테이블에 가장 일반적인 많은 변환을 수행합니다. 티블에서 시작하여 다음과 같은 동사들을 선택할 수 있습니다.

- 열의 값으로 데이터 행을 `filter()` (필터링)
- 이름으로 데이터 열을 `select()` (선택)
- 값을 정렬하여 데이터 행을 `arrange()` (정렬)
- 값을 변환하여 새로운 열로 `mutate()` (생성 및 변이)
- 요약본에 값을 집계하여 데이터 행을 `summarize()` (요약)

이 다섯 가지 dplyr 동사는 **파이프 연산자(pipe operator)**를 사용하여 순차적으로 묶이게 되며, 파이프 연산자는 R 4.1 버전 이상에서 기본 지원됩니다. 우측을 향하는 화살표 모양과 비슷한 `|>` 기호로 나타내는 이 파이프 연산자는 데이터를 함수에서 다른 함수로 이동시켜 데이터를 "전달(pipes)"합니다. 파이프를 사용하면 강력한 함수 사슬(chains)을 생성하여 데이터셋을 순차적으로 처리할 수 있습니다.

R 4.1.0 업데이트 이전 버전에서 파이프 연산자는 `%>%` 문자열로 표시되었으며 `magrittr` 패키지가 필요했습니다. 기존 파이프 기능과 새 파이프 기능 간의 차이는 비교적 사소하지만, 새 파이프는 기본(native) 연산자로서 미세한 속도 이점을 가질 수 있습니다. RStudio 데스크톱 IDE에서는 단축키인 _ctrl_ + _shift_ + _m_ 키 조합을 사용하여 파이프 연산자 문자열을 빠르게 삽입할 수 있습니다. 참고로, 이 단축키가 최신 파이프를 생성하게 하려면 RStudio "Global Options" 메뉴의 "Code" 제목 아래 "Use the native pipe operator, |>" 설정으로 변경해야 할 수 있습니다.

`library(dplyr)` 명령으로 패키지를 로드한 후 티블이 이 패키지의 동사 중 하나로 파이프 연결됨으로써 데이터 변환이 시작됩니다. 예를 들어 Titanic 데이터셋의 행을 여성 승객들로 제한하려면 `filter()`를 사용할 수 있습니다.

```R
> titanic_train |> filter(Sex == "female")
```

마찬가지로 이름, 성별, 나이 열만 `select()`할 수 있습니다.

```R
> titanic_train |> select(Name, Sex, Age)
```

dplyr이 진가를 발휘하기 시작하는 곳은 파이프를 이용해 동사들을 순서대로 사슬처럼 연결할 수 있는 능력입니다. 예를 들어, 다음과 같이 이전의 두 동사를 결합하고 동사 `arrange()`를 사용하여 알파벳순으로 정렬한 뒤 그 결과를 티블로 저장할 수 있습니다.

```R
> titanic_women <- titanic_train |>
    filter(Sex == "female") |>
    select(Name, Sex, Age) |>
    arrange(Name)
```

아직 놀랄 만한 발견처럼 보이지 않을 수도 있겠지만, 이것이 `mutate()` 동사와 결합되면 기본 R 언어보다 단순하고 읽기 쉬운 코드로 복잡한 데이터 변환을 수행할 수 있습니다. 나중에 `mutate()`의 몇 가지 예시를 살펴보겠지만, 지금 기억해야 할 중요한 점은 이 동사가 티블에 새로운 열을 생성하는 데 쓰인다는 것입니다. 예를 들어, 우리는 승객이 65세 이상인지 여부를 나타내는 이진 특성 `elderly`를 생성할 수 있습니다.

이것은 dplyr 패키지의 `if_else()` 함수를 사용하여 승객이 고령자인 경우 `1`의 값을 할당하고, 그렇지 않은 경우 `0`을 할당합니다.

```R
> titanic_train |>
    mutate(elderly = if_else(Age >= 65, 1, 0))
```

쉼표로 문장들을 분리하면 단일 `mutate()` 문 안에서 여러 개의 열을 생성할 수 있습니다. 다음은 승객이 18세 미만인지 여부를 나타내는 추가적인 `child` 피처를 생성하는 것을 보여줍니다.

```R
> titanic_train |>
    mutate(
      elderly = if_else(Age >= 65, 1, 0),
      child = if_else(Age < 18, 1, 0)
    )
```

나머지 `dplyr` 동사인 `summarize()`는 티블 내의 행들을 그룹화함으로써 집계되거나 요약된 측정 항목(metrics)을 생성할 수 있게 해 줍니다. 예를 들어 연령 또는 성별에 따른 생존율을 계산하고 싶다고 가정해 봅시다. 두 경우 중 더 쉬운 성별부터 시작하겠습니다. 단순히 데이터를 `group_by(Sex)` 함수로 파이프(pipe)하여 남성과 여성 그룹을 생성한 다음, 이를 `summarize()` 문으로 이어받아 그룹별 평균 생존율을 계산하는 `survival_rate` 피처를 생성합니다.

```R
> titanic_train |>
    group_by(Sex) |>
    summarize(survival_rate = mean(Survived))
```

```R
# A tibble: 2 x 2
  Sex    survival_rate
  <chr>          <dbl>
1 female         0.742
2 male           0.189
```

출력 결과에서 볼 수 있듯, 여성의 생존 가능성은 남성보다 실질적으로 더 높았습니다.

연령에 따른 생존을 계산하는 것은 나이 값이 결측(missing)된 경우 때문에 상황이 약간 더 복잡합니다. 이 행들을 걸러낸 다음 `group_by()` 함수를 사용하여 다음과 같이 아이(18세 미만)와 성인을 비교해야 합니다.

```R
> titanic_train |>
    filter(!is.na(Age)) |>
    mutate(child = if_else(Age < 18, 1, 0)) |>
    group_by(child) |>
    summarize(survival_rate = mean(Survived))
```

```R
# A tibble: 2 x 2
  child survival_rate
  <dbl>         <dbl>
1     0         0.381
2     1         0.540
```

결과는 아이가 성인보다 생존할 가능성이 약 40% 더 높았음을 시사합니다. 이것이 남성과 여성의 비교와 결합되면 침몰하는 배의 대피에 대해 "여성과 아이들 먼저(women and children first)"라는 가설적 정책이 존재했음에 대한 강력한 증거를 제공합니다.

기본 R의 다른 방법(이전 장에서 설명한 `ave()` 및 `aggregate()` 함수 포함)을 사용하여 그룹별 요약 통계를 계산할 수 있기 때문에, `summarize()` 명령이 이것보다 훨씬 많은 작업들을 수행할 수 있다는 점에 주목하는 것이 중요합니다. 특히, 이 장의 앞부분에서 설명한 피처 엔지니어링 힌트인 '이웃의 행동 관찰하기', '관련된 행 활용하기', '시계열 분해하기' 등에 이 명령을 사용할 수 있습니다. 이 세 가지 경우 모두 가구, 우편 번호, 시간 단위와 같은 `group_by()` 옵션을 포함합니다. 이러한 데이터 준비 작업을 위해 집계를 수행할 때 `dplyr`을 사용하는 것이 기본 R에서 수행하려고 시도하는 것보다 훨씬 더 쉽습니다.

지금까지 배운 내용을 하나로 모으고 파이프를 사용하는 예제를 하나 더 제공하기 위해 Titanic 데이터셋의 의사 결정 트리 모델을 만들어 보겠습니다. 우리는 결측된 나이 값들을 `filter()`하고, 새로운 `AgeGroup` 피처를 생성하기 위해 `mutate()`를 사용하며, 의사 결정 트리 모델을 위해 관심 있는 열들만 `select()` 할 것입니다. 그 결과로 나온 데이터셋은 `rpart()` 의사 결정 트리 알고리즘으로 파이프(piped)되며, 이는 tidyverse 외부의 함수로 데이터를 파이프할 수 있는 능력을 보여줍니다.

```R
> library(rpart)
> m_titanic <- titanic_train |>
    filter(!is.na(Age)) |>
    mutate(AgeGroup = if_else(Age < 18, "Child", "Adult")) |>
    select(Survived, Pclass, Sex, AgeGroup) |>
    rpart(formula = Survived ~ ., data = _)
```

일련의 단계들이 거의 평문(plain-language) 의사코드(pseudocode)처럼 읽힌다는 점에 주목하십시오. `rpart()` 함수 호출 내의 인수들도 주목할 가치가 있습니다. `formula = Survived ~ .` 인수는 모든 예측 변수의 함수로써 생존을 모델링하기 위해 R의 공식(formula) 인터페이스를 사용합니다; 여기서 마침표(dot)는 명시적으로 나열되지 않은 데이터셋의 다른 피처들을 나타냅니다. `data = _` 인수는 파이프에 의해 `rpart()`에 공급되는 데이터를 나타내기 위해 자리 표시자(placeholder)로서 밑줄(\_)을 사용합니다. 밑줄은 이런 식으로 데이터가 어떤 함수 매개변수로 파이프(piped)되어야 하는지 나타내는 데 사용될 수 있습니다.

이것은 일반적으로 dplyr의 내장 함수에는 불필요한데 이 함수들은 기본적으로 첫 번째 매개변수로 파이프 된 데이터를 찾기 때문입니다. 하지만 tidyverse 외부의 함수들은 이처럼 파이프가 특정 함수 매개변수를 타깃으로 하도록 요구할 수도 있습니다.

밑줄 자리 표시자 문자는 R 버전 4.2부터 새로 도입되었으며 이전 버전에서는 작동하지 않는다는 점에 유의하는 것이 중요합니다! `magrittr` 패키지를 사용하는 오래된 코드에서는 점(.) 문자가 자리 표시자로 사용되었습니다.

재미 삼아 그 결과로 나온 의사 결정 트리를 시각화할 수 있는데, 이는 성인, 남성, 그리고 3등석 승객보다 여성과 아이들의 생존 가능성이 더 높음을 보여줍니다.

```R
> library(rpart.plot)
> rpart.plot(m_titanic)
```

## stringr로 텍스트 변환하기 (Transforming text with stringr)

`stringr` 패키지(<https://stringr.tidyverse.org>)는 문자열을 분석하고 변환하는 함수들을 추가합니다. 물론 기본 R에서도 이것이 가능하지만, 기본 함수들은 벡터에서 작동하는 방식이 일관되지 않고 비교적 느립니다; `stringr`은 tidyverse 워크플로에 더 적합한 형태로 이러한 함수들을 구현합니다. 무료 리소스인 *R for Data Science*는 <https://r4ds.hadley.nz/strings.html>에 패키지의 전체 기능 세트를 소개하는 튜토리얼을 제공하지만, 여기서는 피처 엔지니어링과 가장 관련이 있는 몇 가지 측면을 살펴보겠습니다. 직접 따라 해보고 싶다면, 계속하기 전에 Titanic 데이터셋을 로드하고 `stringr` 패키지를 설치 및 로드하십시오.

이 장의 앞부분에서 피처 엔지니어링을 위한 두 번째 조언은 "텍스트에 숨겨진 통찰력 찾기"였습니다. `stringr` 패키지는 문자열을 자르고(slice) 텍스트 내의 패턴을 감지하는(detect) 함수를 제공하여 이러한 노력을 도울 수 있습니다. 모든 `stringr` 함수는 `str_` 접두사로 시작하며, 관련성 있는 몇 가지 예시는 다음과 같습니다.

- `str_detect()`는 문자열에서 검색어(search term)가 발견되는지 여부를 결정합니다.
- `str_sub()`는 위치를 기준으로 문자열을 자르고 하위 문자열(substring)을 반환합니다.
- `str_extract()`는 문자열을 검색하고 일치하는 패턴을 반환합니다.
- `str_replace()`는 문자열의 문자를 다른 것으로 대체합니다.

이 함수들은 꽤 비슷해 보이지만 꽤 다른 용도로 사용됩니다. 이러한 용도를 시연하기 위해 `Cabin` 피처를 검사하여 타이타닉호의 특정 객실들이 더 높은 생존과 연관되어 있는지 확인하는 것으로 시작해 보겠습니다. 각 객실 코드가 고유하기 때문에 이 피처를 그대로 사용할 수는 없습니다.

그러나 코드가 `A10`, `B101` 또는 `E67`과 같은 형태이므로, 알파벳 접두사가 선박 내 위치를 나타낼 수 있으며, 아마도 이러한 위치 중 일부에 있던 승객들이 재난을 피하는 데 더 수월했을 수 있습니다. 우리는 위치 1에서 시작하고 끝나는 단일 문자(1-character) 하위 문자열을 취하기 위해 `str_sub()` 함수를 사용할 것이고 이를 다음과 같이 `CabinCode` 피처에 저장할 것입니다.

```R
> titanic_train <- titanic_train |>
    mutate(CabinCode = str_sub(Cabin, start = 1, end = 1))
```

우선 경칭(Mr., Mrs., 그리고 Miss.)은 예측에 도움이 될 수 있습니다. 문제는 이러한 타이틀들이 이름 문자열 내에서 각각 다른 위치에 있다는 점이며, 따라서 단순히 이들을 추출하기 위해 `str_sub()` 함수를 사용할 수는 없습니다. 이 작업을 위한 적절한 도구는 `str_extract()`이며, 긴 문자열에서 더 짧은 패턴을 일치시키고 추출하는 데 사용됩니다. 이 함수를 다루는 요령은 잠재적인 경칭을 각각 개별적으로 타이핑하는 대신 텍스트 패턴을 표현하는 방법을 아는 데 있습니다.

텍스트 검색 패턴을 표현하는 데 사용되는 속기(shorthand)를 **정규 표현식(regular expression)** 또는 줄여서 **regex**라고 합니다. 정규 표현식을 만드는 방법을 아는 것은 대단히 유용한 기술인데, 많은 텍스트 편집기의 고급 찾기-바꾸기 기능에 사용될 뿐만 아니라 R에서 피처 엔지니어링을 할 때도 유용하기 때문입니다. 우리는 이름 문자열에서 경칭을 추출하는 간단한 정규 표현식을 생성할 것입니다.

정규 표현식을 사용하는 첫 번째 단계는 원하는 대상 문자열 전체의 공통 요소를 식별하는 것입니다. 타이타닉 이름의 경우, 각 경칭 앞에 쉼표(comma)가 오고 그 뒤에 빈 공백(blank space)이 온 다음 일련의 글자들이 있고 마지막에 마침표(period)로 끝나는 것으로 보입니다. 이는 다음과 같은 정규식 문자열로 코딩될 수 있습니다.

```R
", [A-z]+\."
```

이것은 언뜻 보기에 말도 안 되는 소리 같지만, 한 글자씩 패턴 일치를 시도하는 시퀀스로 이해할 수 있습니다. 일치 프로세스는 예상대로 쉼표와 빈 공백으로 시작됩니다. 그다음 대괄호(square brackets)는 대괄호 안의 문자 중 하나를 찾도록 검색 함수에 지시합니다. 예를 들어 `[AB]`는 `A`나 `B`를 검색하고 `[ABC]`는 `A`, `B` 또는 `C`를 검색합니다. 여기서 대시는 `A`에서 `z` 사이의 범위에 있는 문자를 검색하는 데 사용됩니다. `[A-Z]`가 `[A-z]`와는 다르다는 점에서 대문자 사용이 중요하다는 것에 유의하십시오. 전자는 알파벳 대문자로 구성된 26개의 문자를 검색하는 반면 후자는 대문자와 소문자를 포함해 52개의 문자를 검색합니다. `[A-z]`는 단일 문자에만 일치한다는 점을 명심하십시오.

표현식이 더 많은 문자와 일치하게 하려면, 대괄호 뒤에 `+` 기호를 붙여 알고리즘이 대괄호 안에 없는 무언가에 도달할 때까지 문자를 계속 일치시키도록 지시합니다. 그런 다음 정규 표현식의 남은 부분이 일치하는지 확인합니다.

남은 부분은 `\.` 시퀀스이며, 이는 검색 패턴 끝에 있는 단일 마침표 문자를 나타내는 세 개의 문자입니다. 마침표는 임의의 문자를 나타내는 특별한 항(special term)이기 때문에, 앞에 슬래시를 붙여 마침표를 이스케이프(escape)해야 합니다. 불행히도 R에서 슬래시 역시 특별한 문자이므로 그 앞에 또 다른 슬래시를 붙여 동일하게 이스케이프 처리해야 합니다.

정규 표현식은 배우기 까다로울 수 있지만 그만한 노력을 들일 가치가 충분합니다. 이 기능이 어떻게 동작하는지 깊이 있게 이해하고 싶다면 <https://www.regular-expressions.info>를 방문하십시오. 대안으로, 실시간으로 패턴 일치를 보여주는 수많은 텍스트 편집기와 웹 애플리케이션들이 존재합니다. 이것들은 regex 검색 패턴을 어떻게 개발하고 오류를 진단할 수 있는지 이해하는 데 대단히 유용할 수 있습니다. 이러한 도구 중 최고의 도구 하나를 <https://regexr.com>에서 찾아볼 수 있습니다.

`str_extract()`를 함께 사용한 `mutate()` 함수에 다음과 같이 결합하여 타이타닉 이름 데이터에 이 표현식을 적용할 수 있습니다.

```R
> titanic_train <- titanic_train |>
    mutate(Title = str_extract(Name, ", [A-z]+\."))
```

처음 몇 개의 예시를 살펴보면, 조금 정리할 필요가 있어 보입니다.

이들 경칭에서 구두점과 빈칸을 없애기 위해 `str_replace()` 함수를 사용해 보겠습니다. 구두점과 빈 공백에 일치하는 정규 표현식을 만드는 것으로 시작하겠습니다. 그렇게 하는 한 가지 방법은 `"[, \.]"` 검색 문자열을 사용하여 쉼표, 공백, 그리고 마침표를 일치시키는 것입니다. 여기에 보이는 바와 같이 `str_replace()`와 함께 사용하면, `Title`의 모든 쉼표, 공백 및 마침표 문자가 빈(null) 문자열로 대체됩니다.

## lubridate를 사용해 날짜 정리하기 (Cleaning dates with lubridate)

`lubridate` 패키지(<https://lubridate.tidyverse.org>)는 날짜와 시간 데이터를 다루기 위한 중요한 도구입니다. 모든 분석에 꼭 필요한 것은 아닐 수 있지만, 필요한 경우 많은 고충을 덜어줄 수 있습니다. 날짜 및 시간과 관련된 겉보기에 간단한 작업들도 윤년과 시간대와 같은 예상치 못한 미묘한 차이로 인해 금세 험난한 모험으로 바뀔 수 있습니다. 생일 계산이나 청구 주기, 또는 이와 유사한 날짜에 민감한 태스크를 작업해 본 사람이라면 누구든 물어보십시오.

다른 tidyverse 패키지들과 마찬가지로 _R for Data Science_ 리소스는 <https://r4ds.hadley.nz/datetimes.html>에서 심도 있는 lubridate 튜토리얼을 다루고 있지만, 여기서는 세 가지 가장 중요한 피처 엔지니어링 강점을 간략하게 다룰 것입니다.

- 날짜와 시간이 표현되는 방식에 대한 지역적 차이를 고려하면서 날짜와 시간 데이터가 R에 올바르게 로드되도록 보장합니다.
- 시간대와 윤년을 설명하면서 날짜와 시간 간의 차이를 정확하게 계산합니다.
- 사람들이 생일에 "한 살 더 먹는다"는 사실과 같이, 현실 세계에서 시간의 증분을 이해하는 방식의 차이를 설명합니다.

R로 날짜를 읽어 들이는 것은 가장 어려운 첫 번째 관문인데 그 이유는 날짜가 다양한 형식으로 제공되기 때문입니다. 예를 들어, _기계 학습과 R(Machine Learning with R)_ 초판의 출간일은 다음과 같이 표현될 수 있습니다.

- October 25, 2013 (미국의 일반적인 긴 형식(longhand format))
- 10/25/13 (미국의 일반적인 짧은 형식(shorthand format))
- 25 October 2013 (유럽의 일반적인 긴 형식)
- 25.10.13 (유럽의 일반적인 짧은 형식)
- 2013-10-25 (국제 표준)

이렇게 다양한 형식이 주어질 경우, 윤달(월), 일(일), 연(연)은 모두 1에서 12 사이의 값이 될 수 있기 때문에 lubridate는 도움 없이 올바른 형식을 결정할 수 없습니다. 대신, 우리는 입력 데이터의 월(`m`), 일(`d`), 연(`y`) 구성요소의 순서에 따라 `mdy()`, `dmy()` 또는 `ymd()` 등 올바른 날짜 생성자(date constructor)를 제공해야 합니다. 날짜 구성요소의 순서가 주어지면 함수는 자동으로 길고 짧은 변형 형식을 구문 분석하고 선행하는 0(leading zeros) 및 2자리 또는 4자리 연도를 처리합니다. 이를 보여주기 위해 앞에서 표현한 날짜들은 다음과 같이 적절한 lubridate 함수로 처리할 수 있습니다.

```R
> mdy(c("October 25, 2013", "10/25/2013"))
```

```R
[1] "2013-10-25" "2013-10-25"
```

```R
> dmy(c("25 October 2013", "25.10.13"))
```

```R
[1] "2013-10-25" "2013-10-25"
```

```R
> ymd("2013-10-25")
```

```R
[1] "2013-10-25"
```

각 경우에 생성된 `Date` 객체는 정확히 똑같다는 것을 확인하십시오. 이 책의 이전 세 판(editions) 각각에 대해 이와 유사한 객체를 만들어 봅시다.

```R
> MLwR_1stEd <- mdy("October 25, 2013")
> MLwR_2ndEd <- mdy("July 31, 2015")
> MLwR_3rdEd <- mdy("April 15, 2019")
```

간단한 수학 연산을 통해 두 날짜 사이의 차이를 계산할 수 있습니다.

```R
> MLwR_2ndEd - MLwR_1stEd
```

```R
Time difference of 644 days
```

```R
> MLwR_3rdEd - MLwR_2ndEd
```

```R
Time difference of 1354 days
```

기본적으로 두 날짜의 차이는 일(days) 단위로 반환됩니다. 연(years) 단위로 답을 구하고 싶다면 어떻게 해야 할까요? 불행히도 이러한 차이는 특수한 lubridate의 `difftime` 객체이므로 직관적으로 이 숫자들을 단순히 365일로 나누어 계산할 수는 없습니다. 한 가지 선택지는 이들을 **지속 시간(duration)**으로 변환하는 것입니다. 이는 lubridate가 날짜 차이를 계산하는 방법 중 하나이며, 특히 스톱워치처럼 물리적 시간의 흐름을 추적합니다. `as.duration()` 함수가 이 필요한 변환을 수행합니다.

```R
 > as.duration(MLwR_2ndEd - MLwR_1stEd)
```

```R
[1] "55641600s (~1.76 years)"
```

```R
> as.duration(MLwR_3rdEd - MLwR_2ndEd)
```

```R
[1] "116985600s (~3.71 years)"
```

여기서 _Machine Learning with R_ 2판과 3판 사이의 간격이 1판과 2판 사이의 차이보다 거의 두 배나 길었음을 확인할 수 있습니다. 지속 시간은 기본적으로 초 단위로 표시되며 덧붙여 대략적인 연수를 제공한다는 사실도 볼 수 있습니다. 연 단위만 구하려면 지속 시간을 1년의 지속 시간으로 나누면 되는데, lubridate는 이를 `dyears()` 함수로 제공합니다.

```R
> dyears()
```

```R
[1] "31557600s (~1 years)"
```

```R
> as.duration(MLwR_2ndEd - MLwR_1stEd) / dyears()
```

```R
[1] 1.763176
```

```R
> as.duration(MLwR_3rdEd - MLwR_2ndEd) / dyears()
```

```R
[1] 3.70705
```

동일한 계산을 수행할 수 있는 `time_length()` 함수를 기억하는 것이 더 편리하거나 쉬울 수 있습니다.

```R
> time_length(MLwR_2ndEd - MLwR_1stEd, unit = "years")
```

```R
[1] 1.763176
```

```R
> time_length(MLwR_3rdEd - MLwR_2ndEd, unit = "years")
```

```R
[1] 3.70705
```

원하는 결과에 따라 `unit` 인수를 일(days), 월(months), 연(years)과 같은 단위로 설정할 수 있습니다. 하지만 이 지속 시간들은 마치 스톱워치처럼 초 단위까지 정확하다는 점을 유의하십시오. 사람들은 날짜를 이런 식으로 생각하지 않는 경우가 많습니다.

특히 생일이나 기념일의 경우, 사람들은 달력상 시간(calendar time)—즉 달력이 특정한 이정표(milestone)에 도달한 횟수로 생각하는 경향이 있습니다. lubridate에서 이 접근법은 **구간(interval)**이라고 불리며, 이는 앞서 논의한 지속 시간 방법의 스톱워치 기반 접근 방식과 달리 시계열(timeline) 또는 달력 기반의 날짜 차이 관점을 시사합니다.

말하자면 1776년 7월 4일에 태어난 미국의 나이를 계산하고 싶다고 상상해 봅시다. 이는 2023년 7월 3일이 되면 그 나라는 246번째 생일을 맞이하고, 2023년 7월 5일에는 247살이 된다는 것을 뜻합니다. 지속 시간을 이용할 경우 그다지 올바른 답을 얻지 못합니다.

```R
> USA_DOB <- mdy("July 4, 1776") # 미국의 생년월일
> time_length(mdy("July 3 2023") - USA_DOB, unit = "years")
```

```R
[1] 246.9897
```

```R
> time_length(mdy("July 5 2023") - USA_DOB, unit = "years")
```

```R
[1] 246.9952
```

이 문제는 윤년과 시간 변경과 같은 달력의 불규칙성 때문에 지속 시간이 달력상의 시간과 벗어난다는 사실과 관련이 있습니다. `interval()` 함수를 이용해 날짜 차이를 명시적으로 구간(interval)으로 변환한 다음 `years()` 함수로 나누면 정답에 더 가까워집니다.

```R
> interval(USA_DOB, mdy("July 3 2023")) / years()
```

```R
[1] 246.9973
```

```R
> interval(USA_DOB, mdy("July 5 2023")) / years()
```

```R
[1] 247
```

더 나아가기 전에 `end - start`를 사용했던 날짜 차이와 대조적으로 `interval()`이 `start, end` 구문을 사용한다는 사실에 주목하십시오. 또한 `years()` 함수는 lubridate **기간(period)**을 반환하며 이는 날짜와 시간의 차이를 이해하는 또 다른 방법입니다. 기간은 항상 달력에서의 그 위치에 비례합니다. 즉, 1시간 기간은 시간 변경 중에는 2시간의 지속 시간이 될 수 있고 1년 기간은 달력상의 연도에 따라 365일 또는 366일 기간을 포함할 수 있습니다. 이것들이 바로 이 섹션의 여는 단락에서 언급했던 날짜를 다룰 때의 어려운 미묘함의 유형들입니다!

우리의 최종 나이 계산을 생성하기 위해 단축어로 구간(interval) 생성 연산자인 `%--%`를 사용하고, 나이의 정수 부분만 반환하기 위해 정수 나눗셈 연산자인 `%/%`를 사용하겠습니다. 이들은 예상된 나이 값을 반환합니다.

```R
> USA_DOB %--% mdy("July 3 2023") %/% years()
```

```R
[1] 246
```

```R
> USA_DOB %--% mdy("July 5 2023") %/% years()
```

```R
[1] 247
```

이 작업을 일반화하여 주어진 생년월일에 대한 오늘 기준 달력 기반의 나이를 계산하는 함수를 만들 수 있습니다.

```R
> age <- function(birthdate) {
    birthdate %--% today() %/% years()
  }
```

이것이 제대로 작동하는지 증명하기 위해 유명한 기술 분야 억만장자(tech billionaires) 몇 명의 나이를 확인해 보겠습니다.

```R
> age(mdy("February 24, 1955")) # 제프 베이조스(Jeff Bezos)
```

```R
[1] 59
```

```R
> age(mdy("June 28, 1971")) # 일론 머스크(Elon Musk)
```

```R
[1] 51
```

```R
> age(mdy("Oct 28, 1955")) # 빌 게이츠(Bill Gates)
```

```R
[1] 67
```

# 요약 (Summary)

이 장에서는 데이터 준비의 중요성을 시연했습니다. 기계 학습 모델을 구축하는 데 사용되는 도구와 알고리즘은 여러 프로젝트에 걸쳐 동일하기 때문에 데이터 준비야말로 모델의 최고 수준 성능을 열어주는 열쇠입니다. 이것은 컴퓨터가 지칠 줄 모르고 데이터 내에서 유용한 통찰을 찾는 능력을 활용하는 자동화된 데이터 엔지니어링 파이프라인(pipelines)을 개발함으로써 영리한 실무자들이 그들의 강점과 기계의 강점을 조화롭게 이용하긴 하지만, 어쨌든 인간의 지능과 창의성의 일부 측면이 기계의 학습 프로세스에 큰 영향을 미치게 해줍니다. 이러한 파이프라인들은 특히 소위 말하는 '빅데이터 체제(big data regime)'에서 중요합니다. 이곳에서는 딥 러닝(deep learning)과 같이 데이터에 굶주린 접근법이 과적합(overfitting)을 방지하기 위해 많은 양의 데이터를 공급받아야 합니다.

전통적인 중소 규모의 데이터 체제에서는 수작업에 의한 피처 엔지니어링이 여전히 최고입니다. 직관과 주제 전문 지식을 활용하여 훈련 데이터셋 내 가장 유용한 신호(signal)로 모델을 유도할 수 있습니다. 이것은 과학이라기보다 예술에 가깝기 때문에 요령과 팁들은 업무를 하며 익히거나 한 데이터 과학자로부터 다른 이에게 간접적으로 전수됩니다. 이 장에서는 여정을 안내하는 데 도움이 되는 7가지 힌트를 제공했지만 피처 엔지니어링에 진정으로 능숙해지는 유일한 방법은 연습을 통한 것뿐입니다.

`tidyverse` R 패키지 세트와 같은 도구는 피처 엔지니어링 태스크를 수행하는 데 필요한 경험을 얻는 것을 과거 몇 년에 비해 덜 수고스럽게 만듭니다. 이 장은 tidyverse 패키지가 어떻게 데이터를 보다 유용한 예측 변수로 바꾸는 데 쓰일 수 있는지, 그리고 언뜻 쓸모없어 보이는 피처들을 어떻게 중요한 예측 변수로 바꿀 수 있는지 텍스트 데이터에 숨겨진 정보를 어떻게 추출할 수 있는지를 시연했습니다. tidyverse 패키지들은 기본(base) R 함수들보다 방대하고 끝없이 성장하는 데이터셋을 훨씬 더 잘 처리할 수 있으며, 데이터셋의 규모와 복잡성이 늘어나도 R을 즐겁게 사용할 수 있도록 해 줍니다.

이 장에서 개발한 기술들은 앞으로 다가올 작업의 기반을 제공할 것입니다. 다음 장에서는 여러분의 툴킷(toolkit)에 새로운 tidyverse 패키지를 추가하고 이것이 기계 학습 워크플로우에 어떻게 통합되는지에 대한 더 많은 예시들을 확인하게 될 것입니다. 상대적으로 경미한 어려움으로 시작하지만 극한으로 치달을 경우 대규모의 문제로 급성장하는 데이터 문제들을 탐색하면서, 여러분은 데이터 준비 기술의 중요성을 계속해서 목격할 것입니다.
