#  3.1 General structure of input/output functions 

In R, many functions related to I/O are intuitively named. They often start with ` `` read `` ` for loading into R and ` `` write `` ` for saving from R. There are a variety of functions, and all of them include one of the following keywords,

- ` `` read `` ` or ` `` load `` ` , which specifies that these functions import objects into R
- ` `` write `` ` or ` `` save `` ` , which indicates that these functions export objects from R.

They include a mandatory ` `` file `` ` or ` `` path `` ` argument to specify the input or output location, which can often accept a file path string or a connection object. These functions provide flexibility via various optional arguments, such as ` `` col_names `` ` or ` `` compression `` ` .

The ` `` path `` ` or ` `` file `` ` argument usually assumes the project folder as the root directory. You can check your root directory by ` `` getwd() `` ` function. Before that, check what objects are available in your R global environment by typing ` `` ls() `` ` in the console and clear the session using ` `` rm(list=ls()) `` ` .

```
# lists of objects in global environment
ls()

# clear R workspace
rm(list = ls())

# prints root directory
getwd()
```

Let’s create a folder named data inside your project folder if it does not exist already.

```
# check existence of data folder
dir.exists("data")
dir.create("data")
```

The ` `` dir.exists() `` ` function checks for the existence of the data folder, and the ` `` dir.create() `` ` function creates a folder. For this chapter, we will use a folder called ` `` data_chap3 `` ` that resides inside the data folder. The following code checks for the existence of the folder. If it is available, it sets the full path as ` `` data_path `` ` ; if it is not available, it creates the folder and then saves it to ` `` data_path `` ` :

```
# Check if the folder exists and create if it doesn't

if (dir.exists(file.path(getwd(), "data", "data_chap3"))){
  data_path <- file.path(getwd(), "data", "data_chap3")
} else {
  dir.create(
    file.path(getwd(), "data", "data_chap3"),
    recursive = TRUE
  )
  data_path <- file.path(getwd(), "data", "data_chap3")
}
```

When creating folders after checking for their existence, wrapping the actions within an if-else block reduces the chance of accidentally deleting or overwriting folders. You can run this code block multiple times while keeping the existing folder and its component intact.

During the remainder of this chapter, we will use ` `` data_path `` ` as the location for write and read files. Saving the location in an object will save significant typing time in the following examples. You can use any other location of your choice by changing the path or file arguments inside a function.

Now you can programmatically check the existence of a folder and create one if needed. Next, you will see how to save and load R data files into an R workspace.

#  3.2 Saving and loading files generated by R 

The ` `` saveRDS() `` ` and ` `` readRDS() `` ` functions save and load any R objects with extension ` `` .rds `` ` or ` `` .RDS `` ` . These functions are commonly used to save model objects and then load them later for further analysis. Windows and macOS use a case-insensitive file system, which means both the file extensions are treated equally. However, Linux/Unix file systems use a case-sensitive file system which treats ` `` .RDS `` ` differently than ` `` .rds `` ` .

The ` `` saveRDS() `` ` function predominantly saves a single object. Let’s save the ` `` mtcars `` ` data locally using the following code:

```
saveRDS(mtcars,
        file = file.path(data_path,"mtcars.rds"))
```

You can save multiple objects by organizing them in a list as shown in the following code output:

```
saveRDS(list(mtcars, austres),
        file = file.path(data_path, "mtcars_austres.rds"))
```

It is always better to assign a name to a loaded object unless you just want to print it and do nothing afterwards:

```
singl_obj <- readRDS(file.path(data_path, "mtcars.rds"))
singl_obj
```

When multiple objects are loaded from the same RDS file, access them in the standard way that you extract elements from a list:

```
mult_obj <- readRDS(file.path(data_path,"/mtcars_austres.rds"))
df1 <- mult_obj[[1]]
df2 <- mult_obj[[2]]
```

In this section, you have learned how to read and write R data files. You have also learned how to load multiple RDS files with a single command.

##  3.4.1 The readr package 

The ` `` readr `` ` package from tidyverse provides convenient functions to load and parse different types of rectangular data in fast and flexible ways. Parsing involves taking flat files of any format and outputting them as a tibble object while ensuring each column has the correct type.

The set of functions are ` `` read_*() `` ` and ` `` write_*() `` ` where the second part after the underscore indicates which file formats the functions can be applied to, such as comma-separated values (csv), tab-separated value (tsv), fixed-width text file (fwf). The ` `` readr `` ` versions of the base ` `` saveRDS() `` ` and ` `` readRDS() `` ` functions are ` `` write_rds() `` ` and ` `` read_rds() `` ` , respectively.

Let’s add a character column to the ` `` mtcars `` ` data by taking the row names and save it as ` `` mtcars2 `` ` . Use the ` `` write_csv() `` ` function to save the ` `` mtcars2 `` ` object externally as a csv. Remove ` `` mtcars2 `` ` from global environment. The following code block is showing you the operations:

```
mtcars2 <-
  rownames_to_column(mtcars, "make") |>
  as_tibble()

write_csv(
  mtcars2,
  file = file.path(data_path,"mtcars2.csv"))

rm("mtcars2")
```

Now, load the ` `` mtcars2 `` ` object into the workspace. You will see the ` `` read_csv() `` ` function has parsed 1 character and 11 numeric columns accurately:

```
mtcars2 <- read_csv(
  file.path(data_path,"mtcars2.csv"))
```

You can check the column types of a data file before loading it into workspace applying ` `` spec_csv() `` ` function as shown in the following output:

```
> spec_csv(file.path(data_path,"mtcars2.csv"))

  make = col_character(),

```

The ` `` spec_*() `` ` function checks the first 1,000 rows to guess the column specification.

` `` readr `` ` provides convenient functions for parsing one column type to another. It is a common issue for external files to have date/time formats different from what R expects. The package provides three functions to parsing a date/times vector:

- ` `` parse_date() `` ` : Uses 1970-01-01 as the epoch and the format specified by ` `` locale() `` ` . The default uses an automatic date parser and provides output in the format of ` `` Y-m-d `` ` or ` `` Y/m/d `` ` , where ` `` Y `` ` is a four-digit year, ` `` m `` ` is a two digit month, and ` `` d `` ` is a two digit day. You need to provide the format of the input date(s) in the format argument inside the function, not the output date format. Some examples are presented in the following code snippets.

  The input date is in month/day/year format. The format argument should reflect that. The ` `` %Y `` ` format the year in a four-characters form:

  ```
  parse_date("10/05/2023", format="%m/%d/%Y")
  # [1] "2023-10-05"
  ```

  Here, the input date is in day/month/year format and the corresponding ` `` %d/%m/%Y `` ` format is used:

  ```
  parse_date("20/05/2023", format="%d/%m/%Y")
  # [1] "2023-05-20"
  ```

  The following format could not parse the input date due to the mismatch between the input date format and the requested parsing format:

  ```
  parse_date("10/05/2023", format="%Y-%m-%d")
  # [1] NA
  ```

  The delimiter, hyphen ( ` `` - `` ` ) or a front slash ( ` `` / `` ` ) plays no part in accurate date parsing as long as the requested format matches with the input date as shown below:

  ```
  parse_date("2023-05-10", format = "%Y-%m-%d")
  # [1] "2023-05-10"
  ```

- ` `` parse_datetime() `` ` : This function uses the number of seconds since midnight 1970-01-01 as the epoch.

  An example of parsing a date-time input without the format argument:

  ```
  parse_datetime("2023-05-14 16:42")
  # [1] "2023-05-14 16:42:00 UTC"
  ```

  You can pass any custom date-time input and corresponding matching format to parse properly as shown in the following code:

  ```
  parse_datetime("14 May, 2023", "%d %B, %Y")
  # [1] "2023-05-14 UTC"
  ```

- ` `` parse_time() `` ` : Uses the number of seconds since midnight as epoch. By default, the automatic time parser recognizes times of the form H:M. Let’s see an example of the ` `` parse_time() `` ` function:

  ```
  parse_time("4:42pm")
  # 16:42:00
  ```

##  3.4.2 The readxl package 

The ` `` readxl `` ` package is designed to import Excel files in R. You can use the extension specific ` `` read_xls() `` ` and ` `` read_xlsx() `` ` functions, or the generic ` `` read_excel() `` ` . The last one identifies the proper extension from the file itself. In these functions, you can specify the sheet argument to direct which sheets to read from. The cell ranges to read can be provided in multiple ways via the range argument:

- ` `` read_excel("test.xlsx", range = "A1:D10") `` ` reads all cells in the range A1 to D10, regardless of whether they are empty
- ` `` read_excel("test.xlsx", range = cell_rows(1:10)) `` ` reads all non-empty rows from rows 1 to 10, across all columns
- ` `` read_excel("test.xlsx", range = cell_cols("A:D")) `` ` reads all non-empty rows from columns A to D
- ` `` read_excel("test.xlsx", range = anchored("B4", c(3, 4))) `` ` , starting from the cell B4, it reads 3 rows below and 4 columns in the right.

Like the ` `` readr `` ` package, ` `` readxl `` ` provides helper functions for column type guessing. Parsing the date column properly is important as a numeric cell is interpreted as the serial number of days from the epoch of Excel’s two different date systems, 1900 or 1904. For illustration, we will use the ` `` type-me.xlsx `` ` data from the ` `` readxl `` ` package. First, load the data as shown in the following code:

```
typeme <- readxl_example("type-me.xlsx")

##  3.4.3 The fst package 

If you work with large files (100MB) and save intermediate data regularly during an analysis, then the ` `` fst `` ` package becomes helpful. Converting large data files into ` `` fst `` ` format allows random access to stored data. That means a subset of the complete table can be loaded from an fst file depending on the range of rows and by column name. The multithreaded serialization performs lightning-fast compression and decompression while writing on disk or importing in R using ` `` write_fst() `` ` or ` `` read_fst() `` ` function, respectively. By default, ` `` read_fst() `` ` outputs a data frame, which can be transformed into another data object (e.g., ` `` tibble `` ` ).

For illustration, let’s use the ` `` write_fst() `` ` function to compress the ` `` mtcars `` ` data in a ` `` .fst `` ` format. We first convert the row names in a column before saving it as an ` `` mtcars3.fst `` ` file format as shown in the following code:

```
write_fst(
  as_tibble(mtcars, rownames= "make"),
  path = file.path(data_path, "mtcars3.fst"),
  compress = 100)
```

Now, load a subset of the ` `` mtcars3.fst `` ` file by selecting specific columns and rows. The following code will show you how to perform the operations:

```
read_fst(
  path = file.path(data_path,"mtcars3.fst"),
  columns = c("make", "mpg", "cyl"),
  from = 5,
  to = 10) |>
  as_tibble()
```

This returns the following output:

```

  <chr>             <dbl> <dbl>

2 Valiant            18.1     6

4 Merc 240D          24.4     4
5 Merc 230           22.8     4

```

##  3.5.1 Connecting to databases 

Using the DBI package as a core communicator, R offers direct connection to several open source databases via respective packages, for example, the ` `` RMySQL `` ` package for MYSQL database, and bigrquery for Google’s BigQuery database etc. The commercial databases, such as **Snowflake** and **Oracle** , come with their own **ODBC** ( **Open Database Connectivity** ) drivers that are required to setup a connection along with R’s ` `` DBI `` ` and ` `` odbc `` ` packages.

After installing the respective ODBC driver for a database, you can set up a connection from R using the following parameters. A **Database Administrator** ( **DBA** ) in your organization should have this information in case you don’t know:

- ` `` drv `` ` : An object that facilitates connection to a database. For example, ` `` drv=RSQLite::SQLite() `` ` indicates to use the ` `` SQLite() `` ` connector object that comes with the ` `` RSQLite `` ` package. Similarly, in ` `` drv=odbc::odbc() `` ` , ` `` odbc() `` ` is the database connection object included in the package of the same name.
- ` `` dsn `` ` : DSN stands for Data Source Name. A user can set a custom name while installing an ODBC driver on a single machine. In the example ‘‘Snowflake’’ is set as the DSN during ODBC installation. There are file DSNs and system DSNs, which are applicable when multiple users share a single file for driver configuration or by all users under a single system.
- ` `` uid `` ` : The user identifier.
- ` `` pwd `` ` : Password to use. Do not under any circumstances include your password in R script. See *Section 3.5.2* for a brief discussion on how to use credentials securely.
- ` `` authenticator `` ` : Some sort of authentication method to establish the connection. Two common methods are using an external browser or **Single Sign On** ( **SSO** ). It depends on the organization’s set up and you need to comply with that.

Not all databases need every parameter. On the other hand, some databases provide extra parameters to control hierarchies, such as a **warehouse** , **database** , and **schema** in the connection setting.

It is common to have many schemas within a warehouse/database combination. If you need to import data from multiple schemas that reside within a warehouse simultaneously, you need to set up multiple connections, one for each schema, by changing schema names, with the remaining parameters staying the same.

Let’s create an in-memory ` `` SQLite `` ` database connection using the ` `` RSQLite `` ` package:

```
sqlite_con <- DBI::dbConnect(RSQLite::SQLite(), ":memory:")
```

Write the weather data frame from the ` `` nycflights13 `` ` package into it, and use ` `` “ `` ` ` `` WEATHER `` ` ` `` ” `` ` as a database table name. The ` `` dplyr::copy_to() `` ` function copies a local data frame to a remote data source:

```
copy_to(sqlite_con,weather,"WEATHER")
```

The commercial databases require some form of authentication to connect. Usually, it is the user ID and password, or SSO method. You need to follow the organization’s guidelines when connecting to databases. An example of an external browser authentication method using user ID and password to connect Snowflake database is shown next. It is worth noting that the Snowflake connection examples are intended to illustrate best practices. They require a properly configured Snowflake environment, DSN, and authentication method to work. You might not be able to execute this code unless you have access to a Snowflake account and ODBC setup:

```
# Connecting to Snowflake
snowflake_conn <- DBI::dbConnect(
  drv = odbc::odbc(),
  dsn = "Snowflake" ,
  warehouse = "<warehouse name>",
  database = "<database name>",
  schema = "<schemaname>",
  uid = "<user id>",
  pwd  = "<securely_retrieve_password_here>",
  authenticator="externalbrowser"
)
```

The ` `` ROracle `` ` package connects to Oracle by passing the database information as a string:

```
# Loading library prior to setup avoids unexpected errors
library(ROracle)

protocol <- "protocol"
host <- "<host of the database>"
port <- "<port of the database>"
sid <- "<database name>"

connect.string <- paste(
   "(DESCRIPTION=",
  "(ADDRESS=(PROTOCOL=" , protocol,
  ")(HOST=", host,
  ")(PORT=", port, "))",
   "(CONNECT_DATA=(SID=", sid, ")))",
  sep = ""
)

oracle_con <- DBI::dbConnect(
  dbDriver("oracle"),
  dbname = connect.string,
  uid,
  pwd
)
```

There is no message that appears in the R console when a connection is established successfully. Some error messages appear if there are issues, such as the username and password not being correct, or the connection parameters not being properly set. There could be many reasons for a database connection failing. However, broader discussion on them is out of the scope of the book.

It is vitally important to secure credentials when connecting to a database from R. There are multiple options available to the users of R when it comes to securing credentials in code, which you will learn about next.

##  3.5.2 Credential security 

You need to use some form of authentication along with the username and password to connect with a database. However, it is extremely crucial to secure credentials and avoid every possibility of exposing them. A common mistake is to save the username and password in a script and accidentally store that in a version control system (e.g., Git). In the following sections, you will learn four different ways to secure your credentials. So, there is no excuse for exposing them even accidentally.

###  3.5.2.1 Pre-configuring credentials during ODBC set-up 

The username and password can be added when ODBC is configured in your computer system. In such a case, you do not need to supply the ` `` ‘‘ `` ` ` `` uid `` ` ` `` ’’ `` ` and ` `` ‘‘ `` ` ` `` pwd `` ` ` `` ’’ `` ` explicitly while connecting to a database. Your R script is free from any sensitive information. This is the best way to secure credentials.

###  3.5.2.2 The keyring package 

The keyring package encrypts the username/password combination for each service using the operating system’s credential storage. Consider it as one key in a single keyring that opens a unique lock (service). A service-username-password combination is set by the ` `` key_set() `` ` function. The username and password are retrieved using the ` `` key_list() `` ` and ` `` key_get() `` ` functions, respectively:

```
key_set(service = "<database service name>",
        username = "<user id>")

# Retrieved credentials are used in the connection directly
snowflake_conn <- DBI::dbConnect(
  drv = odbc::odbc(),
  dsn = "<database service name>",
  warehouse = "<warehouse name>",
  database = "<database name>",
  schema = "<schema name>",
  uid = keyring::key_list("<database service name>")[1,2],
  pwd = keyring::key_get("<database service name>","<user id>"))
```

Using this method, you can safely secure your credentials for multiple database connectivity and use them simultaneously to extract data for your analysis.

###  3.5.2.3 The config package 

You can make a ` `` config.yml `` ` file to store credentials along with all connection arguments and place them in the root directory of your R project. Required information for the arguments is retrieved via the ` `` config::get() `` ` function to pass in the database connection function.

###  3.5.2.4 The RStudio API 

The RStudio API provides a prompt to supply credentials interactively. You can input both the username and the password by using the ` `` askForPassword() `` ` function twice.

#  3.6 Using SQL from R 

There are multiple ways to use SQL from R, and each of them has advantages and disadvantages. The choice of methods is also dictated by a database’s expectation of SQL queries. As an example, parameterized queries on date/time columns behave differently in Oracle than it does in Snowflake. After a successful connection is set to a database, the connection name is used along with a query to extract data from a relational database table.

The packages that are usually used in SQL query executions are the following:

```

       ,"dplyr"

##  3.6.4 Parameterized query using glue_sql() 

Often, a query needs to be parameterized based on user input. The ` `` dbGetQuery() `` ` function does not work with a parameterized query. Instead, a combination of ` `` glue_sql() - `` ` ` `` > `` ` ` `` dbSendQuery() - `` ` ` `` > `` ` ` `` dbBind() - `` ` ` `` > `` ` ` `` dbFetch() `` ` is used to apply different parameter values at every iteration. The following code is showing an example of parameterized ` `` sql `` ` while extracting weather information for three airports:

```
origin_par <- c("EWR", "JFK" ,"LGA")
origin_sql <- glue_sql(
  "select
    origin,
    year,
    temp
  from weather
  where origin = ?"
)

origin_data <- list()
for(i in seq_along(origin_par)){
  origin_query <- dbSendQuery(sqlite_con, origin_sql)
  dbBind(origin_query, list(origin_par[i]))
  origin_data[[i]] <- dbFetch(origin_query) |>
    as_tibble()
  dbClearResult(origin_query)
}
```

Not all database drivers process the parameterized SQL query through ` `` dbBind() `` ` . A common issue occurs when date/time columns are parameterized since most databases have a unique way of storing date-time data. In such a scenario, you need to use the ` `` sqlInterpolate() `` ` function. Supply the parameters twice, once inside the query and again inside the ` `` sqlInterpolate() `` ` function.

SQLite does not have a specific type to store date-time. In the following example, below, ` `` time_hour `` ` field is formatted to a character before applying filtering based on the user’s input. After loading data to R, the date should be formatted as a date type. It should be noted that ` `` sqlite_con `` ` is used twice, first in the ` `` sqlInterpolate() `` ` function and second in the ` `` dbGetQuery() `` ` function. For example, the following sql query first formats ` `` time_hour `` ` column and then uses ` `` start_date `` ` and ` `` end_date `` ` to extract data:

```
start_date <- "2013-01-01"
end_date <- "2013-05-31"

query <- "
  select *
  from(
    select
      origin,
      strftime(
        '%Y-%m-%d',
        datetime(time_hour,'unixepoch', 'localtime')
      ) as date,
      temp
    from weather
  )
  where date >= ?start_ts
    and date <= ?end_ts
"
query_interpolate <- sqlInterpolate(
  sqlite_con,
  query,
  start_ts = start_date,
  end_ts = start_date )

query_extract <- dbGetQuery(
  sqlite_con, query_interpolate) |>
  as_tibble()
```

#  3.7 Data governance 

When you use R for analysis, it is essential to incorporate key principles of data governance to ensure the integrity, transparency, and accountability of the analytical process. You should consider at least three important aspects: data quality, data privacy and security, and documentation and metadata management. To support these practices, the R ecosystem offers a variety of packages. We will briefly introduce core concepts and highlight selected packages that can assist you in implementing sound data governance strategies within your workflows:

-  **Data quality assurance** : Ensuring data quality is crucial for accurate and reliable analysis. It involves verifying the accuracy, consistency, completeness, and validity of the data being used. It includes data profiling, data cleaning, and data transformation. With the help of various R packages and functions, you can assess data quality, identify missing values, and use standardized data formats. Before performing any analysis, you should check the data quality so that the results obtained are actionable and reliable. The following set of packages might prove useful based on your data analytics needs:
  - ` `` dataMaid `` ` : Automates data quality checks by generating reports that identify missing values, outliers, and potential issues in variable types and distributions.
  - ` `` janitor `` ` : Provides simple functions for cleaning data, including removing empty rows/columns, cleaning column names, and identifying duplicate entries.
  - ` `` validate `` ` : Allows you to define and check data validation rules (e.g., ranges, formats, and logical conditions) to ensure data integrity.
  - ` `` skimr `` ` : Offers a compact summary of datasets, including missing values, data types, and basic statistics, which is great for quick data profiling.
  - ` `` naniar `` ` : Specializes in handling and visualizing missing data, making it easier to understand patterns of NA values and impute them if needed.
  - ` `` Hmisc `` ` : Includes tools for data analysis and cleaning, such as imputation, labeling, and descriptive statistics.
  - ` `` summarytools `` ` : Provides detailed summaries of datasets, including frequency tables, descriptive stats, and missing value counts.

-  **Data privacy and security** : Protecting the privacy and security of data is paramount, especially when handling sensitive and personally identifiable information. In R you could apply appropriate measures to safeguard data from unauthorized access, breaches, or misuse. This includes practices such as anonymization, encryption, and access controls. The keyring package, introduced earlier in this chapter for securely managing passwords is an example of implementing privacy and security measures. It enables the safe storage and retrieval of credentials and reduces the risk of exposing sensitive information in code. There are several other R packages that support data protection practices such as anonymization, encryption, and secure access control. Some notable examples are as follows:

  - ` `` digest `` ` : Offers cryptographic hash functions (e.g., MD5, and SHA-256), which is useful for verifying data integrity and creating secure identifiers.
  - ` `` openssl `` ` : Facilitates encryption, decryption, and secure communication using OpenSSL, making it suitable for protecting data during storage or transmission.
  - ` `` credentials `` ` : Assists in managing Git credentials securely, particularly when working with private repositories or deploying code that accesses sensitive data.
  - ` `` httr `` ` : Supports secure web communication and authentication protocols, including OAuth and token-based access, which are essential for accessing protected APIs.

  Together, these packages provide a robust foundation for safeguarding sensitive data and ensuring compliance with privacy standards in analytical workflows.

-  **Documentation and metadata management** : Proper documentation and metadata management contribute to data governance by promoting transparency, reproducibility, and understanding of the analysis process. It involves but is not limited to documenting data sources, data transformations, variable definitions, and any assumptions or decisions made during analysis. In R, several packages support these practices by enabling structured documentation, automated reporting, and metadata handling. For instance, you can use **rmarkdown** or **Quarto** to create reproducible reports that integrate R code, SQL queries, visualizations, and narrative text in a single document. Beside this:
  - ` `` knitr `` ` : Works in a streamlined way with rmarkdown to execute embedded code chunks and generate well-formatted outputs
  - ` `` codebook `` ` : This package can assist in generating comprehensive metadata documentation for datasets, including variable descriptions, value labels, and summary statistics.
  - ` `` dataMeta `` ` : This provides tools for managing and attaching metadata to data frames, ensuring that contextual information remains linked to the data throughout the analysis.

Through proper use of these tools, you can maintain clear and up-to-date documentation that fosters collaboration, facilitates knowledge transfer, and ensures the integrity of results from analysis.
