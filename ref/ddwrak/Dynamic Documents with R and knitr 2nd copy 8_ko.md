### 8

###### 캐시

동적 문서의 한 가지 과제는 일부 코드 청크가 실행되는 데 오랜 시간이 걸릴 수 있으며, 이러한 청크가 자주 수정되거나 업데이트되지 않을 수 있다는 점입니다. 이런 경우 캐싱이 도움이 될 수 있습니다. 기본 아이디어는 마지막 실행 이후 청크가 수정되지 않은 한 다시 실행되지 않으며, 대신 이전 결과가 직접 로드된다는 것입니다.

###### 8.1 구현

캐시는 새로운 아이디어가 아닙니다. cacheSweave와 weaver 패키지 모두 Sweave를 기반으로 이를 구현했으며, 전자는 filehash를 사용하고 후자는 *.RData 이미지를 사용합니다. 또한 cacheSweave는 filehash를 기반으로 객체의 지연 로딩을 지원합니다. knitr 패키지는 내장 기본 R 함수를 직접 사용하여 객체를 저장(tools:::makeLazyLoadDB())하고 지연 로딩(lazyLoad())합니다.

cacheSweave 설명서(vignette)는 지연 로딩의 개념을 명확하게 설명합니다. 대략적으로 말하자면, 지연 로딩은 객체가 어딘가에서 실제로 사용될 때까지 메모리에 로드되지 않는 것을 의미합니다. 대신 "promise"만 생성되는데, 이는 일반적으로 빠르고 메모리 소비 측면에서 비용이 적게 듭니다. 이 promise가 계산에 사용될 때 실제 객체가 하드 디스크에서 로드됩니다. 이는 캐시에 유용합니다. 때때로 큰 객체를 읽고 캐시한 다음, 분석을 위해 하위 집합을 가져오고 이 하위 집합도 캐시됩니다. 향후에 우리의 계산이 하위 집합 객체에만 기반한다면 초기 큰 객체는 R에 로드되지 않을 것입니다. R의 promise에 대한 자세한 내용은 ?promise를 참조하시기 바랍니다.

캐싱을 켜려면 청크 옵션 cache를 TRUE(기본값은 FALSE)로 설정할 수 있습니다. 아래는 캐시의 효과를 빠르게 보여주는 코드 청크입니다.

- x <- 1 Sys.sleep(10)
- x <- 2


81

R을 10초 동안 대기 상태로 두기 위해 Sys.sleep()을 사용했습니다. 이 청크가 처음 컴파일될 때는 일시 중지를 볼 수 있지만, 다시 컴파일할 때는 코드 평가가 완전히 건너뛰어지기 때문에 일시 중지가 없습니다. 이 청크에서 생성된 객체 x가 있으며, 다음 번에 지연 로드될 것입니다. knitr는 청크에서 새로 생성된 모든 객체를 파악하고 지연 로드 데이터베이스(*.rdb 및 *.rdx 파일)에 저장합니다. 이제 x의 값을 확인할 수 있습니다.

x # value from previous chunk ## [1] 2

###### 8.2 캐시 작성

캐시 파일의 경로는 청크 옵션 cache.path에 의해 결정됩니다. 기본적으로 모든 캐시 파일은 현재 작업 디렉토리를 기준으로 cache/ 디렉토리 아래에 생성됩니다. 옵션 값에 디렉토리가 포함된 경우(예: cache.path = 'cache/abc-'), 캐시 파일은 해당 디렉토리 아래에 저장됩니다. 그림 경로와 유사하게 캐시 디렉토리는 존재하지 않으면 자동으로 생성되며, cache.path는 물리적 경로 대신 캐시 파일의 접두사가 될 수도 있습니다.

캐시는 R 코드와 청크 옵션을 포함하여 코드 청크에 변경 사항이 있을 때마다 무효화되고 제거됩니다. 즉, 이 청크의 이전 캐시 파일이 제거되고 새 캐시 파일로 교체됩니다. 캐시 파일 이름은 청크 레이블을 접두사로 사용하여 식별되며(문서에서 청크 레이블은 고유해야 함을 기억하시기 바랍니다), 캐시 파일 이름의 접미사는 R 코드, 청크 옵션 및 getOption('width') 값을 포함하는 목록인 R 객체의 MD5 해시 문자열입니다. MD5 해시는 digest 패키지에 의해 계산되며, knitr에서 캐시 파일 이름 생성을 에뮬레이트하는 아래 예제를 통해 작동 방식을 명확히 알 수 있습니다.

d <- digest::digest ## imagine x$code is the code chunk; x$options are chunk ## options

- x <- list(code = "1+1", options = list(results = "asis", fig.height = 3), width = getOption("width"))


d(x) ## [1] "667308d70fc72f26eb7454dde04af9a0"

x$code <- "1 + 1" # add spaces to code d(x)

## [1] "e903b616477cfa3e2314a3da65062dfb" x$options$eval <- FALSE # add option eval as FALSE d(x) ## [1] "8decb2a180f7f49b47de54bd5ec8fb34" x$width <- 40 d(x) ## [1] "7e1d77987b195b14d9b563b9a8f0ca6c"

위의 너비 32의 문자열은 MD5 해시입니다. MD5 해시가 내용의 변경에 민감하다는 것을 알 수 있습니다. 변경 사항이 단순히 공백이라 할지라도 모든 변경은 새로운 해시 문자열로 이어집니다. 캐시 파일 이름은 label_hash.rdb 형식입니다. 매번 knitr는 현재 청크의 해시를 캐시 파일 이름과 비교합니다. 일치하지 않는 경우 청크에 변경 사항이 발생했음을 의미하며 이전 캐시를 제거해야 합니다.

한 가지 예외는 include 옵션입니다. 이는 캐시되지 않는데, include = TRUE / FALSE가 코드 평가에 영향을 미치지 않으므로 캐시에 영향을 주지 않고 이 청크 옵션을 변경할 수 있기 때문입니다.

getOption('width')가 캐시에 영향을 미치는 이유는 출력되는 텍스트의 너비에 영향을 줄 수 있기 때문입니다.

###### 8.3 캐시 업데이트 시기

위에서 설명한 세 가지 구성 요소를 고려하는 것이 합리적으로 보이지만, 특정 상황에서는 캐시 업데이트 시기가 명확하지 않을 수 있습니다. 다음과 같은 두 가지 경우를 고려해 보겠습니다.

- 1. R은 몇 달마다 계속 업데이트되고 있으며, 새 버전마다 버그가 수정되고 새로운 기능이 도입됩니다. R을 최신 버전으로 업그레이드한 후 캐시를 업데이트해야 할까요? (R 패키지에도 유사한 문제가 적용됩니다)
- 2. 소스 문서에서 외부 데이터 파일을 읽었는데 그 파일이 수정된 경우, 모든 캐시된 결과를 업데이트해야 한다고 knitr에 어떻게 알릴 수 있을까요(소스 문서가 변경되지 않았더라도)?

이러한 경우 해시를 계산하기 위해 객체에 더 많은 구성 요소를 추가해야 합니다. 코드 청크는 임의의 옵션(이 책에서 소개된 옵션뿐만 아니라)을 수용할 수 있고 모든 청크 옵션이 해시에 반영되므로 추가 청크 옵션을 사용하여 캐시에 영향을 줄 수 있습니다.

첫 번째 질문에 답하기 위해, 예를 들어 R 버전을 값으로 취하는 version이라는 청크 옵션을 문서에 추가할 수 있습니다. 예를 들면 다음과 같습니다.
<<cache-rversion, cache=TRUE, version=R.version.string>>= # R 버전에 영향을 받을 수 있는 코드 R.version.string ## [1] "R version 3.2.0 (2015-04-16)" @

그러면 R이 업그레이드된 경우 이 청크가 다시 실행됩니다. 두 번째 문제를 해결하려면 외부 파일의 변경 사항을 knitr에 알려야 합니다. 한 가지 자연스러운 지표는 file.info() 함수로 얻을 수 있는 파일의 수정 시간입니다. 데이터 파일 이름이 iris.csv라고 가정하면 청크 옵션 iris_time에 수정 시간을 지정할 수 있습니다. 예를 들면 다음과 같습니다.

<<itime, cache=TRUE, iris_time=file.info( iris.csv )$mtime>>= # iris.csv가 최신 파일이 되면 데이터가 다시 읽힙니다 iris <- read.csv("iris.csv") @

캐시 업데이트 시기나 여부에 대한 정해진 규칙은 없습니다. 이는 특정 응용 프로그램에 따라 다릅니다. 예를 들어 R이 업그레이드된 후 캐시를 제거할 필요는 없습니다. 어쨌든 결과가 항상 최신 상태로 유지되도록 청크 옵션을 신중하게 설정해야 합니다.

###### 8.4 부작용 (Side Effects)

컴퓨터 과학에서 부작용(side effect)은 반환된 값이 아닌 함수 외부에서 발생하는 상태 변화를 의미합니다. 일반적인 부작용에는 플롯(창 또는 파일) 생성, 파일 작성, 콘솔에 결과 인쇄 등이 있습니다. 부작용을 캐시하는 것은 간단하지 않습니다. R 객체를 캐시 데이터베이스에 쉽게 저장할 수 있지만 함수에서 반환되는 값이 아니기 때문에 플롯 창을 저장하는 방법은 명확하지 않습니다. 이러한 이유로 weaver 및 cacheSweave와 같은 패키지는 부작용을 캐시하지 않지만, knitr는 다음과 같은 일부 부작용을 보존하려고 시도합니다.

- 1. 인쇄된 결과: 이는 코드 청크의 모든 출력이 실제로 평가되지 않더라도 캐시된 청크를 위해 출력 문서에 로드됨을 의미합니다. 그 이유는 knitr가 청크의 출력을 문자열로도 캐시하기 때문입니다. 그래픽 출력도 출력의 일부이므로 캐시된다는 점에 유의하시기 바랍니다.
- 2. 로드된 패키지: 각 캐시된 청크의 평가 후 현재 R 세션에서 사용된 패키지 목록은 __packages라는 접미사와 함께 캐시 경로 아래의 파일에 기록됩니다. 다음 번에 캐시된 청크를 다시 빌드해야 하는 경우 이러한 패키지가 먼저 로드됩니다. 패키지 이름을 캐시하는 이유는 일부 패키지를 로드하는 데 시간이 오래 걸릴 수 있으며, 이전 캐시된 청크에 로드된 패키지가 다음 캐시된 청크를 다시 빌드할 때 사용하지 못할 수 있기 때문입니다. 이는 캐시된 청크에만 적용되며 캐시되지 않은 청크의 경우 항상 library()를 사용하여 패키지를 명시적으로 로드해야 한다는 점에 유의하시기 바랍니다.
- 3. 무작위 시드: 청크가 무작위 시드(정수 벡터)를 생성한 경우 무작위 시뮬레이션의 재현성을 향상시키기 위해 다음에 시드가 저장되고 로드됩니다(12.4.7절 참조).

knitr가 일부 부작용을 유지하려고 시도하지만 par() 또는 options()를 설정하는 것과 같이 캐시되지 않는 다른 유형의 부작용이 여전히 존재합니다. 사용자는 이러한 특수한 경우를 인지하고 캐시되지 않아야 하는 코드를 캐시되지 않은 청크로 명확히 분리해야 합니다. 예를 들어, 문서의 첫 번째 청크에 모든 전역 옵션을 설정하고 해당 청크를 캐시하지 않습니다. 일반적으로 문서의 첫 번째 청크는 다음과 같습니다.

<<setup, cache=FALSE, include=FALSE>>= # 문서에 대한 일부 전역 옵션 설정 options(width = 60, show.signif.stars = FALSE) # 전역 청크 옵션도 설정 library(knitr) opts_chunk$set(fig.width = 5, fig.height = 4, tidy = FALSE) @

위의 청크에서 cache = FALSE는 기본값이기 때문에 종종 불필요합니다. 보수적으로 접근하여 이 청크가 확실히 캐시되지 않도록 하려면 추가할 수 있습니다.

###### 8.5 청크 종속성

때때로 캐시된 청크가 다른 캐시된 청크의 객체를 사용해야 할 수 있는데, 이는 심각한 문제를 야기할 수 있습니다. 이전 청크의 객체가 변경된 경우 다른 청크에서 이러한 변경을 감지하는 방법이 없다면 이 청크는 변경 사항을 알지 못하고 여전히 이전 캐시 결과를 사용하게 됩니다. 따라서 캐시된 청크에 종속성을 도입해야 합니다.

###### 8.5.1 수동 종속성

knitr에는 dependson이라는 청크 옵션이 있으며(cacheSweave에서 아이디어를 가져옴), dependson = c('chunkA', 'chunkB')와 같이 청크 레이블의 벡터를 설정하여 이 청크가 의존하는 다른 청크를 지정합니다. 그러면 캐시된 청크 chunkA 또는 chunkB 중 하나가 다시 빌드될 때마다 이 청크는 캐시를 잃고 다시 빌드됩니다.

청크 종속성은 체인을 형성할 수 있습니다. 다음 예제에서 chunkC는 chunkB에 의존하고 chunkB는 순차적으로 chunkA에 의존합니다. <<chunkA>>=

- x <- 1

- <<chunkB, dependson= chunkA >>=

y <- x + 2

- <<chunkC, dependson= chunkB >>=




- y + 5 @


chunkC는 chunkB에서 생성된 객체 y를 사용하고 chunkB는 chunkA에서 생성된 x의 값을 필요로 하므로 종속성이 필요합니다. 첫 번째 청크의 x가 변경되면 그에 따라 나머지 두 청크도 업데이트되어야 합니다.

dependson 옵션은 청크 인덱스의 정수 벡터를 사용할 수도 있습니다. 예를 들어 dependson = 1은 이 청크가 문서의 첫 번째 청크에 의존함을 의미하고, dependson = c(3, 5)는 세 번째 및 다섯 번째 청크에 대한 종속성을 나타냅니다. 인덱스가 음수이면 이 청크에서 역순으로 계산됨을 의미합니다. 예를 들어 dependson = -1은 이 청크가 이전 청크에 의존함을 의미하고 -c(1, 2, 3)은 이전 세 개의 청크를 의미합니다. dependson이 정수 값을 취하는 경우 이후 청크에 의존하게 할 수는 없습니다(이전 청크만 가능한 후보임에 유의하시기 바랍니다). dependson의 문자 값에는 이러한 제한이 없습니다.

###### 8.5.2 자동 종속성

청크 간의 종속성을 지정하는 또 다른 방법은 청크 옵션 autodep와 dep_auto() 함수를 사용하는 것입니다. 이는 weaver에서 빌린 실험적인 기능으로, 청크 종속성을 수동으로 설정하는 수고를 덜어줍니다. 기본 아이디어는 이후 청크가 이전 청크에서 생성된 객체를 사용하는 경우 이후 청크가 이전 청크에 종속된다는 것입니다.

codetools 패키지의 findGlobals() 함수는 청크의 모든 전역 객체를 찾는 데 사용되며 해당 문서에 따르면 결과는 근사치입니다. 전역 객체는 대략 로컬로 생성되지 않은 객체를 의미합니다. 예를 들어 function() {y <x} 표현식에서 x는 이 함수의 본문에서 생성되는 것을 볼 수 없기 때문에 외부에 존재하는 전역 객체여야 하는 반면(실제로 어떤 객체이든 상관없이), y는 로컬입니다. 한편, 이후 청크의 전역 객체와 비교할 수 있도록 각 캐시된 청크에서 생성된 객체의 목록도 저장해야 합니다. 예를 들어 청크 A가 객체 x를 생성하고 청크 B가 이 객체를 사용하는 경우 청크 B는 A에 종속되어야 합니다. 즉, A가 변경될 때마다 B도 업데이트되어야 합니다.

autodep = TRUE인 경우 knitr는 캐시된 청크에서 생성된 객체의 이름과 전역 객체를 각각 __objects 및 __globals라는 두 파일에 씁니다. 나중에 dep_auto() 함수를 사용하여 객체 이름을 분석하여 종속성을 자동으로 파악할 수 있습니다. 일반적인 사용법은 다음과 같습니다.

<<setup, cache=FALSE, include=FALSE>>= opts_chunk$set(autodep = TRUE) # 전역적으로 autodep 설정 dep_auto() # 종속성 파악 @

종속성을 지정하는 또 다른 방법은 dep_prev()입니다. 이는 캐시된 청크가 이전의 모든 청크에 종속되도록 종속성을 설정하는 보수적인 접근 방식입니다. 즉, 이전 청크가 업데이트될 때마다 이후의 모든 청크도 그에 따라 업데이트됩니다.

어떤 경우든 캐시되지 않은 청크에 대한 종속성은 knitr에 무의미합니다. 왜냐하면 knitr는 캐시된 청크에 대한 변경 사항만 확인하기 때문입니다. knitr는 캐시되지 않은 청크에 대한 종속성을 발견하면 경고를 제공합니다. 캐시되지 않은 청크에 의존해야 하는 경우 8.3절에서 소개한 트릭을 사용할 수 있습니다. 즉, 캐시되지 않은 객체를 캐시된 청크의 청크 옵션에 넣는 것입니다. 아래는 예제입니다.

- <<A, cache=FALSE>>=

- x <- 1 @

<<B, cache=TRUE, foo=x>>=

- y <- x + 2 @




캐시되지 않은 청크 A에서 객체 x를 생성하고 캐시된 청크 B에서 사용했습니다. 두 청크 간에 종속성이 없으면 A가 업데이트될 때 B가 업데이트되지 않지만, 청크 B에서 foo = x 옵션을 설정한 경우 x의 값이 변경되면 B가 자동으로 업데이트되어 B의 청크 옵션이 변경됩니다.

###### 8.6 수동으로 캐시 로드

일반적으로 캐시 데이터베이스는 캐시된 청크를 위해 자동으로 로드되며 실제로 수동으로 로드할 수도 있습니다. 이것은 유용한 적용 사례가 있습니다. 나중 청크에서 값 x를 계산했지만 문서 앞부분에서 사용하려고 한다고 가정해 보겠습니다. knitr는 문서를 선형 방식으로 컴파일하고 미래에 생성된 객체를 사용할 수 없기 때문에 이는 불가능합니다. 그러나 해당 청크에 대한 캐시를 켠 경우 해당 캐시 데이터베이스를 일찍 로드할 수 있습니다.

knitr의 load_cache() 함수는 이러한 목적으로 설계되었습니다. 캐시 데이터베이스를 찾기 위해 청크 레이블을 취하며, 선택적으로 이 함수가 캐시에서 반환하도록 할 객체를 지정할 수 있습니다.

load_cache(label, object, notfound = "NOT AVAILABLE", path = opts_chunk$get("cache.path"), lazy = TRUE)

이제 문서 나중에 객체 x를 생성하는 foo라는 캐시된 청크가 있다고 가정해 보겠습니다. load_cache('foo', 'x')를 사용하여 해당 청크에서 x의 값을 가져올 수 있습니다. 물론 문서를 처음 컴파일할 때는 x를 사용할 수 없으며, 이것이 notfound 인수가 있는 이유입니다. 인라인 R 표현식에서 x를 사용하면 출력에 NOT AVAILABLE이 표시되며, foo 청크가 캐시되었으므로 문서를 다시 컴파일한 후에는 x의 값으로 교체됩니다.

###### 8.7 기타 옵션

지연 로딩이 유용하긴 하지만 우리가 아직 명확히 알지 못하는 이유로 특정 경우에는 작동하지 않을 수 있습니다. 어쨌든 청크 옵션 cache.lazy = FALSE를 사용하여 지연 로딩을 끌 수 있습니다. 이 경우 knitr는 save()로 객체를 저장하고 load()로 객체를 로드하며 이는 항상 작동할 것입니다.

때로는 코드의 다른 부분을 실제로 변경하지 않고 코드 주석을 수정하는 경우가 있으며, 코드 주석을 업데이트했다는 이유만으로 캐시 데이터베이스를 업데이트하고 싶지는 않을 것입니다. 이 경우 청크 옵션 cache.comments = FALSE를 사용할 수 있습니다. 그러면 MD5 해시를 계산할 때 주석이 제외되므로 주석의 변경 사항이 캐시에 영향을 미치지 않습니다.
