source("_common.R")

1 스프레드시트 (Spreadsheets)

.csv 및 .tsv와 같은 일반 텍스트 파일에서 데이터를 가져오는 방법에 대해 배웠습니다. 이제 Excel 스프레드시트나 Google 스프레드시트 등 스프레드시트에서 데이터를 가져오는 방법을 배울 차례입니다.

이는 스프레드시트 데이터로 작업할 때 추가로 고려해야 할 사항과 복잡성에 대해서도 논의할 것입니다.

여러분이 혹은 여러분의 동료가 데이터 구성을 위해 스프레드시트를 사용하고 있다면 Karl Broman과 Kara Woo의 “스프레드시트의 데이터 구성(Data Organization in Spreadsheets)” 논문(https://doi.org/10.1080/00031305.2017.1375989)을 읽어보실 것을 강력히 권장합니다.

이 논문에 제시된 모범 사례(best practices)는 데이터를 분석하고 시각화하기 위해 스프레드시트에서 R로 가져올 때 많은 골칫거리(headache)를 덜어줄 것입니다.

Microsoft Excel은 스프레드시트 파일 내의 워크시트에 데이터가 구성되는 널리 사용되는 스프레드시트 소프트웨어 프로그램입니다.

#| message: false
library(readxl)
library(tidyverse)
library(writexl)

대부분의 readxl 함수를 사용하여 Excel 스프레드시트를 R로 로드할 수 있습니다.

  1. read_xls()는 xls 형식의 Excel 파일을 읽습니다.
  2. read_xlsx()는 xlsx 형식의 Excel 파일을 읽습니다.
  3. read_excel()은 xls 및 xlsx 형식의 파일을 모두 읽을 수 있습니다. 입력을 기반으로 파일 유형을 추측합니다.

이러한 함수들은 다른 유형의 파일을 읽기 위해 이전에 소개한 다른 함수(read_csv(), read_table() 등)와 마찬가지로 모두 유사한 구문(syntax)을 갖습니다. 이 장의 나머지 부분에서는 read_excel() 사용에 초점을 맞출 것입니다.

1.1 엑셀 스프레드시트 읽기

R로 읽을 스프레드시트가 Excel에서 어떻게 생겼는지 보여줍니다. 이 스프레드시트는 https://docs.google.com/spreadsheets/d/1V1nPp1tzOuutXFLb3G9Eyxi3qxeEhnOXUzL5_BcCQ0w/에서 Excel 파일로 다운로드할 수 있습니다.

read_excel()의 첫 번째 인수는 읽을 파일의 경로입니다.

students <- read_excel("data/students.xlsx")

read_excel()은 파일을 티블로 읽어옵니다.

students

데이터에는 6명의 학생이 있고 각 학생에 대해 5개의 변수가 있습니다. 그러나 이 데이터셋에서 해결(address)하고 싶은 몇 가지 사항이 있습니다.

  1. 열 이름이 엉망입니다.: 일관된 형식을 따르는 열 이름을 제공할 수 있습니다. col_names 인수를 사용하여 snake_case를 권장합니다.
read_excel(
  "data/students.xlsx",
  col_names = c("student_id", "full_name", "favourite_food", "meal_plan", "age")
)

불행히도(Unfortunately) 이것은 완전히(quite) 성공적이지는 않았습니다. 이제 원하는 변수 이름이 생겼지만 이전 헤더 행이었던 것이 데이터의 첫 번째 관측값으로 나타납니다. skip 인수를 사용하여 해당 행을 명시적으로 건너뛸(skip) 수 있습니다.

read_excel(
  "data/students.xlsx",
  col_names = c("student_id", "full_name", "favourite_food", "meal_plan", "age"),
  skip = 1
)
  1. favourite_food 열에서 관측값 중 하나는 N/A인데, 이는 “이용할 수 없음(not available)”을 의미하지만 현재는 NA로 인식되지 않습니다(이 N/A와 목록에 있는 네 번째 학생의 나이의 대조(contrast)에 유의하세요). na 인수를 사용하여 어떤 문자열을 NA로 인식해야 하는지 지정할 수 있습니다. 기본적으로 ""(빈 문자열, 또는 스프레드시트에서 읽을 때 빈 셀이나 수식 =NA()가 있는 셀)만 NA로 인식됩니다.
read_excel(
  "data/students.xlsx",
  col_names = c("student_id", "full_name", "favourite_food", "meal_plan", "age"),
  skip = 1,
  na = c("", "N/A")
)
  1. 남아있는 또 다른 문제는 age가 문자형 변수로 읽히지만 실제로는 숫자형이어야 한다는 것입니다. 플랫 파일에서 데이터를 읽기 위한 read_csv() 및 친구들과 마찬가지로, read_excel()에 col_types 인수를 제공(supply)하고 읽어올 변수의 열 유형을 지정할 수 있습니다. 구문은 약간(a bit) 다릅니다. 여러분의 옵션은 "skip", "guess", "logical", "numeric", "date", "text" 또는 "list"입니다.
read_excel(
  "data/students.xlsx",
  col_names = c("student_id", "full_name", "favourite_food", "meal_plan", "age"),
  skip = 1,
  na = c("", "N/A"),
  col_types = c("numeric", "text", "text", "text", "numeric")
)

그러나 이것도 완전히 원하는 결과를 생성하지는 못했습니다. age가 숫자여야 한다고 지정함으로써 숫자형이 아닌 항목(항목 값 five)이 있는 하나의 셀을 NA로 변경했습니다. 이 경우 나이를 "text"로 읽은 다음 데이터가 R에 로드된 후 변경해야 합니다.

students <- read_excel(
  "data/students.xlsx",
  col_names = c("student_id", "full_name", "favourite_food", "meal_plan", "age"),
  skip = 1,
  na = c("", "N/A"),
  col_types = c("numeric", "text", "text", "text", "text")
)

students <- students |>
  mutate(
    age = if_else(age == "five", "5", age),
    age = parse_number(age)
  )

students

데이터를 우리가 원하는 형식으로 정확하게 로드하는 데 여러 단계와 시행착오(trial-and-error)가 필요했으며, 이는 예상치 못한 일(not unexpected)이 아닙니다. 데이터 과학은 반복적인(iterative) 과정(process)이며, 데이터 저장을 위해서뿐만 아니라 공유와 커뮤니케이션을 위해 사람이 스프레드시트에 데이터를 입력하고 사용하려는 경향이 있기 때문에 스프레드시트에서 데이터를 읽어 들일 때 반복 과정이 다른 일반 텍스트, 사각형(rectangular) 데이터 파일에 비해 훨씬 더 지루할(tedious) 수 있습니다.

데이터를 로드하고 살펴보기 전까지는 데이터가 정확히 어떻게 생겼는지 알 수 있는 방법이 없습니다. 음, 사실(actually) 한 가지 방법이 있습니다. Excel에서 파일을 열고 엿볼(take a peek) 수 있습니다. 이렇게 하려는 경우 원본 데이터 파일은 손대지 않은(untouched) 상태로 유지하고 손대지 않은 파일에서 R로 읽는 동안 상호 작용하여 열어보고 탐색할 수 있도록(to open and browse interactively) Excel 파일의 복사본을 만드는 것이 좋습니다.

이렇게 하면 스프레드시트를 검사(inspecting)하는 동안 우발적으로 덮어쓰지(overwrite) 않도록 할 수 있습니다. 또한 여기서 우리가 한 작업, 즉 데이터를 로드하고, 살펴보고, 코드를 조정(adjustments)하고, 다시 로드하고, 결과에 만족(happy)할 때까지 반복하는 것을 두려워(afraid)해서는 안 됩니다.

1.2 워크시트 읽기

스프레드시트를 플랫 파일과 구별하는(distinguishes) 중요한 기능(feature)은 워크시트라고 하는 여러 시트의 개념(notion)입니다. read_excel()의 sheet 인수를 사용하여 스프레드시트에서 단일 워크시트를 읽을 수 있습니다. 지금까지(up until now) 의존해(relying on) 왔던 기본값은 첫 번째 시트입니다.

read_excel("data/penguins.xlsx", sheet = "Torgersen Island")

숫자형 데이터가 포함된 것으로 보이는 일부 변수는 "NA" 문자열이 실제 NA로 인식되지 않아 문자형으로 읽혔습니다.

penguins_torgersen <- read_excel("data/penguins.xlsx", sheet = "Torgersen Island", na = "NA")

penguins_torgersen

또는(Alternatively) excel_sheets()를 사용하여 Excel 스프레드시트의 모든 워크시트에 대한 정보를 가져온 다음 관심 있는 워크시트를 읽을 수 있습니다.

excel_sheets("data/penguins.xlsx")

워크시트 이름을 알게 되면 read_excel()을 사용하여 개별적(individually)으로 읽을 수 있습니다.

penguins_biscoe <- read_excel("data/penguins.xlsx", sheet = "Biscoe Island", na = "NA")
penguins_dream  <- read_excel("data/penguins.xlsx", sheet = "Dream Island", na = "NA")

이 경우 전체 펭귄 데이터셋은 스프레드시트의 3개 워크시트에 분산(spread)되어 있습니다. 각 워크시트에는 동일한 수의 열이 있지만 행 수는 다릅니다.

dim(penguins_torgersen)
dim(penguins_biscoe)
dim(penguins_dream)

bind_rows()를 사용하여 함께 합칠(put them together) 수 있습니다.

penguins <- bind_rows(penguins_torgersen, penguins_biscoe, penguins_dream)
penguins

1.3 시트의 일부 읽기

많은 사람들이 데이터 저장뿐만 아니라 프레젠테이션용으로도 Excel 스프레드시트를 사용하기 때문에 R로 읽으려는 데이터의 일부가 아닌 셀 항목을 스프레드시트에서 찾는 것은 매우 흔한 일입니다. 시트 중간에는 데이터 프레임처럼 보이는 것이 있지만 데이터 위와 아래의 셀에는 외적인(extraneous) 텍스트가 있습니다.

이 스프레드시트는 readxl 패키지에서 제공하는 예제 스프레드시트 중 하나입니다. readxl_example() 함수를 사용하여 패키지가 설치된 디렉터리의 시스템에서 스프레드시트를 찾을(locate) 수 있습니다.

이 함수는 평소처럼 read_excel()에서 사용할 수 있는 스프레드시트의 경로를 반환합니다.

deaths_path <- readxl_example("deaths.xlsx")
deaths <- read_excel(deaths_path)
deaths

상위 3개 행과 하위 4개 행은 데이터 프레임의 일부가 아닙니다. skip 및 n_max 인수를 사용하여 이러한 외적인(extraneous) 행을 제거(eliminate)할 수 있지만 셀 범위를 사용하는 것을 권장합니다. Excel에서 왼쪽 상단 셀은 A1입니다.

열을 가로질러 오른쪽으로 이동하면 셀 레이블이 알파벳순으로 이동합니다(B1, C1 등). 그리고 열 아래로 이동하면 셀 레이블의 숫자가 증가합니다(A2, A3 등).

여기서 우리가 읽고자 하는 데이터는 셀 A5에서 시작하여 셀 F15에서 끝납니다. 스프레드시트 표기법(notation)으로는 A5:F15이며, 이를 range 인수에 제공합니다.

read_excel(deaths_path, range = "A5:F15")

1.4 데이터 유형

CSV 파일에서 모든 값은 문자열(strings)입니다. 이것이 데이터에 특히 충실한(true) 것은 아니지만 단순합니다. 모든 것이 문자열입니다.

Excel 스프레드시트의 근본적인(underlying) 데이터는 더 복잡합니다. 셀은 다음 네 가지 중 하나일 수 있습니다.

  • TRUE, FALSE 또는 NA와 같은 부울(boolean).
  • “10” 또는 “10.5”와 같은 숫자(number).
  • “11/1/21” 또는 “11/1/21 3:00 PM”과 같이 시간도 포함할 수 있는 날짜-시간(datetime).
  • “ten”과 같은 텍스트 문자열(text string).

스프레드시트 데이터로 작업할 때는 근본적인 데이터가 셀에 표시되는 내용과 매우 다를 수 있다는 점을 명심(keep in mind)하는 것이 중요합니다. 예를 들어 Excel에는 정수(integer)라는 개념(notion)이 없습니다.

모든 숫자는 부동 소수점(floating points)으로 저장되지만 사용자 지정 가능한(customizable) 소수점 이하 자릿수(decimal points)로 데이터를 표시하도록 선택할 수 있습니다.

마찬가지로 날짜는 실제로는 숫자, 구체적으로는 1900년 1월 1일 이후의 일수로 저장됩니다. Excel에서 서식을 적용하여 날짜 표시 방식을 사용자 지정할 수 있습니다.

혼란스럽게도(Confusingly), 숫자처럼 보이지만 실제로는 문자열인 것도 가능합니다(Excel 셀에 '10을 입력).

근본적인 데이터가 저장되는 방식과 표시되는 방식 간의 이러한 차이로 인해 데이터가 R에 로드될 때 놀라움(surprises)을 유발할 수 있습니다.

기본적으로 readxl은 주어진 열의 데이터 유형을 추측합니다.

권장하는 워크플로는 readxl이 열 유형을 추측하도록 하고, 추측된 열 유형에 만족하는지(happy) 확인한 다음, 그렇지 않은 경우 col_types를 지정하여 다시 가져오는(re-import) 것입니다.

또 다른 과제는 Excel 스프레드시트에 이러한 유형이 혼합된 열이 있는 경우입니다(일부 셀은 숫자, 일부는 텍스트, 일부는 날짜).

데이터를 R로 가져올 때 readxl은 몇 가지 결정을 내려야 합니다.

이러한 경우 이 열의 유형을 "list"로 설정할 수 있으며, 그러면 열이 길이 1인 벡터들의 목록으로 로드되며 각 벡터 요소의 유형이 추측됩니다.

1.5 엑셀에 쓰기

나중에 쓸(write out) 수 있는 작은 데이터 프레임을 만들어 봅시다. item은 요인(factor)이고 quantity는 정수입니다.

bake_sale <- tibble(
  item     = factor(c("brownie", "cupcake", "cookie")),
  quantity = c(10, 5, 8)
)

bake_sale

1.6 형식이 지정된 출력

writexl 패키지는 간단한 Excel 스프레드시트를 작성하기 위한 솔루션이지만, 스프레드시트 내의 시트에 쓰거나 스타일 지정(styling)과 같은 추가 기능에 관심이 있다면 openxlsx 패키지를 사용하는 것이 좋습니다.

여기서 이 패키지 사용에 대한 자세한 내용을 다루지는 않지만(go into the details), openxlsx를 사용하여 R에서 Excel로 작성된 데이터에 대한 추가 서식 지정 기능에 대한 광범위한(extensive) 논의는 https://ycphs.github.io/openxlsx/articles/Formatting.html을 읽어보실 것을 권장합니다.

이 패키지는 tidyverse의 일부가 아니므로 함수와 워크플로가 생소하게(unfamiliar) 느껴질 수 있습니다. 예를 들어 함수 이름은 카멜 케이스(camelCase)이고, 여러 함수를 파이프라인으로 구성(composed)할 수 없으며, 인수의 순서가 tidyverse에서 흔히 쓰이는 순서와 다릅니다.

하지만 괜찮습니다.

이 책을 벗어나 R 학습과 사용이 확장(expands)됨에 따라 R에서 특정 목표를 달성(accomplish)하기 위해 사용할 수 있는 다양한 R 패키지에서 사용되는 다양한 스타일을 마주치게(encounter) 될 것입니다.

새로운 패키지에서 사용되는 코딩 스타일에 익숙해지는(familiarizing) 좋은 방법은 함수 설명서에 제공된 예제를 실행하여 구문과 출력 형식에 대한 감을 익히고(get a feel for) 패키지와 함께 제공될 수 있는 비네트(vignettes)를 읽어보는 것입니다.

2 구글 스프레드시트

Google 스프레드시트는 또 다른 널리 사용되는 스프레드시트 프로그램입니다. 무료이며 웹 기반입니다. Excel과 마찬가지로 Google 스프레드시트에서도 데이터는 스프레드시트 파일 내부의 워크시트(또는 시트)에 구성(organized)됩니다.

library(googlesheets4)
library(tidyverse)

패키지 이름에 대한 간단한 참고 사항: googlesheets4는 R 인터페이스를 Google 스프레드시트에 제공하기 위해 Sheets API v4의 v4를 사용하므로 이런 이름이 붙었습니다.

googlesheets4 패키지의 주요 함수는 URL이나 파일 ID에서 Google 스프레드시트를 읽어오는 read_sheet()입니다. 이 함수는 range_read()라는 이름으로도 쓰입니다. 또한 gs4_create()를 사용하여 완전히 새로운 시트를 만들거나 sheet_write()와 친구들을 사용하여 기존 시트에 쓸 수도 있습니다.

Excel과 Google 스프레드시트가 완전히(exactly) 같은 방식으로 동작하지는 않으므로 다른 작업에서는 함수 호출에 대한 추가 업데이트가 필요할 수 있다는 점도 보게 될 것입니다.

2.1 구글 스프레드시트 읽기

read_sheet()의 첫 번째 인수는 읽을 파일의 URL이며 티블(tibble)을 반환합니다. 예를 들어 https://docs.google.com/spreadsheets/d/1V1nPp1tzOuutXFLb3G9Eyxi3qxeEhnOXUzL5_BcCQ0w에서 이러한 URL은 다소 긴 편이므로 종종 해당 ID로 시트를 식별하려고 할 것입니다.

students_sheet_id <- "1V1nPp1tzOuutXFLb3G9Eyxi3qxeEhnOXUzL5_BcCQ0w"
students <- read_sheet(students_sheet_id)
students

read_excel()에서 했던 것과 마찬가지로 read_sheet()에 열 이름, NA 문자열 및 열 유형을 제공(supply)할 수 있습니다.

students <- read_sheet(
  students_sheet_id,
  col_names = c("student_id", "full_name", "favourite_food", "meal_plan", "age"),
  skip = 1,
  na = c("", "N/A"),
  col_types = "dcccc"
)

students

여기서는 짧은 코드(short codes)를 사용하여 열 유형을 약간 다르게 정의했습니다. 예를 들어 “dcccc”는 “double, character, character, character, character”를 나타냅니다.

Google 스프레드시트에서 개별 시트를 읽는 것도 가능합니다. 펭귄 구글 스프레드시트(penguins Google Sheet)에서 “Torgersen Island” 시트를 읽어봅시다.

penguins_sheet_id <- "1aFu8lnD_g0yjF5O-K6SFgSEWiHPpgvFCF0NY9D6LXnY"
read_sheet(penguins_sheet_id, sheet = "Torgersen Island")

sheet_names()를 사용하여 Google 스프레드시트 내의 모든 시트 목록을 얻을(obtain) 수 있습니다.

sheet_names(penguins_sheet_id)

마지막으로 read_excel()과 마찬가지로 read_sheet()에 range를 정의하여 Google 스프레드시트의 일부분을 읽어들일 수 있습니다. 또한 아래의 gs4_example() 함수를 사용하여 googlesheets4 패키지와 함께 제공되는 예제 Google 스프레드시트를 찾고(locate) 있다는 점에 유의하세요.

deaths_url <- gs4_example("deaths")
deaths <- read_sheet(deaths_url, range = "A5:F15")

2.3 인증

공개 Google 스프레드시트의 경우 Google 계정 인증 없이 그리고 gs4_deauth()를 사용하여 읽을 수 있지만, 비공개 시트를 읽거나 시트에 쓰려면 googlesheets4가 여러분의 Google 스프레드시트를 보고 관리할 수 있도록 인증이 필요합니다.

인증이 필요한 시트를 읽으려고 시도할 때, googlesheets4는 웹 브라우저로 안내하여 Google 계정에 로그인하고 Google 스프레드시트를 대신하여 운영할 수 있는 권한을 부여하라는 메시지를 표시합니다.

그러나 특정 Google 계정, 인증 범위 등을 지정하려는 경우 gs4_auth()를 사용할 수 있습니다(gs4_auth(email = "mine@example.com")). 이렇게 하면 특정 이메일과 연결된 토큰을 강제로 사용하게 됩니다.

인증에 대한 자세한 내용은 googlesheets4 인증 비네트(auth vignette) 문서(https://googlesheets4.tidyverse.org/articles/auth.html)를 읽어보실 것을 권장합니다.

3 Arrow

CSV 파일은 사람이 읽기 쉽도록 설계되었습니다. 매우 단순하고 세상의 모든 도구에서 읽을 수 있기 때문에 훌륭한 교환 형식입니다. 하지만 CSV 파일은 그다지 효율적이지 않습니다. R로 데이터를 읽어 들이려면 꽤 많은 작업(work)을 해야 합니다.

이 장에서는 강력한 대안인 빅데이터 시스템에서 널리 사용되는 개방형 표준 기반 형식인 parquet 형식에 대해 배울 것입니다.

우리는 parquet 파일을 대규모 데이터셋의 효율적인 분석 및 전송을 위해 설계된 다국어 도구 상자인 Apache Arrow와 페어링할 것입니다.

익숙한 dplyr 구문을 사용하여 메모리보다 큰 데이터셋을 분석할 수 있는 dplyr 백엔드를 제공하는 arrow 패키지를 통해 Apache Arrow를 사용할 것입니다.

추가적인 이점으로, arrow는 매우 빠릅니다. arrow와 dbplyr 모두 dplyr 백엔드를 제공하므로 언제 각각을 사용해야 할지 궁금할 수 있습니다.

많은 경우, 데이터가 이미 데이터베이스나 parquet 파일에 있고 그대로(as is) 작업하기를 원하므로 선택은 이미 정해져 있습니다. 하지만 자체 데이터(아마도 CSV 파일)로 시작하는 경우 데이터를 데이터베이스에 로드하거나 parquet로 변환할 수 있습니다. 일반적으로 어떤 것이 잘 작동할지 알기 어렵기 때문에 분석 초기 단계에서는 두 가지를 모두 시도해 보고 자신에게 잘 맞는 것을 선택하는 것이 좋습니다.

3.2 데이터셋 열기

데이터를 살펴보는 것부터 시작해 봅시다. 9GB인 이 파일은 메모리에 전체를 로드하고 싶지 않을 정도로 큽니다. 경험 법칙상 일반적으로 데이터 크기의 두 배 이상의 메모리가 필요한데 많은 노트북은 16GB가 최대입니다. 따라서 read_csv()를 피하고 대신 arrow::open_dataset()을 사용하는 것이 좋습니다.

seattle_csv <- open_dataset(
  sources = "data/seattle-library-checkouts.csv", 
  col_types = schema(ISBN = string()),
  format = "csv"
)

open_dataset()은 처음 몇 천 개의 행을 스캔하여 데이터셋의 구조를 파악합니다. ISBN 열에는 처음 80,000개 행에 빈 값이 포함되어 있으므로 arrow가 데이터 구조를 파악하는 데 도움이 되도록 열 유형을 지정해야 합니다. open_dataset()이 데이터를 스캔하면 찾은 내용을 기록하고 중지합니다; 사용자가 명시적으로 요청할 때만 추가 행을 읽습니다. 이 메타데이터는 seattle_csv를 출력하면 볼 수 있는 내용입니다.

3.3 parquet 형식

이 데이터를 작업하기 더 쉽게 만들려면 parquet 파일 형식으로 전환하고 여러 파일로 나누어 봅시다. 다음 섹션에서는 먼저 parquet와 파티셔닝에 대해 소개한 다음 학습한 내용을 시애틀 도서관 데이터에 적용해 볼 것입니다.

3.3.1 parquet의 장점

CSV와 마찬가지로 parquet은 사각형 데이터에 사용되지만 파일 편집기로 읽을 수 있는 텍스트 형식 대신 빅데이터의 요구를 위해 특별히 설계된 사용자 지정 바이너리 형식입니다. 이것이 의미하는 바는 다음과 같습니다.

  • parquet 파일은 일반적으로 동등한 CSV 파일보다 더 작습니다. parquet은 파일 크기를 줄이기 위해 효율적인 인코딩(efficient encodings)에 의존하며 파일 압축을 지원합니다. 디스크에서 메모리로 이동할 데이터가 더 적기 때문에 parquet 파일을 빠르게 만드는 데 도움이 됩니다.

  • parquet 파일은 풍부한 유형 시스템을 갖추고 있습니다. CSV 파일은 열 유형에 대한 어떤 정보도 제공하지 않습니다. 예를 들어 CSV 리더는 "08-10-2022"를 문자열로 구문 분석할지 날짜로 구문 분석할지 추측해야 합니다. 이와 대조적으로 parquet 파일은 데이터와 함께 유형을 기록하는 방식으로 데이터를 저장합니다.

  • parquet 파일은 “열 지향적”입니다. 이는 R의 데이터 프레임과 마찬가지로 열별로 구성되어 있음을 의미합니다. 따라서 일반적으로 행별로 구성된 CSV 파일과 비교하여 데이터 분석 작업의 성능이 더 향상됩니다.

  • parquet 파일은 “청크화(chunked)”되어 있어 파일의 서로 다른 부분을 동시에 작업할 수 있으며 운이 좋다면 일부 청크를 아예 건너뛸 수 있습니다.

parquet 파일에는 한 가지 주된 단점이 있습니다. 더 이상 “사람이 읽을 수” 없다는 것입니다. 즉, readr::read_file()을 사용하여 parquet 파일을 보면 알 수 없는 말 덩어리만 보일 것입니다.

3.3.2 파티셔닝

데이터셋이 점점 더 커짐에 따라 모든 데이터를 단일 파일에 저장하는 것은 점점 더 고통스러워(painful)지며 큰 데이터셋을 여러 파일에 분할(split)하는 것이 종종(often) 유용(useful)합니다.

이 구조화가 지능적으로 이루어지면 많은 분석에서 파일의 하위 집합만 필요하기 때문에 이 전략은 성능에 상당한 개선을 가져올 수 있습니다.

데이터셋을 파티셔닝하는 방법에 대한 확고한 규칙은 없습니다. 결과는 데이터, 액세스 패턴 및 데이터를 읽는 시스템에 따라 달라집니다. 자신의 상황에 맞는 이상적인 파티셔닝을 찾기 전에 몇 가지 실험을 거쳐야 할 가능성이 높습니다.

대략적인 가이드로서 arrow는 20MB보다 작거나 2GB보다 큰 파일을 피하고 10,000개 이상의 파일을 생성하는 파티션을 피할 것을 제안합니다.

또한 필터링 기준으로 삼을 변수로 파티셔닝하려고 노력해야 합니다. 조금 뒤에 보겠지만, 이를 통해 arrow는 관련 파일만 읽어 많은 작업을 건너뛸 수 있습니다.

Hive 스타일 파티션은 “key=value” 규칙으로 폴더 이름을 지정하므로 짐작하셨겠지만 CheckoutYear=2005 디렉터리에는 CheckoutYear가 2005인 모든 데이터가 포함되어 있습니다.

3.4.1 성능

CSV에서 parquet로 전환할 때의 성능 영향(impact)을 간단히 살펴보겠습니다. 먼저, 데이터가 단일 대용량 csv로 저장된 경우 2021년 매월 대출된 도서 수를 계산하는 데 걸리는 시간을 측정해 보겠습니다.

#| cache: true

  filter(CheckoutYear == 2021, MaterialType == "BOOK") |>
  group_by(CheckoutMonth) |>
  summarize(TotalCheckouts = sum(Checkouts)) |>
  arrange(desc(CheckoutMonth)) |>
  collect() |> 
  system.time()

이제 시애틀 도서관 대출 데이터가 18개의 작은 parquet 파일로 파티셔닝된 새 버전의 데이터셋을 사용해 보겠습니다.

#| cache: true

seattle_pq |> 
  filter(CheckoutYear == 2021, MaterialType == "BOOK") |>
  group_by(CheckoutMonth) |>
  summarize(TotalCheckouts = sum(Checkouts)) |>
  arrange(desc(CheckoutMonth)) |>
  collect() |> 
  system.time()

약(~) 100배의 성능 향상(speedup)은 다중 파일 파티셔닝과 개별(individual) 파일 형식이라는 두 가지 요인(factors) 때문(attributable)입니다.

  1. 파티셔닝은 성능을 향상시킵니다. 이 쿼리는 데이터를 필터링하기 위해 CheckoutYear == 2021을 사용하며, arrow는 18개의 parquet 파일 중 1개만 읽으면 된다는 것을 인식(recognize)할 만큼 똑똑하기(smart enough) 때문입니다.

  2. parquet 형식은 데이터를 메모리로 더 직접 읽을 수 있는 바이너리(binary) 형식으로 저장하여 성능을 향상시킵니다. 열 단위(column-wise) 형식과 풍부한 메타데이터(metadata)는 arrow가 쿼리에 실제로(actually) 사용된 4개의 열(CheckoutYear, MaterialType, CheckoutMonth, Checkouts)만 읽으면 된다는 것을 의미합니다.

성능의 이 엄청난 차이(massive difference)가 바로 대용량 CSV를 parquet로 변환하는 것이 가치 있는(pays off) 이유입니다!

parquet과 arrow의 마지막 장점(advantage)이 하나 있습니다. arrow::to_duckdb()를 호출하여 arrow 데이터셋을 DuckDB 데이터베이스로 바꾸는(turn) 것이 매우(very) 쉽다는 것입니다.

4 데이터베이스

엄청난 양의(huge amount of) 데이터가 데이터베이스에 존재하므로(lives in), 데이터베이스에 접근(access)하는 방법을 아는 것은 필수적(essential)입니다. 때로는 다른 사람에게 스냅샷(snapshot)을 .csv로 다운로드해 달라고 요청할 수 있지만, 이는 금방 고통스러워집니다. 변경(change)을 해야 할 때마다 다른 사람과 소통(communicate)해야 합니다.

여러분이 필요할 때 필요한 데이터를 얻기 위해 데이터베이스에 직접 접근(reach into)할 수 있기를 원할 것입니다.

이 장에서는 먼저 DBI 패키지의 기본 사항에 대해 배웁니다. DBI 패키지를 사용하여 데이터베이스에 연결한 다음 SQL 쿼리로 데이터를 검색하는 방법을 배웁니다.

구조화된 질의어(Structured Query Language)의 줄임말인 SQL은 데이터베이스의 공통어이며 모든 데이터 과학자가 배워야 할 중요한 언어입니다.

그렇기는 하지만(That said), SQL로 시작하지 않고 대신 dplyr 코드를 SQL로 변환할 수 있는 dbplyr를 알려드리겠습니다.

이것을 SQL의 중요한 기능 중 일부를 가르치기 위한 방법으로 사용할 것입니다. 이 장이 끝날 때까지(by the end of the chapter) 여러분이 SQL 마스터가 되지는 않겠지만 중요한 구성 요소(components)를 식별하고 그것들이 무엇을 하는지 이해할 수 있을 것입니다.

#| label: setup
#| message: false
library(DBI)
library(dbplyr)
library(tidyverse)

간단한 수준에서 데이터베이스는 데이터베이스 용어(terminology)로 테이블(tables)이라고 하는 데이터 프레임의 모음(collection)이라고 생각할 수 있습니다.

데이터 프레임과 마찬가지로 데이터베이스 테이블은 열의 모든 값이 동일한 유형(type)인 명명된(named) 열의 모음입니다.

데이터 프레임과 데이터베이스 테이블 간에는 세 가지 높은 수준의(high level) 차이점이 있습니다.

  1. 데이터베이스 테이블은 디스크에 저장되며 임의로(arbitrarily) 클 수 있습니다. 데이터 프레임은 메모리에 저장되며 근본적으로(fundamentally) 제한이 있습니다(비록 그 한계가 여전히 많은 문제에 대해 충분히 크긴 하지만).

  2. 데이터베이스 테이블에는 거의 항상 인덱스(indexes)가 있습니다. 책의 인덱스와 마찬가지로(Much like) 데이터베이스 인덱스를 사용하면 모든 행을 일일이 살펴보지 않고도 관심 있는(of interest) 행을 빠르게 찾을 수 있습니다. 데이터 프레임과 티블(tibbles)에는 인덱스가 없지만 data.table에는 있으며, 이것이 속도가 빠른 이유 중 하나입니다.

  3. 대부분의 고전적인(classical) 데이터베이스는 기존 데이터를 분석하는 것이 아니라 데이터를 빠르게 수집(collecting)하는 데 최적화되어(optimized) 있습니다. 이러한 데이터베이스는 데이터가 R과 같이 열 단위(column-by-column)가 아닌 행 단위(row-by-row)로 저장되기 때문에 행 지향형(row-oriented)이라고 합니다. 최근에는 기존 데이터 분석을 훨씬 더 빠르게 해주는 열 지향형(column-oriented) 데이터베이스의 개발이 활발해지고(much development of) 있습니다.

데이터베이스는 데이터베이스 관리 시스템(간단히 DBMS)에 의해 운영되며(run by) 세 가지 기본 형태로 제공됩니다.

  1. 클라이언트-서버(Client-server) DBMS는 컴퓨터(클라이언트)에서 연결(connect to)하는 강력한(powerful) 중앙 서버에서 실행됩니다. 조직 내 여러 사람과 데이터를 공유하는 데 유용합니다(great for). 널리 사용되는 클라이언트-서버 DBMS로는 PostgreSQL, MariaDB, SQL Server 및 Oracle이 있습니다.

  2. Snowflake, Amazon의 RedShift, Google의 BigQuery와 같은 클라우드(Cloud) DBMS는 클라이언트-서버 DBMS와 유사하지만 클라우드에서 실행됩니다. 즉, 매우(extremely) 큰 데이터셋을 쉽게 처리할 수 있으며 필요에 따라 더 많은 컴퓨팅 리소스를 자동으로 제공할 수 있습니다.

  3. SQLite 또는 duckdb와 같은 인-프로세스(In-process) DBMS는 전적으로 여러분의 컴퓨터에서 실행됩니다. 여러분이 기본(primary) 사용자인 큰 데이터셋으로 작업하는 데 유용합니다.

4.1 데이터베이스에 연결하기

R에서 데이터베이스에 연결하려면 다음과 같은 패키지 쌍(pair of packages)을 사용합니다.

  1. 항상 DBI(database interface)를 사용하게 될 것입니다. 데이터베이스에 연결, 데이터 업로드, SQL 쿼리 실행 등을 수행하는 일반적인(generic) 함수 세트를 제공하기 때문입니다.

  2. 연결하려는 DBMS에 맞게 조정된(tailored for) 패키지도 사용하게 됩니다. 이 패키지는 일반적인 DBI 명령을 주어진 DBMS에 필요한 세부 사항(specifics)으로 변환(translates)합니다. 일반적으로 각 DBMS마다 하나의 패키지가 있습니다. 예: PostgreSQL용 RPostgres 및 MySQL용 RMariaDB.

DBMS에 맞는 특정 패키지를 찾을 수 없는 경우 일반적으로 odbc 패키지를 대신 사용할 수 있습니다. 이것은 많은 DBMS에서 지원하는 ODBC 프로토콜을 사용합니다. odbc는 ODBC 드라이버도 설치하고 odbc 패키지에 찾을 위치를 알려주어야 하므로 약간의 추가 설정(setup)이 필요합니다.

구체적으로(Concretely), DBI::dbConnect()를 사용하여 데이터베이스 연결을 생성합니다. 첫 번째 인수는 DBMS를 선택한 다음, 두 번째 및 후속(subsequent) 인수는 연결 방법(즉, DBMS가 있는 위치 및 액세스하는 데 필요한 자격 증명(credentials))을 설명합니다. 다음 코드는 일반적인(typical) 예시 두 가지를 보여줍니다.

#| eval: false
con <- DBI::dbConnect(
  RMariaDB::MariaDB(), 
  username = "foo"
)
con <- DBI::dbConnect(
  RPostgres::Postgres(), 
  hostname = "databases.mycompany.com", 
  port = 1234
)

연결에 대한 정확한(precise) 세부 사항(details)은 DBMS마다 많이 다르므로 아쉽게도(unfortunately) 여기에서 모든 세부 사항을 다룰(cover) 수는 없습니다. 즉(This means), 스스로(on your own) 약간의 조사를 해야 합니다.

일반적으로 팀의 다른 데이터 과학자에게 물어보거나 DBA(database administrator, 데이터베이스 관리자)에게 문의할 수 있습니다. 초기 설정은 제대로 하려면 약간의 만지작거림(fiddling) (그리고 아마도 약간의 구글링)이 필요할 때가 많지만(often), 일반적으로 한 번만 수행하면 됩니다.

클라이언트-서버 또는 클라우드 DBMS를 설정하는 것은 이 책에서 번거로운 일(a pain)이므로 대신 R 패키지에 완전히 상주하는 인-프로세스 DBMS인 duckdb를 사용할 것입니다.

DBI의 마법(magic) 덕분에 duckdb를 사용하는 것과 다른 DBMS를 사용하는 것의 유일한 차이점은 데이터베이스에 연결하는 방법뿐입니다. 이 코드를 쉽게 실행할 수 있고(as well as easily) 배운 내용을 쉽게 가져와(take) 다른 곳에 적용(apply)할 수 있기 때문에 교육용으로 사용하기에 좋습니다.

duckdb에 연결하는 것은 특별히(particularly) 간단합니다. 기본값(defaults)으로 R을 종료할 때 삭제되는 임시(temporary) 데이터베이스가 생성되기 때문입니다. R을 다시 시작할 때마다 백지상태(clean slate)에서 시작할 수 있도록 보장(guarantees)하기 때문에 학습에 좋습니다.

con <- DBI::dbConnect(duckdb::duckdb())

duckdb는 데이터 과학자의 요구에 매우(very much) 부합하도록 설계된 고성능(high-performance) 데이터베이스입니다. 여기서 사용하는 이유는 시작하기 매우 쉽고 기가바이트 단위의 데이터를 엄청난 속도로(with great speed) 처리(handling)할 수 있기 때문입니다.

실제(real) 데이터 분석 프로젝트에서 duckdb를 사용하려면 영구적인(persistent) 데이터베이스를 만들고 duckdb에 저장할 위치를 알려주기 위해 dbdir 인수를 제공(supply)해야 합니다. 프로젝트를 사용하고 있다고 가정(Assuming)하면, 현재 프로젝트의 duckdb 디렉터리에 저장하는 것이 합리적(reasonable)입니다.

#| eval: false
con <- DBI::dbConnect(duckdb::duckdb(), dbdir = "duckdb")

4.1.1 일부 데이터 로드하기

이것은 새 데이터베이스이므로 일부 데이터를 추가하는 것부터 시작해야 합니다. 여기서는 DBI::dbWriteTable()을 사용하여 ggplot2의 mpg와 diamonds 데이터셋을 추가하겠습니다. dbWriteTable()의 간단한 용법(usage)에는 데이터베이스 연결, 데이터베이스에 만들 테이블 이름, 데이터 프레임 형식의 데이터 등 세 가지 인수가 필요합니다.

dbWriteTable(con, "mpg", ggplot2::mpg)
dbWriteTable(con, "diamonds", ggplot2::diamonds)

실제 프로젝트에서 duckdb를 사용하는 경우 duckdb_read_csv() 및 duckdb_register_arrow()에 대해 알아보는(learning about) 것을 적극(highly) 권장합니다. 이들은 먼저 데이터를 R에 로드할 필요 없이 duckdb로 직접 데이터를 빠르게 로드하는 강력하고(powerful) 고성능의(performant) 방법을 제공합니다. 여러 파일을 데이터베이스에 로드하는 유용한(useful) 기법(technique)도 소개(show off)하겠습니다.

4.1.2 DBI 기본

몇 가지 다른 DBI 함수를 사용하여 데이터가 올바르게 로드되었는지 확인할 수 있습니다. dbListTables()는 데이터베이스의 모든 테이블을 나열하고 dbReadTable()은 테이블의 내용(contents)을 검색(retrieves)합니다.

dbListTables(con)

con |> 
  dbReadTable("diamonds") |> 
  as_tibble()

dbReadTable()은 data.frame을 반환(returns)하므로, 멋지게 출력되도록 as_tibble()을 사용하여 티블로 변환합니다.

SQL을 이미 알고 있다면 dbGetQuery()를 사용하여 데이터베이스에서 쿼리를 실행한 결과를 얻을(get) 수 있습니다.

sql <- "
  SELECT carat, cut, clarity, color, price 
  FROM diamonds 
  WHERE price > 15000
"
as_tibble(dbGetQuery(con, sql))

SQL을 이전에 한 번도 본 적이 없더라도 걱정하지(worry) 마세요! 곧(shortly) 이에 대해 자세히 알아볼 것입니다. 하지만 주의 깊게(carefully) 읽어보면(read) diamonds 데이터셋의 5개 열과 price가 15,000보다 큰 모든 행을 선택(selects)한다는 것을 추측(guess)할 수 있습니다.

4.2 dbplyr 기초

이제 데이터베이스에 연결하고 일부 데이터를 로드했으므로 dbplyr에 대해 알아볼(learn about) 수 있습니다. dbplyr는 dplyr 백엔드(backend)인데, 이는 여러분이 계속해서 dplyr 코드를 작성하지만 백엔드가 코드를 다르게(differently) 실행(executes)한다는 것을 의미합니다.

이 경우, dbplyr는 SQL로 변환(translates)합니다. 다른 백엔드로는 data.table(https://r-datatable.com)로 변환하는 dtplyr(https://dtplyr.tidyverse.org)와 여러 코어(multiple cores)에서 코드를 실행하는 multidplyr(https://multidplyr.tidyverse.org)가 있습니다.

dbplyr를 사용하려면 먼저 tbl()을 사용하여 데이터베이스 테이블을 나타내는(represents) 개체(object)를 생성해야 합니다.

diamonds_db <- tbl(con, "diamonds")
diamonds_db

이 객체는 게으른(lazy) 상태입니다. 이 객체에 dplyr 동사(verbs)를 사용해도 dplyr은 아무 작업도 수행하지(do any work) 않습니다. 수행하려는 작업(operations)의 시퀀스(sequence)만 기록(records)하고 필요할 때만 작업을 수행합니다. 예를 들어 다음 파이프라인(pipeline)을 살펴봅시다(take):

big_diamonds_db <- diamonds_db |> 
  filter(price > 15000) |> 
  select(carat:clarity, price)

big_diamonds_db

이 객체가 상단에 DBMS 이름을 출력하기 때문에(because) 데이터베이스 쿼리를 나타낸다는 것을 알(tell) 수 있으며, 열의 수를 알려주지만 일반적으로(typically) 행의 수는 모릅니다. 총 행 수를 찾으려면 일반적으로 완전한(complete) 쿼리를 실행해야 하는데 이는 피하고(avoid) 싶은 부분이기 때문입니다.

dplyr 함수 show_query()에 의해 생성된 SQL 코드를 볼 수 있습니다. dplyr를 안다면 이것은 SQL을 배우는 아주 좋은 방법입니다! dplyr 코드를 작성하고 dbplyr를 사용하여 SQL로 변환한 다음 두 언어가 어떻게 매치(match up)되는지 알아내려고(figure out) 해보세요.

big_diamonds_db |>
  show_query()

모든 데이터를 다시 R로 가져오려면(get back) collect()를 호출(call)합니다. 백그라운드에서(Behind the scenes) 이것은 SQL을 생성하고 dbGetQuery()를 호출하여 데이터를 가져온(get) 다음 결과를 티블로 변환합니다(turns).

big_diamonds <- big_diamonds_db |> 
  collect()
big_diamonds

일반적으로 dbplyr를 사용하여 아래에 설명된 변환을 사용하여 데이터베이스에서 원하는 데이터를 선택하고, 기본적인 필터링(filtering) 및 집계(aggregation)를 수행하게 됩니다. 그런 다음 R 고유의(unique to) 함수로 데이터를 분석(analyse)할 준비가 되면 데이터를 collect()하여 인메모리(in-memory) 티블을 얻고 순수(pure) R 코드로 작업을 계속할(continue) 수 있습니다.

다행히(Luckily) dplyr을 이해한다면 너무 많은 개념(concepts)이 동일하므로(are the same) SQL을 빠르게 배울 수 있는(pick up) 훌륭한(great) 출발점(place)에 있는 것입니다.

flights <- tbl(con, "flights")

4.3.1 SQL 기초

SQL의 최상위(top-level) 구성 요소는 명령문(statements)이라고 합니다. 일반적인(Common) 명령문에는 새 테이블을 정의하는 CREATE, 데이터를 추가하는 INSERT, 데이터를 검색(retrieving)하는 SELECT가 있습니다. 데이터 과학자로서 거의 배타적으로(exclusively) 사용하게 될 명령문인 쿼리(queries)라고도 하는 SELECT 명령문에 중점(focus)을 둘 것입니다.

쿼리는 절(clauses)로 구성(made up of)됩니다. 중요한 절은 SELECT, FROM, WHERE, ORDER BY, GROUP BY 등 5가지입니다. 모든 쿼리에는 SELECT 및 FROM 절이 있어야 하며 지정된(specified) 테이블에서 모든 열을 선택하는 SELECT * FROM table이 간단한 쿼리입니다. 이것은 dbplyr가 순수한(unadulterated) 테이블에 대해 생성하는 것입니다.

혼란스럽게도(Confusingly) 문맥(context)에 따라 SELECT는 명령문이거나 절입니다. 이러한 혼란을 피하기(avoid) 위해 이 책에서는 일반적으로(generally) SELECT 명령문 대신 SELECT 쿼리를 사용합니다.

엄밀히(technically) 말하면 기본적인 계산(calculations)을 수행하기 위해 SELECT 1+1과 같은 쿼리를 작성할 수 있으므로 SELECT만 필수적(required)입니다. 하지만 (항상 그렇듯이) 데이터로 작업(work with data)하려면 FROM 절도 필요합니다.

flights |> show_query()
planes |> show_query()

WHERE와 ORDER BY는 어떤 행이 포함될지, 그리고 그 행들이 어떻게 정렬(ordered)될지 제어(control)합니다.

flights |> 
  filter(dest == "IAH") |> 
  arrange(dep_delay) |>
  show_query()

GROUP BY는 쿼리를 요약(summary)으로 변환(converts)하여 집계(aggregation)가 발생하게(happen) 합니다.

flights |> 
  group_by(dest) |> 
  summarize(dep_delay = mean(dep_delay, na.rm = TRUE)) |> 
  show_query()

dplyr 동사와 SELECT 절 사이에는 두 가지 중요한 차이점(differences)이 있습니다.

  1. SQL에서는 대소문자(case)가 중요하지(matter) 않습니다. select, SELECT 또는 SeLeCt로 작성(write)할 수 있습니다. 이 책에서는 SQL 키워드를 테이블이나 변수 이름과 구별(distinguish)하기 위해 대문자(uppercase)로 작성하는 일반적인 관례(convention)를 고수(stick with)할 것입니다.

  2. SQL에서는 순서가 중요합니다. 절은 항상 SELECT, FROM, WHERE, GROUP BY, ORDER BY 순서로 작성해야 합니다. 혼란스럽게도 이 순서는 절이 실제로 평가(evaluated)되는 방식과 일치(match)하지 않는데, FROM, WHERE, GROUP BY, SELECT, ORDER BY 순서로 평가됩니다.

4.3.1.1 SELECT

SELECT 절은 쿼리의 핵심 요소(workhorse)이며 select(), mutate(), rename(), relocate()와 같은 작업을 수행(performs)하고, 다음 섹션에서 배울(learn) summarize()와 같은 역할(job)도 수행합니다.

select(), rename(), relocate()는 열이 표시(appears)되는 위치(있는 경우)와 열 이름에만 영향을 미치므로(affect) SELECT로 매우 직접적으로 변환(direct translations)됩니다.

planes |> 
  select(tailnum, type, manufacturer, model, year) |> 
  show_query()

planes |> 
  select(tailnum, type, manufacturer, model, year) |> 
  rename(year_built = year) |> 
  show_query()

planes |> 
  select(tailnum, type, manufacturer, model, year) |> 
  relocate(manufacturer, model, .before = type) |> 
  show_query()

이 예제(example)는 SQL이 이름 바꾸기(renaming)를 수행하는 방법도 보여줍니다. SQL 용어로 이름 바꾸기를 별칭(aliasing)이라고 하며 AS를 사용하여 수행(done)됩니다. mutate()와 달리(unlike) 이전(old) 이름은 왼쪽에 있고 새 이름은 오른쪽에 있다는 점에 유의하세요.

mutate()에 대한 변환은 비슷하게 간단합니다(straightforward). 각 변수는 SELECT에서 새로운 표현식(expression)이 됩니다.

flights |> 
  mutate(
    speed = distance / (air_time / 60)
  ) |> 
  show_query()

개별(individual) 구성 요소(/와 같은)의 변환에 대해서는 ?@sec-sql-expressions에서 다시 설명하겠습니다(come back to).

4.3.1.2 FROM

FROM 절은 데이터 소스를 정의합니다.단일 테이블만 사용하기 때문에 당분간(for a little while)은 다소 흥미롭지 않을(uninteresting) 것입니다. 조인 함수에 도달(hit)하면 더 복잡한 예제를 볼 수 있습니다.

4.3.1.3 GROUP BY

group_by()는 GROUP BY 절로 변환되고 summarize()는 SELECT 절로 변환됩니다.

diamonds_db |> 
  group_by(cut) |> 
  summarize(
    n = n(),
    avg_price = mean(price, na.rm = TRUE)
  ) |> 
  show_query()

n()과 mean()의 변환에 무슨 일이 일어나는지 다시 설명(come back to)하겠습니다.

4.3.1.4 WHERE

filter()는 WHERE 절로 변환됩니다.

flights |> 
  filter(dest == "IAH" | dest == "HOU") |> 
  show_query()

flights |> 
  filter(arr_delay > 0 & arr_delay < 20) |> 
  show_query()

여기서 유의해야 할 몇 가지 중요한 세부 사항(details)이 있습니다.

  1. |는 OR이 되고 &는 AND가 됩니다.
  2. SQL은 비교(comparison)를 위해 ==가 아닌 =를 사용합니다. SQL에는 할당(assignment)이 없으므로 혼란이 생길 가능성(potential for confusion)이 없습니다.
  3. SQL은 문자열(strings)에 ""가 아닌 ''만 사용합니다. SQL에서 ""는 R의 backticks 처럼 변수를 식별(identify)하는 데 사용됩니다.

또 다른 유용한 SQL 연산자는 IN으로, R의 %in%과 매우 유사(close)합니다.

flights |> 
  filter(dest %in% c("IAH", "HOU")) |> 
  show_query()

SQL은 NA 대신 NULL을 사용합니다. NULL은 NA와 비슷하게 동작(behave)합니다. 큰(main) 차이점은 비교 및 산술(arithmetic)에서 “전염성(infectious)”이 있지만 요약할(summarizing) 때는 조용히(silently) 삭제(dropped)된다는 것입니다. dbplyr는 여러분이 이 동작에 처음 부딪혔을(hit) 때 이 동작에 대해 상기시켜(remind) 줄 것입니다.

flights |> 
  group_by(dest) |> 
  summarize(delay = mean(arr_delay))

NULL이 어떻게 작동(work)하는지 더 알고 싶으시다면 Markus Winand의 “The Three-Valued Logic of SQL”을 읽어보시면 좋을 것입니다(enjoy).

일반적으로(In general), R에서 NA에 사용하는 함수를 사용하여 NULL로 작업(work with)할 수 있습니다.

flights |> 
  filter(!is.na(dep_delay)) |> 
  show_query()

이 SQL 쿼리는 dbplyr의 단점(drawbacks) 중 하나를 보여줍니다(illustrates). SQL은 정확(correct)하지만 손으로 작성(write by hand)할 수 있을 만큼 간단하지는(simple) 않다는 것입니다.

이 경우 괄호(parentheses)를 생략(drop)하고 읽기 더 쉬운(easier to read) 특수(special) 연산자를 사용할 수 있습니다.

WHERE "dep_delay" IS NOT NULL

요약(summarize)을 사용하여 만든 변수를 filter()하는 경우, dbplyr는 WHERE 절이 아닌 HAVING 절을 생성한다는 점에 유의(Note)하세요. 이것은 SQL의 특이한 점(idiosyncrasies) 중 하나입니다. WHERE는 SELECT 및 GROUP BY 전에 평가(evaluated)되므로, SQL은 나중에(afterwards) 평가될 다른 절이 필요합니다.

diamonds_db |> 
  group_by(cut) |> 
  summarize(n = n()) |> 
  filter(n > 100) |> 
  show_query()
4.3.1.5 ORDER BY

행 정렬(ordering rows)에는 arrange()에서 ORDER BY 절로의 간단한(straightforward) 변환이 포함(involves)됩니다.

flights |> 
  arrange(year, month, day, desc(dep_delay)) |> 
  show_query()

desc()가 DESC로 어떻게 변환되는지 주목하세요(Notice). 이 함수는 이름이 SQL에서 직접 영감을 받은(directly inspired by) 많은 dplyr 함수 중 하나입니다.

4.3.1.6 서브쿼리

때로는(Sometimes) dplyr 파이프라인(pipeline)을 단일 SELECT 명령문으로 변환할 수 없어서 서브쿼리를 사용해야 하는 경우가 있습니다. 서브쿼리(subquery)는 일반적인 테이블 대신 FROM 절에서 데이터 소스로 사용되는 쿼리일 뿐입니다.

dbplyr는 일반적으로 SQL의 한계(limitations)를 해결하기(work around) 위해 서브쿼리를 사용합니다. 예를 들어 SELECT 절의 표현식(expressions)은 방금 생성된(just created) 열을 참조할(refer to) 수 없습니다. 즉, 다음의 (어리석은) dplyr 파이프라인은 두 단계로 수행되어야 합니다. 첫 번째(내부) 쿼리는 year1을 계산(computes)하고 그런 다음 두 번째(외부) 쿼리는 year2를 계산할 수 있습니다.

flights |> 
  mutate(
    year1 = year + 1,
    year2 = year1 + 1
  ) |> 
  show_query()

방금 생성한 변수를 filter()하려고 시도한(attempted) 경우에도 이것을 볼 수 있습니다. WHERE는 SELECT 이후에 작성되지만 그 전에 평가되므로 이 (어리석은) 예제에서는 서브쿼리가 필요합니다(Remember).

flights |> 
  mutate(year1 = year + 1) |> 
  filter(year1 == 2014) |> 
  show_query()

때로는 dbplyr가 해당 변환을 최적화(optimize)하는 방법을 아직 모르기 때문에 필요하지 않은 곳에(where it’s not needed) 서브쿼리를 생성(create)하기도 합니다. 시간이 지나면서(over time) dbplyr가 개선(improves)됨에 따라 이러한 경우는 드물어지겠지만(get rarer) 아마 완전히 없어지지는(never go away) 않을 것입니다.

4.3.1.7 조인

dplyr의 조인에 익숙하다면 SQL 조인도 매우 유사합니다. 다음은 간단한 예시입니다.

flights |> 
  left_join(planes |> rename(year_built = year), join_by(tailnum)) |> 
  show_query()

여기서 주목해야 할 주요(main) 사항은 구문(syntax)입니다. SQL 조인은 FROM 절의 하위 절(sub-clauses)을 사용하여 추가 테이블을 가져오고 ON을 사용하여 테이블 간의 관계(related)를 정의합니다.

이러한 함수에 대한 dplyr의 이름은 SQL과 매우 밀접하게 연결되어(closely connected) 있으므로 inner_join(), right_join() 및 full_join()에 해당하는 SQL을 쉽게 추측(guess)할 수 있습니다.

SELECT flights.*, "type", manufacturer, model, engines, seats, speed
FROM flights
INNER JOIN planes ON (flights.tailnum = planes.tailnum)

SELECT flights.*, "type", manufacturer, model, engines, seats, speed
FROM flights
RIGHT JOIN planes ON (flights.tailnum = planes.tailnum)

SELECT flights.*, "type", manufacturer, model, engines, seats, speed
FROM flights
FULL JOIN planes ON (flights.tailnum = planes.tailnum)

데이터베이스의 데이터로 작업할 때 조인을 많이 사용하게 될 가능성이 높습니다. 데이터베이스 테이블은 각 “사실(fact)”이 한 곳에 저장되고, 분석을 위한 완전한(complete) 데이터셋을 유지(keep)하기 위해 기본 키(primary keys)와 외래 키(foreign keys)로 연결된(connected by) 복잡한 테이블 네트워크(complex network of tables)를 탐색(navigate)해야 하는 매우 정규화된 형태(highly normalized form)로 저장되는 경우가 많기 때문입니다.

이러한 상황에 부닥친다면(hit this scenario), Tobias Schieferdecker, Kirill Müller, Darko Bergant가 만든 dm 패키지가 구세주(life saver)가 될 것입니다.

이 패키지는 DBA가 종종 제공하는 제약 조건(constraints)을 사용하여 테이블 간의 연결을 자동으로 결정(determine)하고, 무슨 일이 일어나고 있는지 볼 수 있도록 연결을 시각화(visualize)하며, 한 테이블을 다른 테이블에 연결하는 데 필요한 조인을 생성(generate)할 수 있습니다.

4.5 함수 변환

지금까지 우리는 dplyr 동사가 쿼리의 절(clauses)로 변환되는 과정의 큰 그림(big picture)에 초점을 맞췄습니다.

이제 조금 더 자세히 살펴보고(zoom in a little) 개별 열(individual columns)에서 작동하는 R 함수의 변환에 대해 이야기해 보겠습니다. 예: summarize()에서 mean(x)를 사용하면 어떻게 됩니까?

무슨 일이 일어나는지(what’s going on) 확인하는 데 도움이 되도록 summarize() 또는 mutate()를 실행하고 생성된 SQL을 보여주는 몇 가지 작은 도우미(helper) 함수를 사용하겠습니다.

이렇게 하면 몇 가지 변형(variations)을 탐구(explore)하고 요약(summaries)과 변형(transformations)이 어떻게 다를(differ) 수 있는지 조금 더 쉽게 볼 수 있습니다.

summarize_query <- function(df, ...) {
  df |> 
    summarize(...) |> 
    show_query()
}
mutate_query <- function(df, ...) {
  df |> 
    mutate(..., .keep = "none") |> 
    show_query()
}

몇 가지 요약으로 뛰어들어(dive in) 봅시다! 아래 코드를 보면 mean()과 같은 일부 요약 함수는 비교적(relatively) 간단한(simple) 변환을 갖는 반면 median()과 같은 다른 함수는 훨씬 더 복잡하다는(complex) 것을 알 수 있습니다.

통계(statistics)에서는 일반적(common)이지만 데이터베이스에서는 덜 일반적인 연산일수록 일반적으로 복잡성이 더 높습니다(higher).

flights |> 
  group_by(year, month, day) |>  
  summarize_query(
    mean = mean(arr_delay, na.rm = TRUE),
    median = median(arr_delay, na.rm = TRUE)
  )

요약 함수를 mutate() 내부에서 사용하면 소위(so-called) 윈도우(window) 함수로 전환되어야 하기 때문에 요약 함수의 변환이 더 복잡(complicated)해집니다. SQL에서는 그 뒤에 OVER를 추가하여 일반(ordinary) 집계 함수를 윈도우 함수로 전환(turn)합니다.

flights |> 
  group_by(year, month, day) |>  
  mutate_query(
    mean = mean(arr_delay, na.rm = TRUE),
  )

SQL에서 GROUP BY 절은 요약 전용(exclusively for summaries)으로 사용되므로 여기서는 그룹화(grouping)가 GROUP BY 절에서 OVER로 이동(moved)한 것을 볼 수 있습니다.

윈도우 함수에는 각각 “이전(previous)” 또는 “다음(next)” 값을 보는(look at) lead() 및 lag()와 같이 앞을 내다보거나(look forward) 뒤를 돌아보는(look backwards) 모든 함수가 포함(include)됩니다.

flights |> 
  group_by(dest) |>  
  arrange(time_hour) |> 
  mutate_query(
    lead = lead(arr_delay),
    lag = lag(arr_delay)
  )

SQL 테이블에는 내재된(intrinsic) 순서가 없기 때문에 여기서 데이터를 arrange()하는 것이 중요합니다.

사실 arrange()를 사용하지 않으면 매번 다른 순서로 행을 반환받을 수도 있습니다! 윈도우 함수의 경우 순서 정보(ordering information)가 반복된다는(repeated) 점에 유의하세요(Notice): 메인 쿼리의 ORDER BY 절이 윈도우 함수에 자동으로 적용(apply)되지는 않습니다.

또 다른 중요한 SQL 함수는 CASE WHEN입니다. 이것은 if_else() 및 case_when()의 변환으로 사용되며, 이 함수는 dplyr 함수에 직접적인 영감을 주었습니다(directly inspired).

다음은 몇 가지 간단한 예시입니다.

flights |> 
  mutate_query(
    description = if_else(arr_delay > 0, "delayed", "on-time")
  )
flights |> 
  mutate_query(
    description = 
      case_when(
        arr_delay < -5 ~ "early", 
        arr_delay < 5 ~ "on-time",
        arr_delay >= 5 ~ "late"
      )
  )

CASE WHEN은 R에서 SQL로 직접 변환(direct translation)되지 않는 다른 일부 함수에도 사용됩니다. 이것의 좋은 예시가 cut()입니다.

flights |> 
  mutate_query(
    description =  cut(
      arr_delay, 
      breaks = c(-Inf, -5, 5, Inf), 
      labels = c("early", "on-time", "late")
    )
  )

dbplyr는 또한 일반적인 문자열 및 날짜-시간 조작(manipulation) 함수도 변환하는데, 이는 vignette("translation-function", package = "dbplyr")에서 배울 수 있습니다.

dbplyr의 변환이 확실히 완벽한 것은 아니며 아직 변환되지 않은 R 함수도 많지만, dbplyr는 여러분이 대부분의(most of the time) 시간에 사용할 함수를 놀라울 정도로 잘 다루어(covering) 냅니다(does a surprisingly good job).

5.1 스크래핑 윤리 및 합법성

웹 스크래핑을 수행하는 데 필요한 코드에 대해 논의하기 전에, 웹 스크래핑을 하는 것이 합법적이고 윤리적인지에 대해 이야기해야 합니다. 전반적으로, 이 두 가지 모두에 대해 상황은 복잡합니다.

합법성은 여러분이 어디에 살고 있는지에 따라 많이 달라집니다. 하지만 일반적인 원칙으로, 데이터가 공개적이고, 개인적인 것이 아니며, 사실적이라면 괜찮을 가능성이 높습니다.

이 세 가지 요소가 중요한 이유는 아래에서 논의할 사이트의 이용 약관, 개인 식별 정보 및 저작권과 관련이 있기 때문입니다.

분명히 우리는 변호사가 아니며 이것은 법적 조언이 아닙니다. 하지만 이것은 우리가 이 주제에 대해 많은 것을 읽고 나서 제공할 수 있는 좋은 요약입니다.

데이터가 공개적, 비개인적 또는 사실적이지 않거나, 데이터를 특별히 돈을 벌기 위해 스크랩하는 경우 변호사와 상담해야 합니다. 어떤 경우든 스크랩하려는 페이지를 호스팅하는 서버의 리소스를 존중해야 합니다. 중요한 것은 여러 페이지를 스크랩하는 경우 각 요청 사이에 약간 기다려야 한다는 점을 확실히 해야 한다는 것입니다.

이를 위한 쉬운 방법 중 하나는 Dmytro Perepolkin의 polite 패키지를 사용하는 것입니다. 이 패키지는 요청 사이에 자동으로 일시 중지하고 결과를 캐시하므로 동일한 페이지를 두 번 요청하는 일이 없습니다.

5.1.1 서비스 약관

자세히 살펴보면 많은 웹사이트가 페이지 어딘가에 “이용 약관(terms and conditions)” 또는 “서비스 약관(terms of service)” 링크를 포함하고 있으며, 해당 페이지를 자세히 읽어보면 웹사이트가 명시적으로 웹 스크래핑을 금지하고 있다는 것을 종종 발견할 수 있습니다. 이러한 페이지는 기업이 매우 광범위한 주장을 펼치는 법적인 땅따먹기인 경향이 있습니다. 가능한 경우 이러한 서비스 약관을 존중하는 것이 예의이지만, 주장은 어느 정도 걸러서 받아들여야 합니다.

미국 법원은 웹사이트의 바닥글에 서비스 약관을 게시하는 것만으로는 사용자가 구속력을 갖기에 충분하지 않다고 판단하는 경우가 많습니다(HiQ Labs v. LinkedIn(https://en.wikipedia.org/wiki/HiQ_Labs_v._LinkedIn).

일반적으로 서비스 약관에 구속되려면 계정 생성 또는 확인란 선택과 같은 명시적인 행동을 취해야 합니다. 이것이 데이터의 공개 여부가 중요한 이유입니다. 데이터에 액세스하는 데 계정이 필요하지 않다면 서비스 약관에 구속될 가능성이 낮습니다.

하지만, 유럽의 상황은 상당히 다르다는 점에 유의하세요. 법원에서는 명시적으로 동의하지 않았더라도 서비스 약관이 집행 가능하다고 판결했습니다.

5.1.2 개인 식별 정보

데이터가 공개되어 있더라도 이름, 이메일 주소, 전화번호, 생년월일 등 개인 식별 정보를 스크랩할 때는 극도로 주의해야 합니다. 유럽은 이러한 데이터의 수집이나 저장에 대해 특히 엄격한 법률(GDPR)을 가지고 있으며 거주지에 관계없이 윤리적 수렁에 빠질 가능성이 높습니다. 예를 들어 2016년에 한 연구자 그룹은 데이팅 사이트인 OkCupid에서 70,000명의 공개 프로필 정보(사용자 이름, 나이, 성별, 위치 등)를 스크랩하고 비식별화를 위한 어떠한 시도도 없이 이 데이터를 공개적으로 발표했습니다.

연구자들은 데이터가 이미 공개되어 있었기 때문에 아무 문제가 없다고 느꼈지만, 이 연구는 데이터셋에 정보가 공개된 사용자의 식별 가능성을 둘러싼 윤리적 우려로 인해 널리 비난을 받았습니다. 작업에 개인 식별 정보를 스크랩하는 내용이 포함되어 있다면, 개인 식별 정보의 획득 및 공개와 관련된 의심스러운 연구 윤리 문제가 있는 유사한 연구뿐만 아니라 OkCupid 연구[^webscraping-3]에 대해서도 읽어보는 것을 강력히 권장합니다.

OkCupid 연구에 대한 기사의 한 예는 Wired(https://www.wired.com/2016/05/okcupid-study-reveals-perils-big-data-science)에 게시되었습니다.

5.1.3 저작권

마지막으로, 저작권법에 대해서도 걱정해야 합니다. 저작권법은 복잡하지만, 정확히 보호되는 대상을 설명하는 미국법을 살펴볼 가치가 있습니다.

“… 어떤 형태의 유형적인 표현 매체에 고정된 저자의 독창적인 저작물, …”

그런 다음 어문 저작물, 음악 저작물, 영화 등과 같이 적용되는 특정 범주를 설명합니다. 데이터는 저작권 보호에서 눈에 띄게 빠져 있습니다. 이는 스크래핑을 사실에 한정하는 한 저작권 보호가 적용되지 않음을 의미합니다. (하지만 유럽에는 데이터베이스를 보호하는 별도의 “독자적(sui generis)” 권리가 있다는 점에 유의하세요.)

간단한 예로, 미국에서는 재료 및 지침 목록이 저작권의 대상이 아니므로 저작권을 사용하여 레시피를 보호할 수 없습니다. 그러나 해당 레시피 목록에 실질적이고 새로운 문학적 콘텐츠가 함께 제공되는 경우에는 저작권이 인정됩니다. 이것이 인터넷에서 레시피를 찾을 때 항상 사전에 내용이 너무 많은 이유입니다.

(텍스트나 이미지 같은) 원본 콘텐츠를 스크랩해야 하는 경우에도 여전히 공정 이용 원칙(doctrine of fair use)(https://en.wikipedia.org/wiki/Fair_use)에 따라 보호받을 수 있습니다. 공정 이용(Fair use)은 확고한 규칙은 아니지만 여러 요소를 저울질합니다. 연구나 비상업적 목적으로 데이터를 수집하고 꼭 필요한 것만 스크랩하도록 제한하는 경우에 적용될 가능성이 더 높습니다.

5.2 HTML의 기초

웹페이지를 스크랩하려면 먼저 웹페이지를 설명하는 언어인 HTML에 대해 약간(a little bit) 이해해야 합니다. HTML은 HyperText Markup Language의 약자(stands for)이며 다음과 같이 생겼습니다(looks something like this).

<html>
<head>
  <title>Page title</title>
</head>
<body>
  <h1 id='first'>A heading</h1>
  <p>Some text &amp; <b>some bold text.</b></p>
  <img src='myimg.png' width='100' height='100'>
</body>

HTML은 시작(start) 태그(tag, 예: <tag>), 선택적(optional) 속성(attributes)(id='first'), 종료(end) 태그(<tag> 등) 및 콘텐츠(contents)(시작 태그와 종료 태그 사이의 모든 항목)로 구성된(consist of) 요소(elements)로 형성된(formed by) 계층 구조(hierarchical structure)를 가지고 있습니다.

< 및 >는 시작 태그와 종료 태그에 사용되므로 직접 작성(write them directly)할 수 없습니다. 대신 HTML 이스케이프(escapes)인 &gt;(보다 큼, greater than) 및 &lt;(보다 작음, less than)을 사용해야(have to use) 합니다.

그리고 이러한 이스케이프는 &를 사용하므로 리터럴(literal) 앰퍼샌드(ampersand)가 필요한 경우 &amp;로 이스케이프해야 합니다. 가능한(possible) HTML 이스케이프는 매우 다양하지만(wide range of), rvest가 자동으로(automatically) 처리(handles)해 주기 때문에 너무 많이 걱정할 필요는 없습니다.

스크랩하려는 데이터가 포함된 대부분의 페이지는 일반적으로 일관된(consistent) 구조를 가지고 있기 때문에 웹 스크래핑이 가능합니다.

5.2.1 요소

100개가 넘는(over) HTML 요소가 있습니다. 중요한 몇 가지는 다음과 같습니다.

  1. 모든 HTML 페이지는 <html> 요소 안에 있어야(must be in) 하며 두 개의 자식(children)이 있어야(must have) 합니다. 페이지 제목과 같은 문서 메타데이터(document metadata)를 포함하는 <head>와 브라우저(browser)에 표시되는 콘텐츠(content you see)를 포함하는 <body>입니다.

  2. <h1>(제목 1, heading 1), <section>(섹션, section), <p>(단락, paragraph), <ol>(순서가 있는 리스트, ordered list)과 같은 블록(Block) 태그는 페이지의 전체적인(overall) 구조를 형성(form)합니다.

  3. <b>(굵게, bold), <i>(기울임꼴, italics), <a>(링크, link)와 같은 인라인(Inline) 태그는 블록 태그 안의 텍스트 형식을 지정(format text)합니다.

이전에 본 적 없는 태그를 만나면(encounter) 약간의 구글링(googling)으로 태그의 기능(what it does)을 찾을(find out) 수 있습니다. 웹 프로그래밍의 거의(just about) 모든(every) 측면(aspect)을 설명(describe)하는 MDN Web Docs도 시작하기에 좋은(good place) 곳입니다.

대부분의 요소는 시작 태그와 종료 태그 사이에 콘텐츠를 가질 수 있습니다. 이 콘텐츠는 텍스트일 수도 있고(either) 더 많은 요소일 수도 있습니다. 예를 들어, 다음 HTML에는 한 단어가 굵게(bold) 표시된 텍스트 단락(paragraph)이 포함되어 있습니다.

<p>
  Hi! My <b>name</b> is Hadley.
</p>

자식(children)은 포함하고 있는 요소이므로 위의 <p> 요소에는 하나의 자식인 <b> 요소가 있습니다. <b> 요소에는 자식이 없지만 내용은 있습니다(text “name”).

5.2.2 속성

태그에는 name1='value1' name2='value2'와 같은 명명된 속성(attributes)이 있을 수(can have) 있습니다. 중요한 두 가지 속성은 id와 class이며 CSS(Cascading Style Sheets)와 함께(in conjunction with) 사용하여 페이지의 시각적 외관(visual appearance)을 제어(control)합니다.

이들은(These are) 페이지에서 데이터를 스크랩할 때 종종(often) 유용(useful)합니다. 속성은 링크 대상(<a> 요소의 href 속성)과 이미지 소스(<img> 요소의 src 속성)를 기록(record)하는 데에도(also) 사용됩니다.

5.3 데이터 추출

스크래핑을 시작(get started)하려면 스크랩할 페이지의 URL이 필요(need)하며, 일반적으로 웹 브라우저에서 복사(copy)할 수 있습니다. 그런 다음 read_html()을 사용하여 해당 페이지의 HTML을 R로 읽어야(read) 합니다. 이 함수는 xml_document 객체를 반환(returns)하며 이후(then) rvest 함수를 사용하여 이 객체를 조작(manipulate)합니다.

html <- read_html("http://rvest.tidyverse.org/")
html

rvest에는 HTML을 인라인(inline)으로 작성할 수 있는(lets you write) 함수도 포함되어(includes) 있습니다. 이 장에서는 다양한 rvest 함수가 어떻게 작동하는지 간단한 예제로 설명(teach)할 때 이 함수를 많이(a bunch) 사용할 것입니다.

html <- minimal_html("
  <p>This is a paragraph</p>
  <ul>
    <li>This is a bulleted list</li>
  </ul>
")
html

이제 R에 HTML이 생겼으므로(have) 관심 있는 데이터를 추출(extract)할 차례입니다(it’s time to). 먼저 관심 있는 요소를 식별(identify)할 수 있는 CSS 선택자(selectors)와 해당 요소에서 데이터를 추출하는 데 사용할 수 있는 rvest 함수에 대해 배울 것입니다. 그런 다음 특별한 도구(special tools)가 있는 HTML 표(tables)를 간략하게(briefly) 다루겠습니다(cover).

5.3.1 요소 찾기

CSS는 cascading style sheets의 약자(short for)이며 HTML 문서의 시각적 스타일링(visual styling)을 정의(defining)하기 위한 도구(tool)입니다. CSS에는 페이지에서 요소를 선택(selecting)하기 위한 축소판(miniature) 언어가 포함되어 있으며 이를 CSS 선택자(CSS selectors)라고 합니다. CSS 선택자는 HTML 요소를 찾기(locating) 위한 패턴을 정의하며 추출하려는 요소를 간결하게 설명할(concise way of describing) 수 있기 때문에 스크래핑에 유용합니다.

CSS 선택자에 대해 더 자세히(in more detail) 다루겠지만(come back to), 다행히(luckily) 세 가지만으로도(with just three) 많은 것을 할 수 있습니다(get a long way):

  • p는 모든 <p> 요소를 선택합니다.
  • .title은 class가 “title”인 모든 요소를 선택합니다.
  • #title은 “title”과 같은(equals) id 속성을 가진 요소를 선택합니다.

Id 속성은 문서 내에서 고유(unique)해야 하므로 이는 항상 단일(single) 요소만 선택합니다(only ever select). 간단한 예시로 이러한 선택자를 시험(try out)해 봅시다.

html <- minimal_html("
  <h1>This is a heading</h1>
  <p id='first'>This is a paragraph</p>
  <p class='important'>This is an important paragraph</p>
")

선택자와 일치(match)하는 모든 요소를 찾으려면 html_elements()를 사용합니다(Use).

html |> html_elements("p")
html |> html_elements(".important")
html |> html_elements("#first")

또 다른 중요한 함수는 항상 입력과 같은 수의 출력을 반환하는 html_element()입니다. 전체 문서에 적용하면 첫 번째로 일치하는 항목(first match)을 제공합니다.

html |> html_element("p")

요소와 일치하지 않는 선택자를 사용할 때 html_element()와 html_elements() 사이에는 중요한 차이가 있습니다. html_elements()는 길이가 0인 벡터를 반환하는 반면(where), html_element()는 결측값(missing value)을 반환합니다. 이것은 곧(shortly) 중요해질 것입니다.

html |> html_elements("b")
html |> html_element("b")

5.3.2 선택자 중첩

대부분의 경우 html_elements()와 html_element()를 함께 사용하게 되며, 일반적으로 html_elements()를 사용하여 관측치(observations)가 될 요소를 식별한 다음 html_element()를 사용하여 변수(variables)가 될 요소를 찾습니다.

간단한 예제를 통해 이것이 어떻게 작동하는지(in action) 살펴봅시다. 여기 StarWars의 네 명의 캐릭터에 대한 일부 정보가 포함된 순서 없는 리스트(unordered list, <ul>)가 있으며 각 리스트 항목(<li>)이 있습니다.

html <- minimal_html("
  <ul>
    <li><b>C-3PO</b> is a <i>droid</i> that weighs <span class='weight'>167 kg</span></li>
    <li><b>R4-P17</b> is a <i>droid</i></li>
    <li><b>R2-D2</b> is a <i>droid</i> that weighs <span class='weight'>96 kg</span></li>
    <li><b>Yoda</b> weighs <span class='weight'>66 kg</span></li>
  </ul>
  ")

html_elements()를 사용하여 각 요소가 다른 캐릭터에 해당하는 벡터를 만들 수 있습니다.

characters <- html |> html_elements("li")
characters

각 캐릭터의 이름을 추출하기 위해 html_element()를 사용합니다. html_elements()의 출력에 적용할 때 각 요소당 하나의 응답을 반환하도록 보장(guaranteed)되기 때문입니다.

characters |> html_element("b")

html_element()와 html_elements()의 차이(distinction)는 이름(name)에는 중요하지 않지만 체중(weight)에는 중요합니다. 체중 <span>이 없는 경우라도(even if) 각 캐릭터마다 하나의 체중을 얻고 싶습니다(want to get). 그것이 바로 html_element()가 하는 일입니다.

characters |> html_element(".weight")

html_elements()는 characters의 자식인 모든 체중 <span>을 찾습니다. 이 중 3개밖에 없기 때문에(There’s only three of these) 이름과 체중 간의 연결(connection)이 끊어집니다(lose).

characters |> html_elements(".weight")

이제 관심 있는 요소를 선택했으므로 텍스트 콘텐츠(text contents) 또는 일부 속성(attributes)에서 데이터를 추출해야 합니다.

5.3.3 텍스트와 속성

html_text2()는 HTML 요소의 일반 텍스트(plain text) 콘텐츠를 추출합니다.

characters |> 
  html_element("b") |> 
  html_text2()

characters |> 
  html_element(".weight") |> 
  html_text2()

모든 이스케이프는 자동으로 처리됩니다. rvest가 반환하는 데이터가 아닌 원본(source) HTML에서만 HTML 이스케이프를 볼 수 있습니다.

html_attr()은 속성에서 데이터를 추출합니다.

html <- minimal_html("
  <p><a href='https://en.wikipedia.org/wiki/Cat'>cats</a></p>
  <p><a href='https://en.wikipedia.org/wiki/Dog'>dogs</a></p>
")

html |> 
  html_elements("p") |> 
  html_element("a") |> 
  html_attr("href")

html_attr()은 항상 문자열을 반환하므로 숫자나 날짜를 추출하는 경우 약간의 후처리(post-processing)를 수행해야 합니다.

5.3.4 표 (Tables)

운이 좋다면(If you’re lucky) 데이터가 이미 HTML 표(table)에 저장되어 있어서 해당 표에서 읽어오기만(just reading it) 하면 될 것입니다. 일반적으로 브라우저에서 표를 인식(recognize)하는 것은 간단(straightforward)합니다. 행과 열의 직사각형 구조를 가지고 있으며 Excel과 같은 도구에 복사(copy)하여 붙여넣을(paste) 수 있습니다.

HTML 표는 주로 4가지 요소(main elements)로 구성(built up from)됩니다. <table>, <tr>(표 행, table row), <th>(표 제목, table heading), <td>(표 데이터, table data). 다음은 2열 3행으로 구성된 간단한 HTML 표입니다.

html <- minimal_html("
  <table class='mytable'>
    <tr><th>x</th>   <th>y</th></tr>
    <tr><td>1.5</td> <td>2.7</td></tr>
    <tr><td>4.9</td> <td>1.3</td></tr>
    <tr><td>7.2</td> <td>8.1</td></tr>
  </table>
  ")

rvest는 이러한 종류의 데이터를 읽을 수 있는(knows how to read) html_table()이라는 함수를 제공합니다. 이 함수는 페이지에서 발견된 각 표에 대해 하나의 티블(tibble)을 포함하는 리스트를 반환합니다. 추출하려는 표를 식별하려면 html_element()를 사용하세요.

html |> 
  html_element(".mytable") |> 
  html_table()

x와 y가 자동으로 숫자로 변환된 것에 유의하세요(Note that). 이 자동 변환은 항상 작동하는 것은 아니므로(doesn’t always work) 더 복잡한 시나리오에서는 convert = FALSE로 끄고 자체적으로 변환(your own conversion)을 수행(do)하는 것이 좋습니다.

5.3.5 올바른 선택자 찾기

데이터에 필요한 선택자를 파악하는 것(Figuring out)은 일반적으로 이 문제(problem)에서 어려운(hardest) 부분입니다. 특정하고(specific, 즉 관심 없는 항목은 선택하지 않음) 민감한(sensitive, 즉 관심 있는 모든 항목을 선택함) 선택자를 찾기 위해 약간의 실험(experimenting)을 해야 하는(need to do) 경우가 많습니다.

많은 시행착오(trial and error)는 과정의 정상적인(normal) 부분입니다! 이 과정에 도움이 되는 두 가지 주요 도구가 있습니다. SelectorGadget과 브라우저의 개발자 도구(developer tools)입니다.

SelectorGadget은 제공하는 긍정적(positive) 및 부정적(negative) 예시(examples)를 기반으로 CSS 선택자를 자동으로 생성(generates)하는 자바스크립트 북마크릿(javascript bookmarklet)입니다.

항상 작동하는 것은 아니지만, 작동할 때는(when it does) 마법과도 같습니다(it’s magic)! https://rvest.tidyverse.org/articles/selectorgadget.html을 읽거나 https://www.youtube.com/watch?v=PetWV5g1Xsc에서 Mine의 비디오를 시청(watching)하여 SelectorGadget을 설치(install)하고 사용하는 방법을 배울 수 있습니다.

모든 최신(modern) 브라우저에는 개발자를 위한 툴킷(toolkit)이 제공되지만, 기본(regular) 브라우저가 아니더라도(even if) Chrome을 사용하는 것을 권장(recommend)합니다. Chrome의 웹 개발자 도구는 최고(some of the best) 수준이며 즉시(immediately) 사용할 수 있습니다(available).

페이지의 요소를 마우스 오른쪽 버튼으로 클릭(Right click)하고 Inspect(검사)를 클릭합니다. 그러면 방금 클릭한 요소를 중심(centered on)으로 전체 HTML 페이지의 확장 가능(expandable)한 뷰(view)가 열립니다.

이를 사용하여 페이지를 탐색(explore)하고 어떤 선택자가 작동할지(might work) 파악(get a sense of)할 수 있습니다.

class 및 id 속성에 특히 주의(Pay particular attention to)하세요. 이들은 종종(often) 페이지의 시각적 구조를 형성하는 데(form) 사용되므로(used to) 원하는 데이터를 추출하는 데 좋은 도구(good tools)가 될 수 있습니다.

요소(Elements) 뷰 내부에서 요소를 마우스 오른쪽 버튼으로 클릭하고 Copy as Selector(선택자로 복사)를 선택(choose)하여 관심 있는 요소를 고유하게 식별하는 선택자를 생성할 수도 있습니다(also).

SelectorGadget이나 Chrome DevTools가 이해할 수 없는(don’t understand) CSS 선택자를 생성한 경우 CSS 선택자를 쉬운 영어(plain English)로 번역(translates)해 주는 Selectors Explainedhttps://kittygiraudel.github.io/selectors-explained/를 사용해 보세요.

이 작업을 많이(a lot) 하게 된다면 CSS 선택자에 대해 전반적으로(generally) 더(more) 배우는(learn) 것이 좋습니다. 재미있는 CSS dinner(https://flukeout.github.io/) 튜토리얼(tutorial)로 시작한 다음 MDN 웹 문서(MDN web docs)https://developer.mozilla.org/en-US/docs/Web/CSS/CSS_Selectors를 참조(referring to)하는 것을 권장합니다.

5.4 종합하기

이제 이것들을 종합하여(put this all together) 몇 가지 웹사이트를 스크랩해 봅시다. 이 예제(examples)를 실행(run)할 때 더 이상 작동(work)하지 않을 위험(risk)이 약간 있습니다. 이는 웹 스크래핑의 근본적인(fundamental) 과제(challenge)입니다. 사이트의 구조가 변경(changes)되면 스크래핑 코드를 변경해야 합니다.

5.4.1 StarWars

rvest에는 vignette("starwars")에 매우 간단한 예제가 포함되어 있습니다. 이것은 HTML이 최소화(minimal)된 간단한 페이지이므로 시작하기 좋은 곳(good place)입니다.

지금 해당 페이지로 이동(navigate)하여 “요소 검사(Inspect Element)”를 사용해 스타워즈 영화의 제목(title)인 제목(headings) 중 하나를 검사해 보시길 권장합니다(encourage).

키보드나 마우스를 사용하여 HTML의 계층 구조를 탐색(explore)하고 각 영화에서 사용된 공통(shared) 구조에 대해 파악(get a sense of)할 수 있는지 확인해 보세요(see if).

각 영화가 다음과 같은 공통 구조를 가지고 있음을 볼 수(see) 있어야 합니다(should be able to):

<section>
  <h2 data-id="1">The Phantom Menace</h2>
  <p>Released: 1999-05-19</p>
  <p>Director: <span class="director">George Lucas</span></p>
  
  <div class="crawl">
    <p>...</p>
    <p>...</p>
    <p>...</p>
  </div>
</section>

우리의 목표(goal)는 이 데이터를 title(제목), year(연도), director(감독), intro(소개) 변수가 있는 7행(7 row) 데이터 프레임으로 바꾸는(turn) 것입니다. HTML을 읽고 모든 <section> 요소를 추출하는 것(extracting)부터 시작하겠습니다.

url <- "https://rvest.tidyverse.org/articles/starwars.html"
html <- read_html(url)

section <- html |> html_elements("section")
section

이것은 해당 페이지에 있는 7편의 영화와 일치(matching)하는 7개의 요소를 검색(retrieves)하므로 section을 선택자로 사용하는 것이 좋다는(good) 것을 시사(suggesting)합니다. 데이터가 항상(always) 텍스트에 있기 때문에(found in) 개별(individual) 요소를 추출하는 것은 간단(straightforward)합니다. 올바른 선택자를 찾는(finding) 문제일 뿐입니다.

section |> html_element("h2") |> html_text2()

section |> html_element(".director") |> html_text2()

각 구성 요소에 대해 그 작업을 수행하고 나면(Once we’ve done that) 모든 결과를 티블로 감쌀(wrap all the results up into) 수 있습니다.

tibble(
  title = section |> 
    html_element("h2") |> 
    html_text2(),
  released = section |> 
    html_element("p") |> 
    html_text2() |> 
    str_remove("Released: ") |> 
    parse_date(),
  director = section |> 
    html_element(".director") |> 
    html_text2(),
  intro = section |> 
    html_element(".crawl") |> 
    html_text2()
)

나중에 분석(analysis)에서 쉽게 사용할 수 있는 변수를 얻기 위해 released를 약간 더 처리(processing)했습니다.

url <- "https://web.archive.org/web/20220201012049/https://www.imdb.com/chart/top/"
html <- read_html(url)

table <- html |> 
  html_element("table") |> 
  html_table()

여기에는 몇 개의 빈(empty) 열이 포함되어 있지만 전반적으로(overall) 표에서 정보를 잘 캡처합니다(does a good job of). 하지만 사용하기 쉽게 만들려면 처리를 좀 더 해야(need to do some more processing) 합니다. 먼저 작업하기 쉽게(easier to work with) 열의 이름을 바꾸고(rename) 순위(rank)와 제목(title)에서 불필요한(extraneous) 공백(whitespace)을 제거합니다. 한 단계(one step)에서 이 두 열의 이름 변경 및 선택을 수행하기 위해 (rename() 대신) select()를 사용합니다. 그런 다음 줄 바꿈(new lines)과 추가 공백을 제거한 다음 separate_wider_regex()를 적용하여 제목, 연도 및 순위를 각각 고유한(their own) 변수로 추출합니다.

ratings <- table |>
  select(
    rank_title_year = `Rank & Title`,
    rating = `IMDb Rating`
  ) |> 
  mutate(
    rank_title_year = str_replace_all(rank_title_year, "\n +", " ")
  ) |> 
  separate_wider_regex(
    rank_title_year,
    patterns = c(
      rank = "\\d+", "\\. ",
      title = ".+", " +\\(",
      year = "\\d+", "\\)"
    )
  )
ratings

대부분의 데이터가 표의 셀(cells)에서 나오는 이런 경우라도 원본(raw) HTML을 살펴볼 가치(worth)가 있습니다. 살펴보면(If you do so) 속성 중 하나를 사용하여 약간의 추가 데이터를 더할(add) 수 있음을 발견하게(discover) 될 것입니다. 페이지의 소스를 동굴 탐험하듯 살펴보는 데(spelunking) 약간의 시간을 투자(spending)할 가치가 있는 이유 중 하나는 추가 데이터를 찾거나 약간 더 쉬운(slightly easier) 구문 분석(parsing) 경로(route)를 찾을 수 있기 때문입니다.

html |> 
  html_elements("td strong") |> 
  head() |> 
  html_attr("title")

이것을 표 데이터와 결합(combine)하고 다시 separate_wider_regex()를 적용하여 관심 있는(care about) 데이터를 추출(extract out)할 수 있습니다.

ratings |>
  mutate(
    rating_n = html |> html_elements("td strong") |> html_attr("title")
  ) |> 
  separate_wider_regex(
    rating_n,
    patterns = c(
      "[0-9.]+ based on ",
      number = "[0-9,]+",
      " user ratings"
    )
  ) |> 
  mutate(
    number = parse_number(number)
  )

5.4.3 동적 사이트

지금까지 우리는 html_elements()가 브라우저에 표시되는 것을 그대로 반환하는 웹사이트에 중점을 두었고, 반환하는 내용을 구문 분석(parse)하는 방법과 깔끔한(tidy) 데이터 프레임으로 해당 정보를 구성(organize)하는 방법에 대해 논의했습니다.

하지만 때때로(From time-to-time) html_elements()와 친구들이(and friends) 브라우저에 표시되는 것과 전혀 다른 것을 반환하는 사이트에 부딪히게(hit) 됩니다.

대부분의 경우 이는(that’s because) 자바스크립트(javascript)를 사용하여 페이지의 콘텐츠를 동적으로 생성(dynamically generates)하는 웹사이트를 스크랩하려고 하기 때문입니다.

rvest는 원본 HTML을 다운로드하고 자바스크립트를 실행하지 않기 때문에 현재는 rvest로 작동하지 않습니다.

이러한 유형의 사이트를 스크랩하는 것은 여전히(still) 가능하지만 rvest는 모든 자바스크립트 실행을 포함하여 웹 브라우저를 완전히 시뮬레이션(fully simulating)하는 더 비싼 과정(expensive process)을 사용해야 합니다.

이 기능(functionality)은 집필 당시(time of writing)에는 사용할 수 없지만 우리가 적극적으로(actively) 작업하고 있는 부분이며 이 글을 읽을 즈음(by the time)에는 사용할 수 있을 것입니다.

이것은 백그라운드에서(in the background) 실제로 Chrome 브라우저를 실행하는 chromote 패키지(https://rstudio.github.io/chromote/index.html)를 사용하며, 인간이 텍스트를 입력하고 버튼을 클릭하는 것과 같이 사이트와 상호 작용(interact)할 수 있는 추가(additional) 도구를 제공합니다.

더 자세한 내용(more details)은 rvest 웹사이트 (http://rvest.tidyverse.org/)를 확인하세요(Check out).

6.1 리스트

지금까지 정수, 숫자, 문자, 날짜-시간 및 요인(factors)과 같은 간단한(simple) 벡터가 포함된 데이터 프레임으로 작업했습니다. 이러한 벡터는 동질적(homogeneous)이기 때문에, 즉 모든 요소가 동일한 데이터 유형이기 때문에 간단합니다. 동일한 벡터에 다른 유형의 요소를 저장(store)하려면 list()를 사용하여 생성하는 리스트(list)가 필요합니다.

x1 <- list(1:4, "a", TRUE)
x1

티블의 열 이름을 지정(naming)하는 것과 같은 방식으로 리스트의 구성 요소(components) 또는 자식(children)의 이름을 지정하는 것이 종종(often) 편리(convenient)합니다.

x2 <- list(a = 1:2, b = 1:3, c = 1:4)
x2

이러한 매우 간단한 리스트의 경우에도(Even for) 인쇄(printing)하는 데 꽤 많은 공간이 필요(takes up)합니다. 유용한 대안(alternative)은 str()로, 내용(contents)을 덜 강조하면서(de-emphasizing) 구조(structure)를 간결하게(compact) 표시합니다.

str(x1)
str(x2)

보시다시피(As you can see) str()은 리스트의 각 자식을 자체 줄에 표시(displays)합니다. 이름이 있는 경우(if present) 이름, 유형의 약어(abbreviation), 처음 몇 개의 값을 표시합니다.

6.1.1 계층 구조

리스트는 다른 리스트를 포함하여 모든 유형의 객체를 포함할 수 있습니다. 이로 인해(This makes them) 계층적(트리형) 구조를 나타내는 데 적합(suitable for)합니다.

x3 <- list(list(1, 2), list(3, 4))
str(x3)

이것은 평면(flat) 벡터를 생성하는 c()와 현저하게(notably) 다릅니다.

c(c(1, 2), c(3, 4))

x4 <- c(list(1, 2), list(3, 4))
str(x4)

리스트가 복잡(complex)해짐에 따라 str()은 계층 구조를 한눈에(at a glance) 볼 수 있게 해주므로 더 유용해집니다.

x5 <- list(1, list(2, list(3, list(4, list(5)))))
str(x5)

리스트가 훨씬(even) 더 크고 복잡해지면 str()은 결국 실패하기(fail) 시작하며(eventually) View()로 전환해야(switch to) 합니다.

뷰어(viewer)는 리스트의 최상위 수준(top level)만 표시하는 것으로 시작하지만 대화형으로(interactively) 구성 요소를 확장(expand)하여 자세히 볼 수 있습니다.

6.1.2 리스트 열

리스트는 티블 안에도 존재(live inside)할 수 있으며 이를 리스트-열(list-columns)이라고 부릅니다. 리스트-열은 일반적(usually)으로 티블에 속하지(belong) 않는(wouldn’t) 객체를 티블에 배치(place)할 수 있기 때문에 유용합니다.

특히 리스트-열은 모델 출력이나 재샘플(resamples)과 같은 것들을 데이터 프레임에 저장할 수 있게 해주기 때문에 tidymodels 생태계에서 많이 사용됩니다.

리스트 열의 간단한 예시(simple example)는 다음과 같습니다.

df <- tibble(
  x = 1:2, 
  y = c("a", "b"),
  z = list(list(1, 2), list(3, 4, 5))
)
df

티블의 리스트에는 특별한(special) 점이 없으며 다른 열과 똑같이 작동(behave like)합니다.

df |> 
  filter(x == 1)

리스트-열을 사용한 계산은(Computing with) 더 어렵지만(harder) 그것은 일반적으로 리스트를 사용한 계산이 더 어렵기 때문입니다.

기본(default) 인쇄 메서드는 내용의 대략적인 요약(rough summary)만 표시합니다. 리스트 열은 임의로(arbitrarily) 복잡할 수 있으므로 잘 인쇄할 방법(good way to print it)이 없습니다. 확인하려면(If you want to see it) 하나의 리스트-열만 추출(pull out)하여 위에서 배운 기술(techniques) 중 하나를 적용해야 합니다(df |> pull(z) |> str() 또는 df |> pull(z) |> View()).

6.1.3 중첩 해제

이제 리스트와 리스트-열의 기초(basics)를 배웠으므로 다시(back into) 일반 행과 열로 되돌리는(turn them) 방법을 살펴보겠습니다.

리스트-열은 두 가지 기본 형태인 명명된(named) 형태와 명명되지 않은(unnamed) 형태로 나타나는(come in) 경향(tend to)이 있습니다.

자식의 이름이 지정된 경우(When the children are named), 모든 행에서 동일한(same) 이름을 갖는 경향이 있습니다. 예를 들어 df1에서 리스트 열 y의 모든 요소에는 a와 b라는 두 개의 요소가 있습니다. 명명된 리스트-열은 자연스럽게(naturally) 열로 중첩 해제(unnest into)됩니다. 각각의 명명된 요소는 새로운 명명된 열이 됩니다.

df1 <- tribble(
  ~x, ~y,
  1, list(a = 11, b = 12),
  2, list(a = 21, b = 22),
  3, list(a = 31, b = 32),
)

자식의 이름이 없는 경우(When the children are unnamed), 요소 수는 행마다(from row-to-row) 다를(vary) 수 있습니다. 예를 들어 df2에서 리스트-열 y의 요소는 이름이 없으며 길이(length)가 하나에서 세 개까지 다릅니다. 명명되지 않은 리스트-열은 자연스럽게 행으로 중첩 해제(unnest into)됩니다. 각 자식마다 하나의 행을 얻게 됩니다.

df2 <- tribble(
  ~x, ~y,
  1, list(11, 12, 13),
  2, list(21),
  3, list(31, 32),
)

tidyr은 이 두 가지 경우(cases)에 대해 unnest_wider()와 unnest_longer()라는 두 가지 함수를 제공합니다.

6.1.4 unnest_wider()

df1처럼 각 행에 이름이 같은(same names) 요소가 같은(same) 수만큼 있는 경우 unnest_wider()를 사용하여 각 구성 요소를 고유한(its own) 열에 넣는 것이 자연스럽습니다.

df1 |> 
  unnest_wider(y)

기본적으로(By default) 새 열의 이름은 전적으로(exclusively from) 리스트 요소의 이름에서 가져오지만 names_sep 인수를 사용하여 열 이름과 요소 이름을 결합(combine)하도록 요청(request)할 수 있습니다. 이것은 반복되는(repeated) 이름을 명확히(disambiguating) 하는 데 유용합니다.

df1 |> 
  unnest_wider(y, names_sep = "_")

6.1.5 unnest_longer()

각 행에 명명되지 않은 리스트가 포함된 경우 unnest_longer()를 사용하여 각 요소를 자체(its own) 행에 넣는 것이 자연스럽습니다.

df2 |> 
  unnest_longer(y)

y 내부의 각 요소에 대해 x가 어떻게 복제(duplicated)되는지 주목하세요(Note how): 리스트-열 내부의 각 요소에 대해 한 행의 출력을 얻습니다(we get one row of output). 하지만 다음 예시처럼(as in the following example) 요소 중 하나가 비어(empty) 있으면 어떻게 됩니까?

df6 <- tribble(
  ~x, ~y,
  "a", list(1, 2),
  "b", list(3),
  "c", list()
)
df6 |> unnest_longer(y)

출력에 행이 0개이므로 해당 행이 효과적으로(effectively) 사라집니다(disappears). y에 NA를 추가하여 해당 행을 보존(preserve)하려면 keep_empty = TRUE를 설정하세요.

6.1.6 일관성 없는 유형

다양한(different) 유형의 벡터를 포함하는 리스트-열의 중첩을 해제하면 어떻게 되나요? 예를 들어 리스트 열 y에 일반적으로(normally) 단일 열에 섞일(mixed) 수 없는 두 개의 숫자, 하나의 문자 및 하나의 논리값(logical)이 포함된 다음 데이터셋을 살펴봅시다(take).

df4 <- tribble(
  ~x, ~y,
  "a", list(1),
  "b", list("a", TRUE, 5)
)

unnest_longer()는 항상(always) 변경되지 않은(unchanged) 열 집합을 유지하는(keeps) 반면 행 수는 변경(changing)합니다. 그럼 어떻게 될까요? unnest_longer()는 어떻게 y의 모든 항목을 유지(keeping everything)하면서 다섯 개의 행을 생성할까요?

df4 |> 
  unnest_longer(y)

보시다시피 출력에는 리스트-열이 포함되지만 리스트-열의 모든 요소에는 단일 요소(single element)가 포함되어 있습니다. unnest_longer()는 벡터의 공통 유형(common type)을 찾을 수 없기 때문에 원래(original) 유형을 리스트-열에 유지합니다. 이것이 열의 모든 요소가 동일한 유형이어야 한다는 계명(commandment)을 어기는(breaks) 것인지 궁금할 수 있습니다. 그렇지 않습니다(It doesn’t). 비록(even though) 내용물(contents)이 다른 유형일지라도 모든 요소는 리스트입니다.

일관성 없는(inconsistent) 유형을 처리하는 것은 까다롭고(challenging) 세부 사항은 문제의 정확한 성격(precise nature)과 여러분의 목표(goals)에 따라 다르지만(depend on) 십중팔구(most likely) 반복 및 순회하는 도구가 필요할 것입니다.

6.1.7 다른 함수들

tidyr에는 몇 가지 다른 유용한 직사각형화(rectangling) 함수가 있습니다.

  1. unnest_auto()는 리스트-열의 구조를 기반으로 unnest_longer()와 unnest_wider() 중 하나를 자동으로(automatically) 선택(picks)합니다. 빠른 탐색(rapid exploration)에는 유용하지만, 데이터가 어떻게 구성되어 있는지 이해하도록 강제(force)하지 않고 코드를 이해하기 어렵게 만들기 때문에 궁극적으로(ultimately) 나쁜 생각(bad idea)입니다.

  2. unnest()는 행과 열을 모두 확장(expands)합니다. 이 책에서는 볼 수 없지만 tidymodels 생태계를 사용하는 경우 접할 수 있는(encounter), 데이터 프레임과 같은 2D 구조를 포함하는 리스트-열이 있을 때 유용합니다.

이러한 함수는 다른 사람의 코드를 읽거나 드문 직사각형화 문제(rarer rectangling challenges)를 직접(yourself) 다룰 때(tackling) 만날(encounter) 수 있으므로 알아두면 좋습니다.

6.1.8 연습 문제

  1. df2와 같이 명명되지 않은 리스트-열과 함께 unnest_wider()를 사용하면 어떻게 됩니까? 이제 어떤 인수가 필요(necessary)합니까? 결측값(missing values)은 어떻게 됩니까?

  2. df1과 같이 명명된 리스트-열과 함께 unnest_longer()를 사용하면 어떻게 됩니까? 출력에서 어떤 추가 정보(additional information)를 얻습니까? 그 추가적인(extra) 세부 정보를 억제(suppress)하려면 어떻게 해야 합니까?

  3. 때때로(From time-to-time) 정렬된 값(aligned values)이 있는 여러 리스트-열을 가진 데이터 프레임을 만나게(encounter) 됩니다. 예를 들어 다음 데이터 프레임에서 y와 z의 값은 정렬(aligned)되어 있습니다(즉, y와 z는 항상 행 내에서 같은 길이를 가지며 y의 첫 번째 값은 z의 첫 번째 값에 해당(corresponds)합니다). 이 데이터 프레임에 두 번의 unnest_longer() 호출을 적용(apply)하면 어떻게 됩니까? x와 y 사이의 관계를 어떻게 보존(preserve)할 수 있습니까? (힌트: 문서(docs)를 주의 깊게(carefully) 읽어보세요).

df4 <- tribble(
  ~x, ~y, ~z,
  "a", list("y-a-1", "y-a-2"), list("z-a-1", "z-a-2"),
  "b", list("y-b-1", "y-b-2", "y-b-3"), list("z-b-1", "z-b-2", "z-b-3")
)

6.1.9 사례 연구

위에서 사용한 간단한 예시와 실제(real) 데이터의 주요(main) 차이점은 실제 데이터에는 일반적으로 unnest_longer() 및/또는 unnest_wider()를 여러 번(multiple) 호출해야 하는 중첩(nesting) 수준이 여러 개(multiple levels of) 포함(contains)되어 있다는 것입니다.

이것이 실제로 어떻게 작동(action)하는지 보여주기 위해 이 섹션에서는 repurrrsive 패키지의 데이터셋을 사용하여 세 가지 실제 직사각형화 과제(challenges)를 해결해(works through) 봅니다.

6.1.9.1 매우 넓은 데이터

gh_repos부터 시작하겠습니다. 이 데이터는 GitHub API를 사용하여 가져온 GitHub 리포지토리 모음(collection)에 대한 데이터를 포함하는 리스트입니다. 너무 깊게 중첩된 리스트라 이 책에서 구조를 보여주기(show) 어렵기 때문에 계속(continue)하기 전에 View(gh_repos)를 사용하여 직접(on your own) 조금 살펴보는(exploring) 것을 권장합니다.

gh_repos는 리스트이지만 도구(tools)는 리스트-열과 함께 작동하므로(work with) 이를 티블에 넣는(putting) 것부터 시작합니다. 나중에(later) 설명할(get to) 이유(reasons)로 이 열을 json이라고 부릅니다.

repos <- tibble(json = gh_repos)
repos

이 티블은 gh_repos의 각 자식(child)에 대해 하나씩(one row for each), 6개의 행을 포함합니다. 각 행에는 26개 또는 30개의 행이 있는 명명되지 않은 리스트가 포함됩니다. 이들은 명명되지 않았으므로 각 자식을 자체 행(its own row)에 넣기 위해 unnest_longer()로 시작합니다.

repos |> 
  unnest_longer(json)

언뜻 보기에(At first glance)는 상황(situation)이 개선(improved)되지 않은 것 같을 수 있습니다. 행은 더 많아졌지만(6개 대신 176개) json의 각 요소는 여전히 리스트입니다. 하지만 중요한 차이점이 있습니다. 이제 각 요소가 명명된 리스트이므로 unnest_wider()를 사용하여 각 요소를 고유한 열(its own column)에 넣을 수 있습니다.

repos |> 
  unnest_longer(json) |> 
  unnest_wider(json)

이 작업은 잘 되었지만 결과(result)는 조금 압도적(overwhelming)입니다. 열이 너무 많아서 티블이 모두 인쇄하지조차 못합니다(doesn’t even print all of them)! names()를 사용하여 모두(them all) 볼 수 있으며, 여기서는 처음 10개만 봅니다.

repos |> 
  unnest_longer(json) |> 
  unnest_wider(json) |> 
  names() |> 
  head(10)

흥미로워 보이는 몇 가지를 뽑아보겠습니다(pull out):

repos |> 
  unnest_longer(json) |> 
  unnest_wider(json) |> 
  select(id, full_name, owner, description)

이것을 사용하여(use this to) gh_repos가 어떻게 구성(structured)되었는지 거꾸로(work back) 이해(understand)할 수 있습니다. 각 자식은 자신이 생성(created)한 최대 30개의 GitHub 리포지토리 리스트를 포함하는 GitHub 사용자였습니다.

owner는 또 다른 리스트-열이며 명명된 리스트가 포함되어 있으므로 unnest_wider()를 사용하여 값에 접근할(get at) 수 있습니다.

#| error: true
repos |> 
  unnest_longer(json) |> 
  unnest_wider(json) |> 
  select(id, full_name, owner, description) |> 
  unnest_wider(owner)

어어(Uh oh), 이 리스트 열에도 id 열이 포함되어 있는데(contains) 같은 데이터 프레임에 두 개의 id 열을 가질(have) 수 없습니다. 제안(suggested)된 대로 names_sep을 사용하여 문제(problem)를 해결(resolve)해 봅시다.

repos |> 
  unnest_longer(json) |> 
  unnest_wider(json) |> 
  select(id, full_name, owner, description) |> 
  unnest_wider(owner, names_sep = "_")

이것은 또 다른 넓은(wide) 데이터셋을 제공하지만 owner에 리포지토리를 “소유한(owns)” 사람에 대한 많은 추가 데이터가 포함된 것 같다는(appears to contain) 느낌(sense)을 받을 수 있습니다.

6.1.9.2 관계형 데이터

중첩된(Nested) 데이터는 일반적으로 여러 데이터 프레임에 걸쳐(across) 분산되어(spread) 있는 데이터를 나타내는(represent) 데 종종 사용됩니다(sometimes used to). 예를 들어 왕좌의 게임(Game of Thrones) 책과 TV 시리즈에 등장하는(appear in) 캐릭터에 대한 데이터가 포함된 got_chars를 살펴보겠습니다(take). gh_repos와 마찬가지로 리스트이므로(it’s a list) 티블의 리스트 열로 전환(turning)하는 것부터 시작합니다.

chars <- tibble(json = got_chars)
chars

json 열에는 명명된 요소가 포함되어 있으므로(contains named elements) 넓히기(widening)로 시작하겠습니다.

chars |> 
  unnest_wider(json)

그리고 읽기 쉽도록(easier to read) 몇 개의 열을 선택합니다.

characters <- chars |> 
  unnest_wider(json) |> 
  select(id, name, gender, culture, born, died, alive)
characters

이 데이터셋에는 여러(many) 리스트 열도 포함되어 있습니다.

chars |> 
  unnest_wider(json) |> 
  select(id, where(is.list))

titles 열을 살펴보겠습니다(explore). 이것은 이름이 없는 리스트-열이므로 행으로 중첩 해제합니다(unnest it into rows):

chars |> 
  unnest_wider(json) |> 
  select(id, titles) |> 
  unnest_longer(titles)

필요에 따라(as needed) 캐릭터 데이터에 쉽게 조인(join)할 수 있기 때문에 이 데이터를 고유한(its own) 테이블에서 볼 수 있을 것으로 기대할(expect) 수 있습니다. 그렇게 해보겠습니다. 이를 위해서는 빈 문자열(empty strings)이 포함된 행을 제거(removing)하고 각 행에 이제(now) 단일 칭호(single title)만 포함되어 있으므로 titles의 이름을 title로 바꾸는(renaming) 약간의 정리(little cleaning)가 필요합니다.

  unnest_wider(json) |> 
  select(id, titles) |> 
  unnest_longer(titles) |> 
  filter(titles != "") |> 
  rename(title = titles)
titles

6.1.9.3 깊은 중첩

풀기(unravel) 위해(requires) unnest_wider()와 unnest_longer()를 여러 번 반복해서(repeated rounds of) 호출해야 하는 매우 깊게(very deeply) 중첩된 리스트-열인 gmaps_cities로 이 사례 연구를 마무리(finish off)하겠습니다.

이것은 5개의 도시 이름과 Google의 geocoding API를 사용하여 위치(location)를 확인한(determine) 결과(results)가 포함된(containing) 2열짜리 티블입니다.

gmaps_cities

json은 내부(internal) 이름이 있는 리스트-열이므로 unnest_wider()로 시작합니다.

gmaps_cities |> 
  unnest_wider(json)

이것은 우리에게 status와 results를 줍니다(gives us). 이것들이(they’re) 모두 OK이므로(since) status 열을 삭제(drop)할 것입니다; 실제(real) 분석에서는 status != "OK"인 모든 행을 캡처(capture)하고 무엇이 잘못되었는지(went wrong) 파악(figure out)하려고 할 것입니다. results는 하나 또는 두 개의 요소가 있는 이름 없는 리스트이므로(이유는 잠시 후에 알게 될 것입니다) 행으로 중첩 해제합니다.

gmaps_cities |> 
  unnest_wider(json) |> 
  select(-status) |> 
  unnest_longer(results)

이제 results가 이름이 지정된(named) 리스트이므로 unnest_wider()를 사용합니다.

locations <- gmaps_cities |> 
  unnest_wider(json) |> 
  select(-status) |> 
  unnest_longer(results) |> 
  unnest_wider(results)
locations

이제 왜(why) 두 도시가 두 개의 결과를 얻었는지(got) 알 수 있습니다. 워싱턴(Washington)은 워싱턴 주(state)와 워싱턴 DC 모두 일치(matched)했고 알링턴(Arlington)은 버지니아주(Virginia) 알링턴과 텍사스주(Texas) 알링턴 모두 일치했습니다.

여기서(from here) 우리가 갈 수 있는 몇 가지 다양한(different) 곳이 있습니다. 우리는 일치하는 항목의 정확한 위치(exact location)를 확인(determine)하고 싶을 수 있으며 이는 geometry 리스트 열에 저장(stored)되어 있습니다.

locations |> 
  select(city, formatted_address, geometry) |> 
  unnest_wider(geometry)

새로운(new) bounds(직사각형 영역)와 location(포인트)을 제공(gives)합니다. 위도(latitude, lat)와 경도(longitude, lng)를 보려면 location을 중첩 해제(unnest)할 수 있습니다.

locations |> 
  select(city, formatted_address, geometry) |> 
  unnest_wider(geometry) |> 
  unnest_wider(location)

경계를 추출(Extracting)하려면 몇 가지 단계(steps)가 더 필요(requires)합니다.

locations |> 
  select(city, formatted_address, geometry) |> 
  unnest_wider(geometry) |> 
  # 관심 변수에 초점을 맞춤 (focus on the variables of interest)
  select(!location:viewport) |>
  unnest_wider(bounds)

그런 다음 짧지만(short) 환기(evocative)하기 쉬운 이름을 만들기 위해 names_sep을 사용할 수 있도록(so we can use) southwest와 northeast(직사각형의 모서리)의 이름을 바꿉니다(rename).

locations |> 
  select(city, formatted_address, geometry) |> 
  unnest_wider(geometry) |> 
  select(!location:viewport) |>
  unnest_wider(bounds) |> 
  rename(ne = northeast, sw = southwest) |> 
  unnest_wider(c(ne, sw), names_sep = "_")

변수(variable) 이름 벡터를 unnest_wider()에 제공(supplying)하여 어떻게(how) 두 열을 동시에(simultaneously) 중첩 해제(unnest)하는지 주목하세요(Note).

관심 있는 구성 요소로 가는(get to) 경로(path)를 발견(discovered)하면(Once) 또 다른 tidyr 함수인 hoist()를 사용하여 구성 요소를 직접(directly) 추출(extract)할 수 있습니다.

  select(city, formatted_address, geometry) |>

    geometry,
    ne_lat = c("bounds", "northeast", "lat"),
    sw_lat = c("bounds", "southwest", "lat"),
    ne_lng = c("bounds", "northeast", "lng"),
    sw_lng = c("bounds", "southwest", "lng"),

이러한 사례 연구가 실생활(real-life)의 직사각형화에 대한 식욕(appetite)을 돋우었다면(whetted) vignette("rectangling", package = "tidyr")에서 몇 가지 예시를 더 볼 수 있습니다.

6.2 JSON

JSON은 javascript object notation의 약자(short for)이며 대부분의 웹 API가 데이터를 반환(return)하는 방식입니다.

JSON과 R의 데이터 유형은 꽤 비슷하지만(pretty similar) 완벽한 1대1 매핑(mapping)이 없기 때문에 이것을 이해하는 것이 중요하며, 문제가 발생했을 때(if things go wrong) JSON에 대해 조금 이해하는 것이 좋습니다.

6.2.1 데이터 유형

JSON은 사람이 아닌 기계가 쉽게 읽고 쓸 수 있도록 설계된 간단한 형식(simple format)입니다. 여기에는 6가지 핵심(key) 데이터 유형이 있습니다. 그중 4개는 스칼라(scalars)입니다.

  1. 간단한(simplest) 유형은 R의 NA와 같은 역할(role)을 하는 null(null)입니다. 데이터의 부재(absence)를 나타냅니다(represents).

  2. 문자열(string)은 R의 문자열과 매우 유사하지만(much like) 항상 큰따옴표(double quotes)를 사용해야 합니다.

  3. 숫자(number)는 R의 숫자와 유사합니다(similar to): 정수(123), 소수(decimal, 예: 123.45) 또는 과학적(scientific, 예: 1.23e3) 표기법(notation)을 사용할 수 있습니다. JSON은 Inf, -Inf 또는 NaN을 지원하지 않습니다.

  4. 부울(boolean)은 R의 TRUE 및 FALSE와 유사하지만 소문자 true 및 false를 사용합니다.

JSON의 문자열, 숫자 및 부울은 R의 문자, 숫자 및 논리(logical) 벡터와 꽤 유사합니다(pretty similar). 큰 차이점은 JSON의 스칼라는 단일 값(single value)만 나타낼(represent) 수 있다는 것입니다. 여러(multiple) 값을 나타내려면 나머지(remaining) 두 가지 유형인 배열(arrays)과 객체(objects) 중 하나를 사용해야 합니다.

배열과 객체 모두 R의 리스트와 유사합니다. 차이점은 이름이 지정(named)되어 있는지 여부(whether or not)입니다. 배열(array)은 이름이 없는 리스트와 같으며 []로 작성(written with)됩니다. 예를 들어 [1, 2, 3]은 3개의 숫자를 포함하는 배열이고 [null, 1, "string", false]는 null, 숫자, 문자열 및 부울을 포함하는 배열입니다.

객체(object)는 이름이 지정된 리스트와 같으며 {}로 작성됩니다. 이름(JSON 용어로는 키(keys))은 문자열이므로 따옴표로 묶어야(surrounded by quotes) 합니다. 예를 들어 {"x": 1, "y": 2}는 x를 1에 매핑(maps)하고 y를 2에 매핑하는 객체입니다.

JSON에는 날짜(dates)나 날짜-시간(date-times)을 나타내는(represent) 기본(native) 방법이 없으므로 종종 문자열로 저장(stored)되며, 올바른 데이터 구조로 바꾸려면(turn) readr::parse_date() 또는 readr::parse_datetime()을 사용해야(need to use) 합니다.

마찬가지로(Similarly) JSON에서 부동 소수점 숫자(floating point numbers)를 나타내는 JSON의 규칙은 약간 부정확하므로(imprecise) 문자열로 저장된 숫자를 종종(sometimes) 발견할 수 있습니다.

필요에 따라(As needed) readr::parse_double()을 적용(Apply)하여 올바른 변수 유형을 얻습니다.

6.2.2 jsonlite

JSON을 R 데이터 구조로 변환하려면 Jeroen Ooms의 jsonlite 패키지를 추천(recommend)합니다. 여기서는 read_json()과 parse_json()이라는 두 가지 jsonlite 함수만 사용할 것입니다. 실생활(In real life)에서는 디스크에서 JSON 파일을 읽기 위해 read_json()을 사용합니다. 예를 들어 repurrsive 패키지는 gh_user의 소스도 JSON 파일로 제공하며 read_json()을 사용하여 읽을 수 있습니다.

# 패키지 내부의 json 파일에 대한 경로:
gh_users_json()

# read_json()으로 읽기
gh_users2 <- read_json(gh_users_json())

# 이전에 사용하던 데이터와 동일한지 확인
identical(gh_users, gh_users2)

이 책에서는 JSON이 포함된 문자열을 가져와(takes) 간단한 예제를 생성하는 데 적합(good for)하므로 parse_json()도 사용할 것입니다.

시작하기(To get started) 위해 여기 세 가지 간단한 JSON 데이터셋이 있습니다. 숫자로 시작한 다음 배열에 몇 개의 숫자를 넣고 마지막으로 해당 배열을 객체에 넣습니다.

str(parse_json('1'))
str(parse_json('[1, 2, 3]'))
str(parse_json('{"x": [1, 2, 3]}'))

jsonlite에는 fromJSON()이라는 또 다른 중요한 함수가 있습니다. 자동 단순화(automatic simplification)(simplifyVector = TRUE)를 수행하므로 여기서는 사용하지 않습니다.

이것은 특히 간단한 경우에 자주 잘 작동(works well)하지만 직사각형화는 여러분이 직접(yourself) 수행하여 정확히(exactly) 무슨 일이 일어나고 있는지(what’s happening) 알고 복잡한(complicated) 중첩 구조를 더 쉽게 처리(handle)할 수 있도록 하는 것이 더 낫다고(better off) 생각합니다.

6.2.3 직사각형화 과정 시작하기

대부분의 경우 JSON 파일에는 단일 최상위(top-level) 배열이 포함되어 있습니다. 여러 “항목(things)”(여러 페이지, 여러 레코드 또는 여러 결과)에 대한 데이터를 제공하도록 설계(designed)되었기 때문입니다.

이 경우 각 요소가 행이 되도록(becomes a row) tibble(json)을 사용하여 직사각형화(rectangling)를 시작하게 됩니다.

json <- '[
  {"name": "John", "age": 34},
  {"name": "Susan", "age": 27}
]'
df <- tibble(json = parse_json(json))
df

df |> 
  unnest_wider(json)

드문 경우(In rarer cases)지만 JSON 파일이 하나의 “항목”을 나타내는 단일 최상위 JSON 객체로 구성(consists of)되기도 합니다.

이 경우 티블에 넣기(put) 전에 리스트로 감싸서(wrapping it in a list) 직사각형화 과정을 시작(kick off)해야 합니다.

json <- '{
  "status": "OK", 
  "results": [
    {"name": "John", "age": 34},
    {"name": "Susan", "age": 27}
 ]
}
'
df <- tibble(json = list(parse_json(json)))
df

df |> 
  unnest_wider(json) |> 
  unnest_longer(results) |> 
  unnest_wider(results)

또는 구문 분석된 JSON 내부에 접근(reach inside)하여 실제로 관심 있는(care about) 부분(bit)부터 시작할 수도 있습니다.

df <- tibble(results = parse_json(json)$results)
df |> 
  unnest_wider(results)
